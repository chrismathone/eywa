# 역동기화(eywa → makeedu) 타당성 검토

작성 2026-07-02. 읽기 전용 정찰(로그인 후 각 목록의 폼·등록 링크·AJAX 엔드포인트 구조만 덤프, 제출·저장 클릭 없음) 결과.

> **상태: 아래 권장 opt-in 경로(QR 접수 상담 건별 수동 푸시)가 v1으로 구현·실검증됨(2026-07-02).**
> 설계·매핑·운영 런북 = [makeedu-reverse-sync-v1.md](makeedu-reverse-sync-v1.md). 전면 자동 양방향 비권장 결론은 유지.

## 요약 (결론 먼저)

**기술적으로는 가능하지만, "전면 자동 양방향 동기화"는 권장하지 않는다.** makeedu에 공개 API·CSRF 토큰이 없어
현행 스크래퍼와 같은 세션으로 폼 POST를 재현하면 쓰기가 되긴 한다. 그러나 makeedu는 **운영의 정본(system of
record)** 이고 전체 동기화 설계가 "makeedu=진실, eywa=그 아래 additive 오버레이" 위에 서 있다. eywa를 정본에
써 넣는 순간 그 불변식이 깨지고, 잘못 쓰면 **되돌릴 수 없는 실운영 데이터 오염**이 makeedu 쪽에 난다.

→ **권장: 전면 자동 푸시는 하지 않는다. 대신 "eywa가 원본인, 손으로 이중 입력하던 소수 레코드"에 한해
사람이 건별 확인하는 opt-in 푸시**만 선택적으로 검토한다(가장 강한 후보 = QR 공개접수로 들어온 신규 상담).

## makeedu 쓰기 인터페이스 정찰 결과

- makeedu는 서버렌더 JSP/Struts류 앱. 모든 폼이 **POST `*.do`**, 목록↔상세↔등록이 `_regist.do`(GET 폼) +
  `*InsProc.do`(POST 저장) 쌍으로 돌아간다.
- **CSRF 토큰이 없다**(모든 페이지 `csrfHiddens` = 빈 배열). 즉 스크립트가 폼 필드만 맞춰 POST하면 서버가 받는다
  = 자동 쓰기가 기술적으로 막혀 있지 않다.
- 도메인별 등록 진입점(정찰로 확인):
  - 원생 등록 `/member/student/list_regist.do`
  - **상담 등록 `/counsel/counselList_regist.do`** (예비/재원 공용, `?callpage=res`로 예비 구분) — 역동기화 최유력 후보
  - 반/수업 `/lesson/lessonAllList_regist.do`, 수업원생추가 `/lesson/lessonRegist.do`
  - 수납 추가 `/pay/payMngList.do` + `insForm`, 성적 `/lesson/markRegist.do`
- 다만 저장 폼은 **복잡한 hidden 배열 상태머신**(예: `insForm`의 `studNoChgArr/reqAmtChgArr/...`, `findForm`의
  다중 Arr 필드)이라, 유효한 POST 한 번을 재현하는 게 취약하고 makeedu UI 버전 변경에 잘 깨진다.

## 역동기화가 읽기 동기화보다 근본적으로 위험한 이유

1. **정본에 쓰기.** makeedu가 진실이라는 전제(전체 sync 설계의 뿌리)를 뒤집는다. 버그 = makeedu 실데이터 오염,
   언두 없음. 읽기는 틀려도 eywa만 지저분해지지만, 쓰기는 학원 운영 시스템을 건드린다.
2. **멱등 키 부재.** 읽기는 `makeedu_id`로 매칭해 additive. 쓰기는 makeedu에 upsert가 없어 **POST는 항상 insert** →
   재실행·중복 요청 시 makeedu에 **중복 레코드**가 쌓인다(eywa처럼 자연키 유니크 제약이 없음).
3. **봇/캡차 위험 증가.** makeedu는 이미 낯선 IP·헤드리스 로그인을 CAPTCHA로 막는다. 자동 **쓰기** POST는 읽기보다
   abuse 탐지를 훨씬 잘 건드린다(계정 잠금 리스크).
4. **신뢰 IP 제약 동일.** 읽기와 같은 집 PC(신뢰 IP)에서만 가능 → 워처 상주 인프라를 그대로 얹어야 한다.
5. **양방향 = 충돌·에코 루프.** 같은 레코드를 양쪽이 고치면 어느 쪽이 이기나? 마지막 쓰기가 이기고, 읽기 sync가
   그걸 다시 끌어와 덮는 **핑퐁**이 난다. 필드 소유권(누가 어느 필드의 정본인가) 설계가 선행돼야 한다.

## 그럼에도 가치 있는 좁은 케이스 (검토 대상)

전면 푸시가 아니라 **"eywa가 원본이라 어차피 사무실이 makeedu에 손으로 다시 치는 것"** 만 골라 밀어주면 이중
입력을 없애면서 위 위험 대부분을 피한다(방향이 항상 eywa→makeedu 단방향 = 에코 루프 없음, 신규 생성만 =
필드 소유권 충돌 없음):

- **최유력: QR 공개접수 상담**(`enrollment_consultations.from_public_intake=true`). 학부모가 eywa QR 폼으로
  넣은 신규 상담은 makeedu에 없어 사무실이 지금 손으로 재입력한다 → `/counsel/counselList_regist.do`에 건별 푸시.
  · 저volume(하루 몇 건), 항상 신규(중복 위험 낮음), eywa가 명백한 원본.
- 차선: eywa에서 새로 만든 **등록 상담 → makeedu 예비 상담**.

이것도 **자동이 아니라 "이 건 makeedu로 보내기" 버튼 + 성공 후 makeedu가 돌려준 seq를 eywa에 저장(재푸시 차단)**
형태여야 한다. 즉 읽기 동기화의 거울(정본 갱신)이 아니라, **명시적·건별·멱등가드 있는 단방향 보조 기능**.

## 권장 결론

- **하지 말 것:** 학생/반/수납/성적의 전면 자동 양방향 동기화. 정본 오염·중복·핑퐁·캡차 리스크 대비 이득이 적다.
  이 도메인들은 사무실이 makeedu에서 직접 입력하는 게 맞다(현행 유지).
- **검토 가치 있음(opt-in):** QR 공개접수 신규 상담의 eywa→makeedu **건별 수동 푸시**(버튼 + 멱등 가드 + 워처 릴레이
  재사용). 이중 입력 제거가 실이득. 별도 결정·설계 필요(이번 범위 아님).
- 어느 쪽이든 **쓰기는 반드시 사람이 트리거**하고, makeedu가 반환한 식별자를 eywa에 저장해 재푸시를 막아야 한다.
