# 연동 PC 조회 오류 수정 및 handoff

## 재현과 원인

1.0.1 설치 파일을 게시·등록했지만 운영 `학원 설정 → 연동 → 연동 PC`에서 `처리하지 못했습니다. 잠시 후 다시 시도해 주세요.`가 표시됐다. 별도 로그인된 Orca 탭에서 같은 오류와 비활성 설정, `설치 파일을 준비 중입니다`를 재현했다. 다운로드·기기 상태·설정의 묶음 조회가 실패했는데 클라이언트가 조회 실패를 “게시되지 않음/기기 없음/기록 없음”으로 표시했다.

앱과 같은 프로젝트의 서버 DB 연결을 검사하니 Supabase 세션 풀(5432)이 `XX000 / (EMAXCONNSESSION) max clients reached in session mode ... pool_size: 15`로 연결을 거부했다. 트랜잭션 풀(6543)에서는 같은 계정·DB의 조회가 성공했다. Vercel 운영 로그는 연결된 관리 계정의 403 및 CLI의 `The specified scope does not exist` 때문에 열지 못했으므로 해당 운영 로그가 직접 원인을 확인해 주었다고 주장하지 않는다. 운영 화면 재현·실제 프로젝트의 DB 오류·트랜잭션 연결 및 배포 후 화면 확인을 근거로 한다.

## 구현

- `agentDb`만 Supabase 공유 세션 풀 URL의 포트를 6543으로 바꾼다. 호스트·계정·비밀번호·DB·쿼리 옵션을 보존한다. 직접 연결·로컬 시험 DB·다른 제공자·이미 설정된 트랜잭션 연결은 그대로다. 기존 PC 워커와 다른 기능의 `DATABASE_URL`은 수정하지 않는다.
- 준비된 쿼리는 끄고, 인스턴스별 문장용 풀과 트랜잭션용 풀을 각각 최대 1개 연결·10초 idle로 제한한다. 문장용 풀의 pipelining은 0이다. SQL 문자열·지점 필터·권한 확인은 변경하지 않는다.
- postgres.js 3.4.9에서 pipelining 1의 동시 독립 조회가 멈추는 경우를 실제 DB에서 확인했고, 0에서는 독립 조회가 정상이나 네이티브 `sql.begin()`의 초기화가 `TypeError ... reading 'queue'`로 실패하는 것도 재현했다. 라이브러리를 수정하지 않고 **네이티브 BEGIN 전용 풀**로 이 제약을 처리했다. 이 풀은 독립 조회를 받지 않으며 BEGIN이 잡은 연결에서 원래 콜백·잠금·SET LOCAL·COMMIT/ROLLBACK을 수행한다. 두 풀 모두 종료한다.
- 서버 액션 실패 시 SQLSTATE의 제한된 문자열과 오류 범주만 관측성 로그에 기록한다. 원본 오류·SQL·파라미터·DB 비밀은 기록하지 않는다. 연결 한도 오류는 새로고침을 안내한다.
- 클라이언트는 로딩·조회 실패·실제 빈 조회를 구별한다. 조회하지 못했을 때 코드 발급을 비활성화하고 네트워크 예외도 처리한다. 기존에 성공적으로 얻은 다운로드 URL은 이후 일시적 조회 실패가 있어도 보존한다.

## 검증

- 관련 Vitest **8개 파일 / 42개 검사 통과**: DB URL의 프로젝트/자격/SSL 보존·다른 호스트 제외, 풀 구분과 종료, 권한 거절 후 DB 미조회, 민감 오류 로그 차단, 로딩/실패/복구 UI, 기존 API 인증·첨부 경계·카탈로그와 연동 탭.
- 전체 `npm run typecheck`, 변경 파일 ESLint, `git diff --check` 통과.
- 실제 프로젝트 DB 읽기 검증 **7개 통과**: 동시 파라미터 조회 16개의 결과 보존, 지점별 RLS, 트랜잭션 종료 후 역할 초기화, 서로 다른 지점의 대기 트랜잭션 격리, 실패 시 로컬 설정 롤백, 화면의 모든 SQL 조회, 기기/릴리스 수 보존.
- 검증 당시 기기·이벤트·설정 행은 0개, 정식 릴리스는 1.0.1이었다. 코드 발급·PC 등록·연동 시작·발송·동기화·운영 설정 저장은 하지 않았다.
- [Supabase 접속 가이드](https://supabase.com/docs/guides/database/connecting-to-postgres) 및 [postgres.js 제한](https://supabase.com/docs/guides/database/postgres-js)을 확인했다. 서버리스의 트랜잭션 방식과 pipelining/BEGIN 제약을 실제 사용 중인 라이브러리와 DB로 대조했다.

개인 검증 산출물은 무시된 `work/sync-agent-publish/2/transaction-verification.json`에 있다. 실제 PC 이전은 별도이며 [운영 안내](../../apps/sync-agent/README.md)의 순서를 따른다. 이번 변경은 웹 서버 쪽이므로 공개한 1.0.1 EXE·서명된 ZIP을 교체하지 않는다.
