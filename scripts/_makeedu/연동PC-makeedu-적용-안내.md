> 아래 파일들을 덮어써야 새 기능이 돕니다.

## 🔴🔴 청구월 앵커 수정 + 대량 무효 차단 (2026-07-31 4차 — 첫 실행 결과 반영)

3차를 실제로 돌려보고 **두 가지가 드러났다.** 이 zip에 수정이 들어 있다.

**① 청구월을 달력으로 계산하면 안 된다.** makeedu는 **선청구**라 달력 7월에 이미 청구월이 2026-08이다.
달력 기준 `당월-2 ~ 당월` = `2026-05~2026-07`이 되어 **정작 살아있는 2026-08이 통째로 빠졌고**,
그 달 360건이 한 번도 갱신되지 않아 미수 ₩54M이 옛 스냅샷으로 굳었다.
→ **앵커 = 화면의 `fromYm` 기본값**(= makeedu가 말하는 현재 청구월)으로 바꿨다. 못 읽으면 달력 당월 **+1**까지 본다.

**② 범위를 넓힌 첫 실행에서 17건이 한 번에 무효 처리됐다**(₩5.4M). 새로 범위에 들어온 달의 행은
그동안 스크랩 밖이었다는 이유만으로 "부재 지속일"이 길게 잡혀 가드를 **전부 정상 통과**한다 —
개별 가드로는 원리적으로 못 막는 상황이다.
→ **대량 무효 서킷브레이커**: 한 실행에서 10건을 넘기면 **전부 보류**하고 사람을 부른다.
   목록을 확인한 뒤 의도한 정리면 `--allow-bulk-void`(또는 `MAKEEDU_ALLOW_BULK_VOID=true`)로 실행한다.

## 🔴🔴 스크랩 검색 조건 2건 수정 (2026-07-30 3차 — 프로브 실측)

연동 PC 프로브로 상세수납 화면을 열어 보니, **목록이 검색 조건이 걸린 채로 열리고 있었다.** 둘 다 동기화를
조용히 망가뜨리던 원인이다.

| 조건 | 옛 기본값 | 무슨 일이 있었나 | 바뀐 값 |
|---|---|---|---|
| `studStatus` | **재원생만** | 휴·퇴원생의 **살아있는 청구가 목록에 안 보였다** → 임포터가 "삭제됨"으로 오판 | **전체원생** |
| `fromYm`~`toYm` | 당월 1개월 | 청구월이 넘어가면 직전 달이 **영원히 갱신 안 됨**(2026-07이 07-16에 동결, 미수 ₩12.86M이 스냅샷으로 굳음) | **당월+직전 2개월** |

실측: 재원생만 855건 → 전체원생 **857건**(2건이 숨어 있었다) → 3개월 범위 **3,174건**.

🔴 **삭제 판정의 전제가 퇴원생에 대해 틀렸던 것**이라, 이 수정이 5번째 가드보다 더 근본이다.
이미 무효 처리된 청구가 다음 실행에서 목록에 다시 나타나면 **자동으로 복원**된다(`[동기화]` 마커도 지워진다).

⚠️ 개월 수는 `MAKEEDU_INVOICE_MONTHS`(기본 3)로 조절한다. 늘리면 스크랩 시간이 그만큼 는다.
⚠️ 스크래퍼가 화면의 `총 N건`을 함께 저장해 **수집 행수와 대조**한다. 다르면 '절단 의심'으로 배지에 뜬다 —
   목록을 덜 받은 상태의 삭제 판정은 전부 신뢰할 수 없기 때문에 대조보다도 먼저 보고한다.

## 🔴 수납 삭제 반영이 달라진다 (2026-07-30 2차)

지금까지 "makeedu에서 사라진 청구"의 판정 근거는 **전부 eywa가 가진 정황**이었다 — 활성 수강이 없다,
며칠째 안 보인다. 그런데 그날 부재 18건을 실제로 뜯어보니 **13건이 재원생**이었고 2건은 06:00엔 있다가
18:00에 사라졌다. 12시간 만의 이탈은 '삭제'보다 **다른 청구월로 옮겨졌거나 수납 처리된 것**에 가깝다.
정황만으로는 이 둘을 못 가른다.

**퇴원 목록은 makeedu가 직접 "이 원생은 퇴원"이라고 말하는 유일한 증거다.** 그래서 무효 처리는 이제
기존 4중 가드 + **퇴원 목록에서 원생번호가 확인된 건**만 통과한다.

- 목록을 못 읽으면(파일 없음·헤더 변경) **가드만 꺼진 채 진행**한다(동기화는 안 멈춘다). 꺼졌다는 사실은
  로그·리포트·화면 배지에 남는다 — 조용히 약해지지 않는다.
- `makeedu_id`가 없는 학생은 통과시키지 않는다. 이름 매칭은 동명이인·개명으로 틀리고, **틀리면 남의 청구를 지운다.**
- 낡은 `withdrawn.json`이 남아 있어도 양방향으로 안전하다: 재등원한 학생은 활성 수강 가드가 막고,
  새로 퇴원한 학생은 목록에 없어 보류될 뿐이다.

## 🔴 월별 대조가 붙는다 — "맞는지"를 실행이 스스로 확인한다

동기화는 지금까지 **넣고 끝**이었다. 그래서 2026-07이 07-16에 통째로 멈춘 뒤에도 화면 배지는 2주 내내
초록불이었다 — 맞는지 아무도 확인하지 않았기 때문이다. 이제 매 실행이 월별로 검산한다:

`makeedu 라인 합` → `eywa 집계 합` → `저장 후 DB 합` — **허용 오차 0원.**

1원이라도 어긋나면 `makeedu_sync_state.error`에 실려 화면 동기화 배지가 **amber '확인 필요'** 로 바뀐다.
연동 PC 로그에도 월별 표(`✅/🔴`)가 찍힌다.

## 🔴 이번에 확인된 사실 (설계가 바뀐 근거)

**연동 PC(신뢰 IP)에서는 ID/PW 자동 로그인이 CAPTCHA 없이 통과한다** — 실측 `login ok → main.do`.
CAPTCHA는 **낯선 IP·헤드리스**에서만 걸린다. 그래서:

- **세션 캡처(`capture-session.cjs`)는 이 PC에선 필요 없다** — 매 실행마다 로그인하면 된다.
- 따라서 감시할 것은 "세션 만료"가 아니라 **"로그인 자체가 실패하는 날"**(비밀번호 변경·CAPTCHA 도입·계정 잠금)이다.
  그날 동기화가 **조용히** 멈추므로 `check-session.mjs`가 원장 벨에 알린다.
- ⚠️ 로그인 실패 시 **재시도하지 않는다**(반복 실패 = 계정 잠금).

## 적용 절차

1. zip을 `C:\eywa-sync-pc` 폴더에서 **'여기에 압축 풀기'**(덮어쓰기). ⚠️ **폴더 전체**를 덮는다 —
   스크립트들이 `lib.cjs`·`invoice-stale.cjs`를 공유하므로 부분 복사는 버전이 섞인다.
2. 동작 확인:
   ```
   cd /d C:\eywa-sync-pc
   node --env-file=C:\eywa-sync-pc\.env.local scripts\_makeedu\scrape.cjs --list=withdrawn
   node --env-file=C:\eywa-sync-pc\.env.local scripts\_makeedu\check-session.mjs --dry-run
   ```
   · 첫 명령 → `.makeedu-tmp\withdrawn.json` 저장(행 수·headers 출력)
   · 둘째 명령 → `✅ 정상` 이면 접속 OK(알림 안 보냄)
   · ⚠️ `withdrawn.json`이 없으면 수납 삭제 판정의 **5번째 가드가 꺼진 채** 돈다(동기화는 정상).
     정기 실행은 `sync-all.cjs`가 알아서 같이 긁으므로, 위 명령은 첫 확인용이다.
3. 퇴원일 대조(**먼저 dry-run**):
   ```
   node --env-file=C:\eywa-sync-pc\.env.local scripts\_makeedu\compare-withdrawal-dates.mjs
   ```
   · ① 채우기 대상 · ② 기존 날짜와 불일치 · ③ 미매칭 이 각각 몇 건인지 보고만 한다.
   · 결과를 확인한 뒤에만 `--apply` (실행 시 **undo JSON**을 같은 폴더에 남긴다).

## 스케줄 등록 — `동기화PC-지정.bat` 한 번이면 끝 (2026-07-30 갱신)

접속 헬스체크는 **별도로 등록하지 않는다.** 기존 지정 스크립트가 세 작업을 **한 세트로** 등록한다:

```
C:\eywa-sync-pc\scripts\_makeedu\동기화PC-지정.bat        (더블클릭)
```

| 작업 | 주기 | 하는 일 |
|---|---|---|
| `eywa-makeedu-sync` | 매일 06시·18시 | 스크랩 + 임포트(학생·반·예비원생·수납) |
| `eywa-makeedu-sync-watcher` | 로그온 상주 + 10분 부활 | 웹의 '지금 동기화'·역동기화 요청 처리 |
| **`eywa-makeedu-health`** | **매일 08:30** | **접속 점검 → 실패하면 원장 벨 알림** |

- 이미 지정된 PC에서 다시 실행해도 안전하다(멱등 `-Force` 재등록). **헬스체크만 추가된다.**
- 상태 확인 = `동기화PC-상태확인.bat`(세 작업 + 접속 점검 마지막 결과 한 줄).
- 로그 = `.makeedu-tmp\health-check.log`(하루 한 줄, 2,000줄 넘으면 최근 1,000줄만 남김).

🔴 **`schtasks`로 따로 등록하지 말 것.** 지정 해제(`동기화PC-해제.bat`)가 그 작업을 못 지워서, 동기화 PC를
옮긴 뒤에도 **옛 PC가 계속 makeedu 로그인을 시도**한다(이중 로그인 = 계정 잠금 위험).

🔴 **첫 실패도 즉시 알린다** — 다른 Phase 3 이벤트의 "콜드스타트 무발송 시드"를 여기엔 **적용하지 않는다**(2026-07-30 수정).
그 규칙은 결석 마일스톤처럼 **이미 쌓인 과거 상태 수백 건**이 한꺼번에 울리는 걸 막는 장치인데, 이 점검은 주체가
`makeedu` 하나뿐이라 막을 폭탄이 없고, 시드를 두면 **정작 첫 로그인 실패가 통째로 침묵한다.**
⚠️ 알림은 **원장(master)** 에게만 가고, 컴퓨터 알림 + 화면 중앙 팝업까지 뜬다(벨 배지만으론 지나친다).

## 주의

- `compare-withdrawal-dates.mjs`는 **날짜만** 고친다. `status`·퇴원 사유는 건드리지 않는다.
- 매칭 우선순위 = **원생번호 → 전화 → 이름**(양쪽 모두 유일할 때만). 형제가 같은 번호를 쓰면 그 번호는 **버린다**(뒤바꾸면 최악).
- `withdrawn.json`에는 **보호자·원생 전화번호와 퇴원 사유**가 들어 있다(실 PII). `.makeedu-tmp`는 gitignore 대상이며, 외부로 보내지 말 것. **AI 프롬프트에 넣지 말 것.**
  (수납 임포터는 이 파일에서 **원생번호만** 읽는다 — 나머지 열은 건드리지 않는다.)
- 적용 후 첫 정기 실행 로그에서 두 줄을 확인할 것:
  · `퇴원 목록: N명 — 삭제 판정 5번째 가드 ON`
  · `── 월별 대조 …` 표가 **전부 ✅** 인지. 🔴가 있으면 그 달 금액이 makeedu와 다르다는 뜻이다.
- 스크랩 목록이 하나 늘어 실행이 조금 길어진다(현재 53~76초). `sync-all.cjs`의 자식 timeout은 8분이라 여유는 충분하다.
