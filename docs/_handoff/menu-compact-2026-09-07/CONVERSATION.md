# 메뉴 컴팩트화 대화 기록

날짜: 2026-09-07. 아래는 대화의 모든 사용자 업무 요청 원문과, 각 요청에 대한 실질적인 답변·시안 변경을 순서대로 보존한 기록이다. 반복적인 도구 출력과 진행 상태 알림은 원시 로그 대신 그 결과·판단에 포함했다. 사용자 지시와 에이전트의 제안을 구분했다.

## 1. 최초 요청 — 좌측과 내부 메뉴 전체 검토

사용자 첨부: [기존 좌측 메뉴](./reference-sidebar.png).

사용자 원문:

> [Image #1] 좌측 탭 및 내부탭 메뉴 전체 확인해보고 대규모로 컴팩트화 시킬 방법 모색

응답·진행:

- 전체 메뉴와 각 화면의 내부 탭을 코드에서 조사하겠다고 설명하고 frontend-design 스킬을 적용했다.
- `NAV_GROUPS`뿐 아니라 화면별 FaceTabs, 별도 보기 토글, 상세 탭, 숨김·역할 조건부 메뉴를 확인했다.
- 현재 사이드바는 화면 내부 탭을 왼쪽에 반복하는 부분이 있으며, 특히 수납·학원 설정이 길어진다고 보고했다.
- 별도 권한과 창을 사용하는 강사 시트·등록상담 등을 단순히 하나의 권한으로 합칠 수 없다고 판단했다.
- 내부 탭 수를 구체적으로 보고했다: 설정 11, 학생 상세 9, 수납 최대 8, 보고서 최대 8, 계산기 내부 5.
- 교재 단가표가 계산기·교재 양쪽에 있다는 중복도 확인했다.

검토한 세 가지 대안:

1. 행 높이 36→32px, 간격 4→2px 정도의 밀도 조정. 원래 긴 구조는 남음.
2. 업무군 8개 + 자주 쓰는 즐겨찾기 4개 + 지원 2개. 당시 초안은 업무군을 누르면 옆으로 메뉴 목록을 여는 플라이아웃.
3. 모든 기능을 약 6개 큰 업무 화면으로 통합. 가장 큰 구조 변경이지만 여러 창·권한·상태·조회 경계의 변경 비용이 큼.

2번을 추천하고 23개 기존 메뉴 전체 대응표와 내부 탭 정리안을 작성했다. 상시 노출 위치가 23→14개로 줄어도 기능을 삭제하는 것이 아니라고 구분했다. 메뉴 높이 약 1,050→460px의 계산은 설계 추정이며 실제 운영 화면 실측이 아니라고 명시했다.

추가로 확인해 보고한 연결:

- 내부 탭은 현재 전체 검색에서 직접 검색되지 않음.
- 수학 시트는 관리자 모바일 부모 메뉴 목록에 독립 진입 항목이 없음.
- 셔틀 내부 탭은 왼쪽 하부탭 정의에서 파생하므로 배열을 삭제하면 화면 탭까지 사라짐.

## 3. 사용자 — 왼쪽은 긍정, 본문 버튼으로 진입하자는 제안

사용자 첨부: [버튼형 진입 참고 이미지](./reference-menu-buttons.png).

이미지는 업무스케줄 / 입학상담카드 / 수학시간표 / 에이와시스템 / 연간일정 / 영어시간표의 6개 큰 버튼으로 구성돼 있다. 3열×2행, 파스텔 바탕과 둥근 모서리, 아이콘 받침이 있는 형태다. 이 문구 6개로 현재 앱 메뉴를 갈아 끼우라는 지시는 아니었다. **진입 방식의 참고**로 사용했다.

사용자 원문:

> 왼쪽 탭은 좋아. 왼쪽 탭을 눌렀을때, [Image #1] 이런식으로 버튼 눌러서 메뉴로 진입하도록 하는건 어때

응답의 판단:

> 좋습니다. 왼쪽에서 업무군을 고르면 본문에 해당 메뉴 버튼이 나타나고, 버튼을 눌러 화면에 진입하는 방식이 잘 맞습니다. 첨부처럼 색과 아이콘으로 구분하되 버튼 크기는 조금 줄이고, 자주 쓰는 메뉴는 즐겨찾기에서 바로 열 수 있게 시안을 바꾸겠습니다.

작업 중 덧붙인 설명:

- 작은 펼침 목록보다 메뉴 이름과 용도를 본문에서 한눈에 보기 쉽다.
- 왼쪽 구성은 유지하고 수업·상담·운영 등을 누르면 본문 메뉴 버튼이 나오게 한다.
- 화면 진입 뒤에는 작은 내부 탭을 사용하고, ‘메뉴로 돌아가기’를 둔다.

실제 변경:

- 추천 모드의 플라이아웃 진입을 본문 버튼형 메뉴로 교체했다.
- 기본 진입 시 수업 업무군 버튼 8개를 보이게 했다.
- 영어·수학 시트는 별도 버튼으로 한 번에 선택 가능하게 했다.
- 수납관리와 설정도 본문 버튼형 입구를 제공했다.
- 운영실·캘린더와 즐겨찾기는 단일 목적지 직접 진입으로 두었다.
- 각 화면에서 해당 업무군 메뉴로 돌아오는 동작을 추가했다.
- 처음에는 이미지에 가까운 파스텔 버튼을 만들던 중 다음 사용자 메시지가 도착했다.

## 4. 사용자 — 파스텔은 필수 아님, 디자인 위임

사용자 원문:

> 꼭 버튼은 파스텔일 필요는 없음. 디자인은 맡길게

응답:

> 색은 기존 학원 UI에 맞춰 흰색 버튼, 얇은 테두리, 네이비 아이콘으로 정리하겠습니다. 메뉴명과 짧은 설명이 먼저 읽히도록 하고, 버튼형 진입 방식은 그대로 살리겠습니다.

실제 변경:

- 파스텔 그라데이션·이모지를 최종 요구로 취급하지 않았다.
- 흰색 버튼, #dce3ec 계열 얇은 테두리, 12px 모서리, 네이비 기능 아이콘으로 변경했다.
- 기존 `src/components/icons/eywa-icons.tsx`의 EyIcon을 정적 SVG로 렌더해 사용했다. SVG 23종을 HTML에 내장했다.
- 넓은 PC에서 버튼은 3열·약 108px 높이, 모바일은 2열로 맞췄다.
- 모든 메뉴명이 크게 읽히고 아래에 한 줄 기능 설명이 붙도록 했다.
- 실제 값이나 사용 빈도를 지어내지 않았다. 권한 조건이 있는 화면은 모형의 한계로 명시했다.
- 업무군별 카드 수, 개별 화면 진입, 돌아가기, 검색, 직접 즐겨찾기, PC/모바일 넘침, JS 오류를 확인했다.
- Orca 미리보기를 최신 버전으로 reload했다.

사용자에게 전달한 답변:

> 수정한 HTML 시안 보기
>
> 흰색 버튼·네이비 아이콘으로 정리했습니다.
>
> - 왼쪽 업무군 클릭 → 본문 메뉴 버튼 → 화면 진입
> - 즐겨찾기는 바로 진입
> - PC 3열·모바일 2열
>

이후 사용자가 바로 다음 질문에서 **“버튼 시안 아주 좋고”**라고 말했다. 따라서 긍정의 대상은 이 최신 흰색·네이비 버튼형 버전이다.

## 5. 사용자 — iframe과 창모드 유지 가치 질문

사용자 원문:

> 버튼 시안 아주 좋고, 구조적으로 버튼 시안으로 갔을때, ifram을 지금처럼 유지하는게 더 좋아 보여 ? 어떄? 창모드가 계속 진행하는게 장점이 있을까?

먼저 밝힌 판단:

> 여러 화면을 함께 쓰는 기능은 남길 가치가 있고, iframe을 계속 사용할지는 따로 판단하는 게 맞습니다.

현재 창·캐시·레이아웃 코드를 읽고 MDN iframe 문서를 확인한 뒤 다음 답변을 전달했다. 아래는 그 실질적인 최종 답변 전체다.

> **이번 개편에서는 iframe을 유지하고, 기본 사용 방식은 ‘큰 작업 화면 하나 + 필요할 때 나란히 보기’로 바꾸는 쪽을 추천합니다.**
>
> 버튼형 메뉴는 어디로 들어갈지 고르는 방식이고, 창모드는 들어간 화면들을 어떻게 함께 사용할지의 문제라 잘 결합할 수 있습니다.
>
> 학원 업무에서는 창모드를 남길 만한 이유가 있습니다.

| 업무 상황 | 여러 화면을 유지하는 이점 |
|---|---|
| 시간표 ↔ 강사 시트 | 수업 배치를 보면서 시트 확인 |
| 학생 정보 ↔ 상담 작성 | 학생 기록을 참고하면서 상담 입력 |
| 출석부 ↔ 수납관리 | 출결·회차를 대조하면서 확인 |
| 서로 다른 학생·반 비교 | 같은 메뉴를 두 개 열어 비교 |

> 현재 코드도 최소화할 때 화면을 없애지 않고 숨겨서, 스크롤과 작성 중인 상태를 유지하도록 만들어져 있습니다. 이 장점은 살리는 게 좋습니다.
>
> 다만 작은 창을 계속 띄워 사용자가 위치와 크기를 정리하게 만드는 방식은 컴팩트화 목표와 맞지 않습니다. 저는 다음 동선을 권합니다.

1. 왼쪽 업무군 클릭 → 본문에 메뉴 버튼 표시.
2. 메뉴 버튼 클릭 → 작업 영역을 넓게 채워 화면 열기.
3. 다른 메뉴로 이동 → 기존 작업은 유지하고, 열린 작업 목록에서 다시 선택.
4. 비교가 필요할 때 → ‘나란히 보기’로 두 화면 배치.
5. 자유로운 창 이동·크기 조절은 추가 기능으로 유지.

> 이렇게 하면 평소에는 단순한 웹앱처럼 쓰면서, 필요한 순간에는 창모드의 이점을 얻습니다. 메뉴로 돌아와도 작업 중인 화면을 닫지 않는 것이 핵심입니다.
>
> **iframe 자체는 장기적으로 유지 여부를 다시 판단할 대상입니다.** 기존 페이지를 독립된 화면으로 재사용하기에는 유리하지만, 프레임마다 별도의 문서 실행 환경이 생겨 메모리·실행 비용이 추가되고 화면 간 갱신도 연결해야 합니다.
>
> 이번에는 버튼 메뉴와 작업 전환 방식을 먼저 개선하고, 이후 실제 사용에서 느린 화면과 동시 작업 수를 측정해 iframe 교체 범위를 정하는 것이 좋겠습니다. 여러 화면을 유지하는 기능은 iframe 없이도 구현할 수 있으므로, 두 결정을 한 번에 묶을 필요는 없습니다.

근거 링크:

- `src/components/workspace/floating-window.tsx:111` — 최소화 시 숨김으로 상태 보존.
- [MDN iframe 설명](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe) — 독립 문서 환경과 자원 비용.

이 질문에 대해서는 파일을 더 수정하거나 실제 창모드를 변경하지 않았다. 자세한 코드 관찰과 오래된 성능 문서의 한계는 HANDOFF §6에 보완했다. **사용자는 이 답변 뒤에 iframe 유지·전면 교체를 확정하지 않고 인수인계를 요청했다.**

## 7. 사용자 최종 결정 — 버튼형으로 진행

> 버튼형으로 갈꺼니까 그렇게 넘겨

응답:

> 버튼형 메뉴 진입을 확정된 구현 방향으로 명시해서 넘기겠습니다. iframe·창모드는 별도의 검토 의견으로 남기겠습니다.

이 메시지는 버튼형을 단순히 ‘좋아한 후보안’으로 전달하지 말고 **실행 방향으로 확정해서 인수인계**하라는 지시다. 따라서 수신 세션은 왼쪽 업무군 → 본문 메뉴 버튼 → 작업 화면의 구조로 진행한다. 이 결정이 iframe 영구 유지·전면 제거 또는 내부 탭 세부안 전부의 일괄 확정까지 의미하지는 않는다.
