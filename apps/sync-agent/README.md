# AYWA 연동 앱

Windows x64용 통합 연동 앱. 클래스노트의 보고서·공지·회수·학부모 연락·답글·공감·명단·읽음 처리와 Google Drive 영상 보관, 메이크에듀의 기존 동기화·상담 전송·접속 점검을 기존 실행기로 처리한다. 일반 사용자는 최초 설치 한 번 이후 ZIP을 풀 필요가 없다.

현재 버전은 **1.0.0 / sequence 1**이다. 설치 파일과 가상 검증은 준비되어 있으며, 운영 DB 반영·웹 배포·파일 게시·실제 연동 PC 전환은 별도다. 자세한 근거와 한계는 [검증 보고서](../../docs/_audit/sync-agent-acceptance-2026-10-08.md)를 따른다.

## 운영자 사용

1. 웹 `학원 설정 → 연동 → 연동 PC`에서 설치 파일을 받고 12자리 연결 코드를 발급한다. 연결 코드는 15분 동안 한 번 사용할 수 있다.
2. 설치한 `AYWA 연동`을 열어 코드를 입력하고 화면의 지점 이름을 확인한다. 앱만 설치하거나 지점만 연결해서는 업무가 시작되지 않는다.
3. 기존 워커가 현재 작업을 마치고 종료하면 **기존 설정·기록 가져오기**로 기존 `.env.local`이 있는 폴더를 선택한다. 지점이 다른 설정은 거부한다. 기존 폴더는 보존하고, 새 폴더에 이미 있는 처리 기록은 덮어쓰지 않는다.
4. 계정을 확인하고 **이 PC에서 연동 시작**을 누른다. 알려진 기존 예약 작업을 끄고, 남은 구 실행과 서버의 최근 활동이 없는지 확인한다. 이전 활동이 감지되면 3분 뒤 다시 확인한다.
5. 웹과 PC 양쪽에서 켜 둔 연동만 실행된다. 실제 발송·자동 동기화·답글 모드 등의 기존 업무 설정도 계속 적용된다. 메이크에듀의 정기 동기화는 06:00/18:00, 접속 점검은 08:30 KST다.

PC 설정은 웹에서 발급한 별도 12자리 **관리 코드**로 10분 동안 연다. Windows 로그인 시 실행, 트레이 시작, 전체/연동별 일시 중지, 자동 업데이트와 적용 시간대를 설정한다. 창 닫기는 트레이 유지이며 **작업을 마치고 종료**가 실제 종료다.

Google 계정과 영상 저장 폴더는 기존 웹의 `숙제영상 드라이브`에서 관리한다. 기존 PC의 Google 환경 설정은 가져오기에서 허용된 항목만 이전한다. gcloud 인증을 쓰는 PC는 같은 Windows 사용자와 설치된 gcloud가 필요하다. 과거 Drive 영상을 옮기거나 폴더를 바꾸지 않는다.

PC 교체는 웹에서 현재 PC 연결 해제 → 실행 만료 확인 → 새 코드 발급 순서다. 복사 설치나 같은 PC 중복 실행도 동시에 업무를 맡을 수 없다. 새 기기에 다른 지점의 계정·작업 기록을 자동으로 넘기지 않는다.

## 실행·저장·업데이트

- 안정된 진입점 `AywaSync.exe`가 `AywaSyncRuntime.exe`를 실행한다. 각 업무 프로세스와 브라우저·영상 도구는 Windows Job Object 안에서 실행된다.
- `%LOCALAPPDATA%\AYWA\Sync`에 연결·설정·기기별 로그·지점별 작업 상태를 둔다. 계정/기기 비밀은 Windows DPAPI로 암호화한다. 재설치·업데이트가 지점 상태를 초기화하지 않는다.
- 서버 실행 임대는 90초이고 20초마다 갱신한다. PC는 단조 시계와 10초 여유를 사용한다. 갱신 실패·절전·임대 소실은 프로세스 트리 종료로 이어진다. 정상 중지·업데이트는 작업 사이에서 멈추고 진행 영상·첨부 복구를 기다린다.
- 새 정식 버전은 6시간 간격으로 확인한다. 다운로드는 작업 중에도 가능하며 적용은 유휴 시점과 지정 시간에만 한다. RSA 서명, 버전 순번, 만료일, 전체 ZIP과 각 파일의 SHA-256, 파일 경로를 검증한다.
- 새 버전 시작은 최대 180초 동안 확인한다. 실패하면 이전 버전으로 되돌리고 실패한 순번을 격리한다. 롤백은 처리한 업무 데이터를 되돌리지 않는다.
- 웹에는 지점에 귀속된 구조화 로그를 보낸다. 학생 이름·연락처·글 본문·비밀번호·원시 stdout은 보내지 않는다. 웹 로그는 30일, 로컬 전송 대기열은 최대 1,000건이다. 기존 업무 로그의 보관 설정은 가져온 값을 유지한다.
- 새 EXE에 DB 접속 비밀번호, 서비스 키, 공용 내부 인증키를 넣지 않는다. 정확히 등록된 SQL 템플릿과 이름 있는 서버 처리만 허용하며 DB 역할의 RLS가 지점 경계를 강제한다.

정상 완료를 기다리는 중에 OS가 종료되거나 전원이 끊길 수 있다. 이 경우 기존 업무의 큐·잠금·외부 중복 대조·영상 재개 상태로 복구한다. 이미 외부 서비스가 접수한 요청을 되돌렸다고 표시하지 않는다.

## 빌드

Windows x64, Node/npm, .NET Framework C# 컴파일러가 필요하다. 루트 저장소 의존성과 이 디렉터리의 의존성을 먼저 설치한다.

```powershell
cd F:\eywa\apps\sync-agent
npm ci
# FFmpeg의 ffmpeg.exe와 ffprobe.exe가 들어 있는 디렉터리
$env:EYWA_AGENT_FFMPEG_DIR = 'C:\tools\ffmpeg\bin'
$env:EYWA_AGENT_SEQUENCE = '1'
npm run prepare:runtime
npm test
npm run package
node test/package-audit.cjs
node test/ui-smoke.cjs --packaged
node test/bundled-runtime.cjs
```

`prepare:runtime`은 기존 실행기에서 125개 소스를 추적해 복사하고, 직접 DB 클라이언트를 서버 어댑터로 바꾸며, 고정 버전 의존성·Chromium·FFmpeg와 네이티브 실행기를 준비한다. 새 소스를 추가하면 SQL 카탈로그와 필요한 RLS 표 목록도 검토한다. `after-pack.cjs`는 패키저가 생략하는 중첩 의존성을 명시적으로 포함한다.

서명 개인키 기본 위치는 `%LOCALAPPDATA%\AYWA\ReleaseKeys\sync-agent-private.pem`이다. **저장소나 배포 묶음에 넣지 말고 별도로 백업한다.** 다른 빌드 PC에서는 `EYWA_AGENT_SIGNING_KEY_FILE`로 같은 키를 지정한다. 키를 새로 생성하면 이미 설치된 앱은 새 서명을 신뢰하지 않는다.

다음 버전은 `package.json` 버전과 `EYWA_AGENT_SEQUENCE`를 모두 높인다. 같은 순번의 게시 파일을 교체하지 않는다. 현재 설치기는 Windows Authenticode 인증서로 서명되지 않았다. 자체 RSA 업데이트 서명과 Windows 게시자 서명은 별개다.

## 서버 반영과 최초 게시

다음은 아직 실행하지 않은 운영 전환 절차다. 자동으로 기존 PC를 교체하는 명령은 제공하지 않는다.

1. 기존 DB 백업/배포 절차로 다음 마이그레이션을 순서대로 반영한다: `20261008073000`, `20261008100000`, `20261008101000`, `20261008102000`, `20261008103000`. 새로운 제어 표와 역할 정책이며 현재 시간표·학생·수납을 이관하거나 초기화하는 SQL은 없다.
2. 웹/API를 배포한다. 서버 `DATABASE_URL`의 역할은 새 `eywa_sync_agent` 역할로 전환할 수 있어야 한다. `SYNC_AGENT_CODE_SECRET`은 서버에만 두는 안정된 난수 비밀이다. 미설정 시 기존 서버 서비스 키를 사용하므로 가능하면 별도 비밀을 지정한다.
3. 변경 불가능한 HTTPS 파일 경로를 정하고 아래와 같이 배포 묶음을 만든다. 현재 준비한 경로는 서비스 저장소의 `sync-agent-releases/1/`이며 **게시된 경로가 아니다**. 실제 업로드 위치가 다르면 새 공개 전에 URL과 서명을 다시 만든다.

```powershell
$env:EYWA_AGENT_RELEASE_BASE_URL = 'https://YOUR-STORAGE-HOST/path/1/'
node release.cjs
node register-release.cjs
```

4. 생성된 `dist/release/1/AywaSync-Setup-1.0.0.exe`, `AywaSync-1.0.0.zip`, `release.json`, `checksums.json`을 해당 HTTPS 경로에 게시한다. EXE/ZIP은 리다이렉트 없이 200 응답이어야 한다. 대용량 파일을 지원하는 저장소 용량 제한을 먼저 확인한다.
5. `node register-release.cjs --verify-remote`로 게시된 EXE와 ZIP 전체 해시를 확인한다. 서버 접속 환경에서 `node --env-file=../../.env.local register-release.cjs --apply`를 실행하면 같은 검증 후 정식 릴리스 행을 등록한다. 기본 실행은 로컬 검증뿐이며, `--apply`는 업로드나 마이그레이션을 하지 않는다. 등록 후 웹 다운로드와 자동 업데이트 조회에 나타난다.
6. 최초 실제 연동 PC에서 설정/기록을 가져오고 구 워커 종료를 확인한 뒤 전환한다. 실제 외부 계정·IP 허용·Drive 권한·재시작을 확인한다. 이전 PC의 오래된 예약 작업과 공유 DB 자격증명 사용처를 정리한 후 구 설치를 제거한다.

구형 워커는 새 프로토콜을 모르므로 서버의 기기 등록만으로 과거에 배포한 DB 비밀번호를 무효화할 수 없다. 기존 파일과 공유 자격증명을 그대로 둔 채 “어떤 구 PC도 다시 실행할 수 없다”고 보장하지 않는다.

## 검사

- `npm test`: 임대 경쟁·만료, 브로커 인증, Windows 자식 프로세스 종료, 서명/압축 파일 검증, 실제 부트스트랩 복구, 기존 설정 이관.
- `node test/controller-smoke.cjs`: 가짜 서버를 사용한 실제 Electron 등록·암호화·중복 실행·연결 해제. 외부 업무는 시작하지 않는다.
- `node ../../scripts/_sync-agent/control-db-check.cjs`: 명시적으로 라벨이 붙은 로컬 PostgreSQL 시험 컨테이너에서 실제 서버 함수/SQL 검증. 운영 DB를 사용하지 않는다.
- 루트에서 `node scripts/_sync-agent/dryrun.cjs`: 환경변수 제거 및 Node 외부 통신 차단 후 기존 업무 회귀 검사. 전체 저장소 검사나 실제 외부 계정 인수 시험과는 범위가 다르다.

수동 복구·초기 데이터 정리 스크립트는 기존 저장소에 보존되어 있다. 이를 설치 시 자동 실행하거나 PC에서 임의 스크립트를 실행하는 기능은 제공하지 않는다.
