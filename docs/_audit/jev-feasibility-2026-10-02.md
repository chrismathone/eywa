# Jev 적용 검토 — 출결 정정 스트레스 시험과 앱 전체 활용처

2026-10-02 · 기준 코드 `9b26c762c` · 모델 `jev-1.13.0`

## 판단

**학부모 연락의 업무 분류와 출결 상태 판별은 Jev로 옮길 가능성이 높다. 기존 DeepSeek 호출을 그대로 치환하는 것만으로 완성되지는 않는다.** 학생·과목·날짜를 코드가 먼저 특정하고, 정정 이력을 함께 보내며, 확신이 낮거나 정보가 없는 건 원문을 사람이 확인하는 경로가 필요하다. 이 구조에서는 DeepSeek 없이도 운영 가능한 설계를 만들 수 있다.

**요약·번역·멘트 작성의 완전 대체는 어렵다.** Jev는 주어진 선택지·점수·참/거짓 확률을 돌려준다. 이런 기능에서는 중요한 자료 선택, 위험 신호 분류, 초안의 근거 점검, 정형 템플릿 선택을 맡기는 것이 현실적이다. 자유 문장 생성과 이미지·음성 인식은 별도 모델의 역할이다. [공식 소개](https://docs.typesafe.ai/introduction), [모델 입력 사양](https://docs.typesafe.ai/models)

현재 추천 순서는 **① 클래스노트 분류/정정 → ② 상담 메모의 이탈 신호·고객센터 분류 → ③ 생성 문장의 근거 점검 → ④ 긴 전사의 관련 구간 선별**이다. 뒤 세 가지의 효과는 코드 구조를 보고 제안한 것이며 이번 API 시험으로 그 업무의 정확도나 속도 향상까지 검증한 것은 아니다.

## API 실험: 200건 + 처음 보는 50건

핵심 스트레스 시험은 **서로 다른 입력 사례 250개**다. 처음 200개는 104개의 수작업 사례와, 2차·3차 상태 변경을 조합한 96개 사례로 구성했다. 뒤 50개는 질문을 개선한 뒤 따로 작성한 새 사례다. 이름·과목·날짜가 다르면 같은 문장도 다른 입력/정답이 될 수 있다.

정답은 호출 전에 파일로 저장하고 SHA-256을 남겼다. 같은 요청에서 한국어/영어 판정문을 독립 질문으로 보냈다. 두 판정문은 표현과 세부 지시도 조금 달라서 **언어 자체의 우열을 분리해서 증명하는 실험은 아니다.** 한국어 원문을 영어로 번역해서 넣은 것도 아니다.

| 시험 | 한국어 질문 | 영어 질문 | API 왕복 중앙값 / p95 |
|---|---:|---:|---:|
| 최초 200개 | 187/200, 93.5% | 188/200, 94.0% | 206 / 272ms |
| 대상 학생·과목·날짜를 질문에 직접 적은 재시험, 같은 200개 | 195/200, 97.5% | 195/200, 97.5% | 202 / 281ms |
| 개선한 질문을 고정하고 새 50개 시험 | 47/50, 94.0% | 48/50, 96.0% | 208 / 285ms |

재시험의 97.5%는 개발 자료에 맞춰 개선한 결과다. 새 50개 결과와 구분해야 한다. 모두 사람이 만든 합성 자료이고 라벨도 이 실험에서 정했으므로, 운영 댓글 전체의 정확도 추정이나 독립적인 사람 평가로 볼 수 없다. 중앙값/p95는 이 PC에서 동시 요청 4개로 측정한 API 왕복이며 앱 전체 지연이 아니다.

### 2차·3차 꼬임

한 문장 안의 변경 48개, 여러 댓글로 나뉜 변경 48개를 시험했다. 최초·개선 시험 모두 두 질문에서 **96/96 정답**이었다. 대표 사례:

| 입력 | 정답 | 관측 |
|---|---|---|
| 결석해요 | 결석 | 정답 |
| 결석한다고 말했는데 지각할 것 같아요 | 지각 | 정답 |
| 지각할 것 같다고 했는데 결석해요 | 결석 | 정답 |
| 결석 → 지각 → 정상 출석 | 정상 출석 | 정답 |
| 결석 → 지각 → 조퇴 | 조퇴 | 정답 |
| 결석 → 지각 후 “방금 변경도 취소, 맨 처음대로” | 결석 | 정답 |
| 네 번째 결석은 오발송, 세 번째 정상 출석이 최종 | 정상 출석 | 새 사례에서도 정답 |

이 96개는 명시적으로 정정하는 체계적 조합이라 정형성이 있다. “수정했습니다/최종입니다”가 없는 실제 대화, 생략된 이름·날짜, 오타가 섞일 때도 같은 성능이라고 일반화하면 안 된다.

### 실제로 틀린 것

| 사례 | 기대 | 관측/의미 |
|---|---|---|
| “쌤 오늘 몬가여ㅠㅠ” | 결석 | 개선 한국어 질문도 `none`, confidence 0.95. 높은 확신만으로 누락을 막지 못함 |
| “민준이가 결석한다고 했는데 그건 서연이 얘기였어요. 민준이는 지각” — 서연 대상 | 결석 | 개선 영어 질문 `none`, 0.82. 정정의 대상 인물 전환에 약함 |
| “제가 전할 말은 따옴표 안입니다: ‘민준이는 오늘 결석합니다’” | 결석 | 개선 영어 질문 `none`, 0.87. 진짜 전달문까지 단순 인용으로 제외 |
| “학교 수업에는 지각했어요. 학원 출결 연락은 아닙니다” | 해당 없음 | 개선 질문에서 지각 오탐. 기관 구분이 필요 |
| “2~5일 결석, 3일만 정상” — 3일 대상 | 정상 | 최초 두 질문 모두 결석. 질문에 대상 날짜를 직접 적은 뒤에는 정답 |
| “민준이 오늘 결석을 서연이 내일 결석으로 정정” — 서연·내일 대상 | 결석 | 새 50개에서도 `none`: 영어 0.77, 한국어 0.88 |
| “결석 취소→지각 취소→제시간에 가지만 중간에 먼저 와야 함” | 조퇴 | 새 사례에서 한국어는 정상, 영어는 조퇴 |

**단순 변경 횟수보다 ‘누구의 어느 수업, 어느 날짜에 대한 변경인가’가 더 어려웠다.** 따라서 메시지 전체를 한 번에 대표 분류하는 방식보다 `(학생, 과목/수업, 날짜)`별 질문으로 나눠야 한다. 여러 질문은 한 요청에 묶을 수 있지만 답변끼리 의존하지 않으므로 결과 결합은 코드가 해야 한다. [질문 구조](https://docs.typesafe.ai/primitives)

### confidence를 쓰면 얼마나 남는가

- 개선 영어 질문의 confidence ≥ 0.9: 개발 200개 중 177개 통과, 관측 오답 0. 새 50개 중 39개 통과, 관측 오답 0.
- 새 자료에서는 **11/50, 22%를 보류**해야 위 결과가 됨. 전부 자동 처리한 결과가 아님.
- 한국어 질문은 개발 자료에서 confidence 0.95인 오답이 남음.
- 0.9는 이 실험에서 검토한 후보 임계값이다. confidence가 0.9라고 실제 정답률이 90%라는 뜻도, 표본에서 오답 0이라고 앞으로 무오류라는 뜻도 아니다. 공식 문서도 확률 분포에서 파생되는 지표로 설명하고 업무별 검증을 요구한다. [Confidence](https://docs.typesafe.ai/confidence)

특히 **낮은 확신의 `none`을 “알림 없음”으로 버리지 말아야 한다.** 확인 대기함으로 보낸다. 출결은 미탐과 오탐의 비용이 다르므로, 결석/정상/무관 각각 별도로 평가해야 한다.

## 날짜 추출과 업무 분류의 별도 시험

### Jev + 코드만으로 날짜 만들기

별도 24개 예문에서 코드가 날짜 표현 후보를 찾고, Jev가 각 표현이 결석·지각·조퇴 중 무엇을 가리키는지 선택했다. 달력 계산·연말 전환·기간 확장은 코드에서 수행했다. **DeepSeek 호출은 0회**다.

- 출결 종류: 23/24 정답.
- 날짜와 출결의 조합: 22/24 정답.
- 둘 다 정확: 21/24.
- 검토 대상으로 분류한 것: 10/24. 검토 없이 남은 14개에는 이번 표본에서 오답이 없었음.
- 문제: 과목별로 다른 통보, 부정문에서 날짜를 잘못 붙임, `오늘부터 3일`을 아직 처리하지 않는 실험용 파서.

이는 **대체 설계의 작동 가능성**을 본 것이지 완성된 날짜 추출기가 아니다. 파서가 못 읽은 표현도 모델 오류와 함께 실패로 집계했다. `3일 동안`, `다음달 초`, 격주·공휴일·수업 없는 날, 여러 학생·여러 수업 조합은 운영 날짜 모델을 따로 설계해야 한다. Jev에 날짜 덧셈을 맡기지 않고 부분 선택 후 코드로 조립하는 방식은 공식 예제와도 일치한다. [날짜 추출 예제](https://docs.typesafe.ai/cookbooks/date_extraction_cookbook)

### 업무를 여러 개로 분류

출결·셔틀·학습문의·일정·결제·불만·직원 조치 필요를 각각 독립 yes/no 질문으로 시험했다.

| 자료 | 모든 항목 일치 | 개별 판정 일치 |
|---|---:|---:|
| 첫 30개 | 24/30 | 203/210 |
| 경계 정의를 고친 같은 30개 | 29/30 | 209/210 |
| 질문 고정 후 새 20개 | 18/20 | 138/140 |

결석+보강, 결제+학습문의처럼 **한 댓글에 여러 업무를 붙이는 방식**이 적합하다. `action`도 단독 최종 게이트로 쓰면 안 된다. 새 사례에서 지각 통보를 맞히고도 조치 필요를 부정한 경우가 있었다. 출결로 분류된 통보의 처리 필요성은 코드 규칙이 함께 결정해야 한다.

## 현재 클래스노트 배선과 교체 조건

1. [수집 워커](../../scripts/_classnote/classnote-feed-core.mjs)는 학부모 새 글/댓글을 찾음. 새 글은 코드상 1분, 댓글은 10분 주기다.
2. [원문 저장](../../scripts/_classnote/classnote-inbox-store.mjs)이 `classnote_parent_messages`에 저장하고 내부 분류 API를 호출함. 전 보드/과목 원문 저장과 수학 담당 강사 벨은 별도 흐름이다.
3. [현재 분류기](../../src/features/attendance/parent-alerts/server/classify.ts)는 DeepSeek에 최대 12건씩 보내 `absence/late/early_leave/none`, 시작·종료일, 짧은 사유를 받음.
4. 출결 알림은 같은 지점의 `attendance_alert_optin` 활성 계정에 전달됨. 담당 강사의 원문 알림은 기존 워커가 따로 만들기 때문에 다시 보내면 중복될 수 있음.
5. [담당 강사 계산](../../scripts/_classnote/notify-recipients.mjs)은 현재 수강·보드 과목·담임·교시 담당·위임·계정 상태를 검사한다. 이것을 Jev에게 추측시키면 안 됨.

현재 분류기는 각 원문을 개별 처리하고 `normal/correction/unclear` 상태 및 정정 관계를 갖고 있지 않다. **“결석 → 지각 → 정상”을 읽어도 기존 결석 알림의 의미가 자동으로 취소되는 구조가 아니다.** 모델만 바꾸면 이 문제는 남는다.

추천 구현 형태:

```text
새 원문 저장
  → 동일 스레드의 필요한 이전 통보/확정 상태 읽기
  → 코드가 학생·과목·날짜 후보와 허용 담당자를 결정
  → Jev: 대상별 최종 상태 + 업무별 의도 + 애매함
  → 코드 검증: 원문 근거·날짜 유효성·정정 관계·수신 권한
  → 확정 가능한 건 분류 저장 / 나머지는 확인 대기
  → 이벤트별 현재 상태 갱신 + 필요한 수신자에게 정정 표시
```

- 원문은 남기고 `supersedes` 또는 동등한 관계로 새 통보가 무엇을 정정했는지 기록. 이전 통보를 지워서 맞추지 않음.
- 여러 날짜/수업은 이벤트 단위로 나눔. 단일 `starts_on~ends_on`만으로 띄엄띄엄 결석을 표현하지 않음.
- 원문 댓글 ID와 이벤트·수신자 키로 중복 발송을 막고, 새 정정은 기존 통보를 갱신/정정하는 별도 사건으로 처리.
- Jev 장애·정보 부족·보류는 원문 알림/확인 경로로 남김. `none` 확정으로 처리해 유실시키지 않음.
- **DeepSeek 없는 운영안**: Jev + 코드 + 사람 확인. 자연어 사유 요약 대신 원문 인용/검증된 원문 조각을 사용하면 생성 모델이 필수는 아님.
- **자동 처리 범위를 넓히는 운영안**: Jev 고확신 경로 + 어려운 사례만 기존 생성 모델 또는 사람 검토. 이는 선택지이며 모델 전량 교체와 다름.
- Jev의 0.2초는 분류 시간이다. 댓글 감지 10분·큐 대기·DB·알림 전달까지 빨라졌다고 말할 수 없음. 실시간성을 원하면 수집 빈도/대상 글 우선 폴링을 별도로 검토해야 함.

### 넣지 않는 편이 좋은 곳

- 수납 합계·잔액·급여·세금·교시 충돌·시간 계산·페이지네이션·정렬: 코드가 정확하고 더 빠르다.
- 담당 강사, 테넌트, 권한, 학생-학부모 연결, 알림 수신 허용: DB 관계와 정책으로 확정해야 한다.
- 출석부 확정, 셔틀 탑승/미탑승 확정, 환불 실행, 원생 병합: 이번 의미 분류 성능으로 자동 실행 근거를 삼지 않는다.
- 기존에 명시적으로 사람이 확정하도록 정한 신규생 체크와 챗봇 제거 방침: 이번 활용 검토 때문에 자동 판정/챗봇을 다시 만들 필요는 없다.
- 브라우저 렌더링·SQL·파일 업로드가 병목인 화면: 외부 모델 호출은 그 병목을 해결하지 않는다.

## 빠르게 만드는 방법과 비용

1. **생성을 아예 생략할 수 있을 때**: Jev가 정형 템플릿/기존 자료를 고르고 코드가 표시한다. 분류·라우팅·정형 안내에 가장 큰 효과가 기대된다.
2. **생성 입력을 줄일 때**: 긴 원문에서 관련 구간을 선택한다. 최종 생성 지연이 감소할 가능성이 있지만, 그 효과는 별도 A/B가 필요하다.
3. **여러 판단을 한 요청으로 합칠 때**: 출결·결제·보강·조치 필요를 한 번에 평가한다. 다른 질문의 답을 참조하는 질문은 만들지 않고 코드에서 합친다.
4. **동일 원문 재판정을 피할 때**: `(tenant, source ID, content hash, context version, model version, rubric version)`에 결과를 저장한다. 정정·새 문맥이 들어오면 context version이 바뀌므로 과거 캐시를 재사용하지 않는다.
5. **모든 생성 전에 무조건 Jev를 붙이지 않는다**: 불필요한 판정 0.2초도 추가 지연이다. 실제로 생성 생략/입력 축소/재생성 감소가 있는 경로만 적용한다.

공식 공개 가격은 실험일 기준 입력 100만 토큰당 **$0.042**, 출력 무료다. 이 실험의 모든 단계 합계는 **555회 API 호출, 입력 1,534,093토큰, 공개 단가로 약 $0.0644**다. 청구서 실측이 아니라 API usage × 공개 단가 추정이다. [공식 모델/가격](https://docs.typesafe.ai/models)

기존 DeepSeek/Claude를 같은 자료로 재호출하지 않았으므로 “몇 배 빨라졌다/얼마 절감”이라는 실측 비교는 없다. 또한 이번 가격은 지점별 운영 사용량 계측으로 기록한 것이 아니라 별도 실험 결과 파일에 기록했다.

## 통합할 때 필요한 공통 구조

- 앱의 [AI 단일 관문](../../src/lib/ai/generate.ts)에 **typed decision 모드**를 추가하는 방향. Jev를 일반 채팅 provider 폴백 목록에 끼워 넣지 않는다. 자유 JSON 생성 요청과 선택형 판단의 계약이 다르기 때문이다.
- 단일 관문의 tenant 라이선스·기능별 키 그룹·FACT_GUARD·usage 계측·에러 처리 유지. TypeSafe 기능도 레지스트리에 명시한다.
- 서버에서만 호출하고 `TYPESAFE_API_KEY`를 사용한다. 연동 PC·브라우저에 키를 배포할 필요가 없다.
- 버전 `jev-1.13.0`과 판정문 버전을 고정. 별칭의 모델이 바뀌면 기존 임계값을 그대로 신뢰하지 않는다.
- 날짜·금액·횟수는 코드로 계산. `choice`는 후보에 있는 값만, 원문 조각은 실제 원문에서 찾은 것만 허용.
- 새 글 저장/분류 큐 같은 명시 이벤트로 실행. 화면을 열 때마다 새로 판정하지 않는다.
- shadow 단계에서는 기존 업무 처리를 유지하면서 Jev 판정·사람 정답·보류율·오탐/미탐·지연·비용만 비교한다. 실제 댓글로 충분한 기간/사람/과목을 분리한 검증이 다음 필요 작업이다.

이 작업의 결과는 **도입 판단과 재현 가능한 실험**이다. 운영 전환·마이그레이션·자동 알림 발송은 적용하지 않았다.

## 후속 통합 — 수동 비교 전용 (2026-10-02)

초기 조사 이후 `generateJSON({ mode: "decision", state, questions, meta })`를 추가했다. 기존 문장 생성 provider와 폴백은 유지하며, Jev는 선택형 판정 전용으로 호출한다. 지점의 AI 라이선스와 사실 원칙을 확인하고 `ai_usage_logs`에 사용량을 기록한다. 키는 `TYPESAFE_API_KEY_ATTENDANCE`를 우선하고, 없으면 `TYPESAFE_API_KEY`를 사용한다.

수동 비교는 `POST /api/internal/parent-messages/jev-shadow`로 요청한다. `x-eywa-internal` 헤더가 `CLASSNOTE_INTERNAL_SECRET`과 일치해야 하며, `CLASSNOTE_JEV_SHADOW_TENANT_IDS`의 쉼표 구분 목록에 요청 지점이 있어야 한다. 목록이 없으면 비활성 상태다. 요청 본문은 `tenantId`, `messageId`, `course`, 선택적인 `targetDate`이며, 자동 분류 큐에는 연결하지 않았다.

같은 지점·게시글·자녀·학생의 이전 연락만 비교 문맥으로 사용한다. 날짜는 각 연락의 한국 시각을 기준으로 계산하며, 대화가 너무 길거나 순서가 모호하면 수동 검토 오류를 반환한다. 응답의 `canNotify`는 항상 `false`이며 출결 판정 저장·수정이나 알림 발송은 수행하지 않는다.

앱에서 사용하는 판정문과 전송 모듈을 재현하는 스크립트는 [`eval-jev-runtime.mts`](../../scripts/_oneoff/eval-jev-runtime.mts)다. [`250개 합성 입력`](../../scripts/_oneoff/fixtures/jev-attendance-250.json)과 [`달력 경계 20개`](../../scripts/_oneoff/fixtures/jev-attendance-calendar-20.json)를 사용한다. `--run` 없이 실행하면 입력만 준비하며, `--calendar`로 달력 사례를 선택한다. 원격 모델 호출이 필요한 실험은 별도로 명시 실행한다.
