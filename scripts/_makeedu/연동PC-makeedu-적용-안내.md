## 2026-11-06 — makeedu가 사람 확인을 요구할 때: 'makeedu 다시 로그인'

makeedu가 11-04에 로그인 화면에 봇 확인을 붙여, 자동 로그인(Playwright)에 **사람 확인(구글 reCAPTCHA)**을 요구합니다.
그래서 자동 동기화는 **사람이 한 번 로그인한 상태(세션)를 재사용**합니다. 우회(자동화 표시 숨기기·캡차 풀이·자동 클릭)는 하지 않습니다.

**적용**: AYWA 연동 앱(AywaSync) **새 판**이 깔려야 합니다(스크립트가 앱 안에 묶여 있어 웹 배포만으로는 바뀌지 않습니다).

📌 **업데이트 직후 바로 'makeedu 다시 로그인'을 누르면 자동 시도 없이 세션이 생깁니다.** 누르지 않으면 첫 정기 동기화(또는 08:30 점검)가
ID/PW 로그인을 한 번 시도해 사람 확인에 막히고, 자동 로그인 멈춤 + 원장 벨이 온 뒤에 같은 절차를 하게 됩니다.

**언제 하나** — 아래 중 하나가 보이면:
- 원장 벨 "makeedu가 사람 확인을 요구합니다"(또는 "makeedu 로그인 정보가 올바르지 않습니다(남은 시도 N회)" · "makeedu 계정이 미인증 상태입니다" 등 — 아래 '안 됐을 때')
- 웹 연동 이력 "makeedu가 자동 로그인에 사람 확인을 요구합니다 — … 'makeedu 다시 로그인'이 필요합니다"
- 동기화 PC의 AYWA 연동 앱 메이크에듀 칸 "자동 로그인 멈춤 · …"

**절차**(동기화 PC에서, 1~2분):
1. 알림 영역(트레이)의 AYWA 아이콘을 더블클릭해 **AYWA 연동** 앱을 연다.
2. (선택) 비밀번호까지 미리 채우려면 먼저 웹 **연동 PC 탭에서 관리 코드**를 받아 'PC 설정 잠금'에 넣는다(10분). 안 하면 비밀번호는 직접 입력한다.
   단 '비밀번호·계정 확인' 멈춤 중에는 저장된 비밀번호를 **일부러 채우지 않는다**(틀린 것으로 확인된 값을 그대로 누르면 시도 횟수가 준다) — 직접 입력한다.
3. **메이크에듀** 칸의 **makeedu 다시 로그인**을 누른다.
4. makeedu 로그인 창이 열린다(안 보이면 작업 표시줄의 **Chrome for Testing** 창). 아이디가 채워져 있다.
5. (권장) 로그인 버튼 아래 **'로그인상태유지'**를 체크해 본다 — 세션이 길어질 수 있다(앱은 이 칸을 건드리지 않는다 · 사람 선택).
   **로그인** 버튼을 누르고 "사람이 맞습니까?" 확인을 마친 뒤, 다시 로그인 버튼을 누른다. **재인증 화면(loginReCert)**이 나오면 그 창에서 재인증까지 마친다(재인증 화면에서는 아직 저장하지 않는다).
6. 로그인 화면을 벗어나면 앱이 그 창의 로그인 상태를 makeedu 메인 화면으로 한 번 확인하고(주소만 보고 판단하지 않는다), 확인되면 창이 저절로 닫히고 앱에 **"다시 로그인되었습니다 — aywa의 '지금 동기화'로 바로 가져올 수 있습니다"**가 뜬다.
7. 웹 **학원 설정 → 연동 → 지금 동기화**로 바로 가져온다(아니면 다음 정기 동기화 06:00/18:00).

**안 됐을 때**:
- 5분이 넘거나 창을 닫으면 실패 사유가 뜨고 '자동 로그인 멈춤'은 그대로다 → 3번부터 다시.
- **비밀번호 계열** "로그인 정보가 올바르지 않습니다 · 남은 시도 N회" · "인증정보가 올바르지 않습니다" → **더 시도하지 말고** 관리 코드로 설정을 연 뒤 **연동 계정**에서 메이크에듀 비밀번호를 확인해 **다시 저장**한다.
- **계정 계열** "계정이 미인증 상태입니다" · "호출정보가 올바르지 않습니다" · "무료형·실속형(라이트) 사용자로 안내됩니다" · "사용 기한·결제 화면으로 안내됩니다" · "알 수 없는 응답(코드)" → makeedu에서 먼저 해결한 뒤(필요하면 makeedu 고객센터) **연동 계정**에서 메이크에듀 비밀번호를 **한 번 더 저장**한다(같은 값이어도 — 그때 자동 로그인을 다시 시도한다).
  - 이 두 계열은 'makeedu 다시 로그인'이 성공해도 **풀리지 않는다** — 저장된 비밀번호가 틀린 채면 세션이 끊길 때 자동 로그인이 또 틀려 시도 횟수를 쓰기 때문이다. **비밀번호를 저장할 때만** 풀린다(아이디만 바꿔 저장해서는 풀리지 않는다).
  - 그동안에도 'makeedu 다시 로그인'으로 받은 세션은 계속 써서 동기화는 돈다(그 창에서는 비밀번호를 직접 입력). 횟수를 다 쓰면 makeedu 계정이 잠긴다.
- 사람 확인·재인증 멈춤은 'makeedu 다시 로그인'이 성공하면 풀린다(연동 계정을 다시 저장해도 풀리지 않는다 — makeedu가 사람을 요구하는 것이라).
- 메이크에듀 칸에 "⚠️ 멈춤 표시를 예비 파일에 남겼습니다"가 보이면 상태 폴더 쓰기가 막혀 있던 것이다(백신·권한) — 로그 폴더를 확인한다. 멈춤은 그대로 효력이 있다.
- 웹 연동 이력이 "⚠️ 멈춤 표시 저장 실패 — 다음 실행이 같은 자격으로 다시 시도할 수 있음(잠김 위험)"으로 시작하면 멈춤 표시를 본·예비 어디에도 못 남긴 것이다 — 앱에는 안 보일 수 있다. 뒤에 붙은 사유대로 처리하되, 비밀번호 계열이면 **바로** 연동 PC의 상태 폴더 쓰기(백신·권한)부터 확인한다(그대로 두면 다음 정기 실행이 같은 비밀번호로 다시 시도해 남은 횟수를 쓴다).
- "동기화 PC의 (makeedu 자동 로그인) 멈춤 기록을 읽지 못했습니다"는 makeedu가 거절한 것이 아니라 연동 PC의 멈춤 기록 파일 **내용이 깨져** 읽지 못한 것이다 — 안전을 위해 자동 로그인을 멈춰 둔다. **연동 계정**에서 메이크에듀 비밀번호를 한 번 더 저장하면(같은 값이어도) 다시 시도한다.
- "동기화 PC의 makeedu 멈춤 기록 파일을 열 수 없습니다(백신·권한·잠금 등)"는 파일을 **열지 못한** 것이다 — 이때는 비밀번호를 저장해도, 'makeedu 다시 로그인'을 해도 풀리지 않는다(무엇인지 모르는 기록은 지우지 않는다). 동기화 PC를 다시 시작하거나 백신 예외·상태 폴더 권한을 확인한다 — 파일을 다시 읽을 수 있으면 원래 상태(원래 멈춤 사유 또는 멈춤 없음)로 돌아간다.
- 웹 연동 이력이 "makeedu 로그인 상태를 확인하지 못했습니다(… 판정 불가)"면 네트워크·사이트 문제다 — 자동 로그인은 멈추지 않았고 다음 실행에서 다시 확인한다.
- 자동 동기화는 세션이 끊긴 뒤 ID/PW 로그인을 **한 번만** 시도하고, 실패하면 같은 계정으로는 다시 시도하지 않는다(계정 잠김 방지). 그래서 같은 알림이 하루 한 번 울리며 사람을 기다린다.
- 그 사이 들어온 'makeedu로 보내기'(역동기화) 요청은 '실패'로 닫힌다(로그인 시도는 늘지 않는다) — 다시 로그인한 뒤 웹에서 다시 보내거나 다음 주간 자동 전송이 다시 싣는다.

**첫 실사용 확인**(새 판을 깐 뒤 처음 한 번 — 순서대로 보고 결과별로 판단한다):
1. **창**: 'makeedu 다시 로그인' → 로그인 창이 뜬다(안 보이면 작업 표시줄의 Chrome for Testing).
2. **캡차**: 로그인 버튼 → "사람이 맞습니까?" 확인 → 로그인 버튼 다시.
3. **결과**(앱 위쪽 안내):
   - "다시 로그인되었습니다 …" → 정상. 4번으로.
   - "makeedu가 이 창의 로그인을 받지 않습니다(사람 확인을 마친 제출에도 다시 사람 확인을 요구했습니다) — makeedu 문의" → makeedu가 자동화 표시가 있는 창의 로그인을 아예 받지 않는다. 우리 쪽에서 우회하지 않는다 → **makeedu 문의**.
   - "사람 로그인은 됐지만 자동 실행에서 그 세션을 쓸 수 없습니다(makeedu가 브라우저를 바꾼 세션을 막는 것으로 보임) — makeedu 문의" → 사람 창(헤드 있는 창)에서 받은 세션을 정기 실행(headless)이 쓰지 못한다. 우회(UA 위장·headless 끄기)하지 않는다 → **makeedu 문의**.
   - "5분 안에 로그인을 마치지 못해 … (마지막 makeedu 응답: 사람 확인 필요 — 확인 칸을 마친 뒤 …)" → 캡차를 안 풀고 눌렀다. 다시.
4. **makeedu.log**(앱 → 로그 폴더 열기 → 날짜 → `makeedu.log`): 끝의 `AYWA_HUMAN_LOGIN {...}` 줄과 그 위 줄들을 본다.
   - `"ok":true,"code":"OK","headless":"alive"` = 자동 실행도 이 세션을 쓴다(가장 좋은 결과) · `"headless":"unknown"` = 그 확인만 네트워크로 못 했다(다음 정기 실행이 확인).
   - "제출 진단 — 캡차 토큰 있음/없음 · loginBrowserRuntime=automation · makeedu 응답 …" = 누른 제출마다 한 줄(값은 남기지 않는다). 토큰 있음인데 응답 CAPTCHA_REQUIRED면 3번의 '받지 않습니다'와 같은 뜻.
   - "makeedu 로그인 확인 — 도착 화면 /main.do …" = 로그인 확인이 된 화면(경로만).
   - 사람 창의 로그인 확인은 브라우저 탭이 아니라 같은 쿠키로 보내는 main.do 요청이다(첫 실사용에서 이 확인이 실제 makeedu에서도 맞게 도는지 — 위 '도착 화면' 줄이 뜨면 맞다).
5. **지금 동기화**: 웹 학원 설정 → 연동 → 지금 동기화 → 연동 이력이 정상으로 끝나는지.
6. **다음 날**: `makeedu.log`의 `[makeedu-health] makeedu 세션 살아 있음 — 로그인 후 N시간` 줄(08:30 점검)로 세션이 하루를 넘기는지 본다. "세션 끊김 — 로그인 후 N시간"이면 그 사이에 끊긴 것이다('로그인상태유지'를 체크해 다시 해 볼 만하다).

**세션은 하루 1번 확인한다**(원장 결정 — 따로 깨우는 장치 없음): 매일 08:30 접속 점검과 06:00/18:00 정기 동기화가 저장된 세션으로 먼저 들어가 보고,
살아 있으면 그대로 쓰며 갱신한다. 그 사이 세션이 끊기면 다음 실행이 알아채고 위 '안 됐을 때' 흐름(멈춤 표시 · 벨 · 다시 로그인)으로 간다.
08:30 점검은 매번 로그 폴더(`앱 → 로그 폴더 열기` → 날짜 → `makeedu.log`)에 **"makeedu 세션 살아 있음 — 로그인 후 N시간 M분"**(또는 "세션 끊김 — 로그인 후 …")을 한 줄 남긴다.
세션이 끊긴 걸 처음 알면 **"makeedu 세션 수명 — … 세션 저장 후 N시간 M분 · 로그인 후 N시간 M분"**도 한 줄 남는다. 세션이 실제로 얼마나 사는지는 이 기록으로 잰다.

- 잘못된 날짜·숫자가 아닌 금액·확인되지 않은 환불 상태는 추측하지 않고 반영을 중단합니다. 실패 원인은 `invoices.json.error`와 웹 동기화 이력에 전달되며, 못 읽은 항목을 구체적으로 표시합니다.
- Chrome의 테스트 HTML에서 기존 링크 방식 실패를 재현하고 수정 결과를 검증했습니다. 실제 사이트 수집 확인은 이 ZIP을 연동 PC에 덮어쓴 뒤 동기화를 한 번 실행해야 끝납니다.

이번 ZIP도 `scripts/_makeedu` 전체를 포함합니다. 기존 `C:\eywa-sync-pc`에 압축을 풀어 덮어쓰고, `.env.local`은 그대로 둡니다. 다음 수납 동기화부터 새 스크립트를 사용합니다.

- `extract-table.cjs`(신규)와 `scrape.cjs`: 원 수납 바로 아래의 `환불1` 등 상세 행을 해당 수납에 연결합니다. 전체/부분 환불·금액·일자·방법을 `invoices.json`의 `invoiceRefunds`에 기록합니다. 원 청구 행수에는 환불 상세 행을 중복 합산하지 않습니다.
- `import-invoices.cjs`: 항목별 `refunds`를 보존합니다. 원 청구·할인·실납부 합계는 그대로 두며, 웹앱의 배분·급여 기준은 전체환불 시 0원입니다. 부분환불은 기준액 확인 전 자동 배분을 보류합니다.
- 환불 상세를 해석하지 못하면 해당 수납 수집을 중단하고 오류를 남깁니다. 0행으로 반영하거나 환불이 없다고 덮어쓰지 않습니다.
- 개발 PC에서는 합성 DOM·DB 롤백 검증을 통과했습니다. 실제 사이트 확인은 로그인 설정이 있는 연동 PC에서 아래처럼 실행합니다. `--apply`가 없으므로 마지막 명령은 DB를 수정하지 않습니다.

```powershell

node --env-file=.env.local scripts/_makeedu/import-invoices.cjs
```

스크랩/대조가 정상임을 확인한 뒤 웹앱의 `지금 동기화`를 실행합니다. DB에 이미 확인된 환불은 구 워커의 환불 없는 payload만으로 지워지지 않도록 보호됩니다.

## 🔴 이번에 확인된 사실 (설계가 바뀐 근거)

**연동 PC(신뢰 IP)에서는 ID/PW 자동 로그인이 CAPTCHA 없이 통과한다** — 실측 `login ok → main.do`.
CAPTCHA는 **낯선 IP·헤드리스**에서만 걸린다. 그래서:

- **세션 캡처(`capture-session.cjs`)는 이 PC에선 필요 없다** — 매 실행마다 로그인하면 된다.
- 따라서 감시할 것은 "세션 만료"가 아니라 **"로그인 자체가 실패하는 날"**(비밀번호 변경·CAPTCHA 도입·계정 잠금)이다.
  그날 동기화가 **조용히** 멈추므로 `check-session.mjs`가 원장 벨에 알린다.
- ⚠️ 로그인 실패 시 **재시도하지 않는다**(반복 실패 = 계정 잠금).

- 로그 = `.makeedu-tmp\health-check.log`(하루 한 줄, 2,000줄 넘으면 최근 1,000줄만 남김).

🔴 **`schtasks`로 따로 등록하지 말 것.** 지정 해제(`동기화PC-해제.bat`)가 그 작업을 못 지워서, 동기화 PC를
옮긴 뒤에도 **옛 PC가 계속 makeedu 로그인을 시도**한다(이중 로그인 = 계정 잠금 위험).

🔴 **첫 실패도 즉시 알린다** — 다른 Phase 3 이벤트의 "콜드스타트 무발송 시드"를 여기엔 **적용하지 않는다**(2026-07-30 수정).
그 규칙은 결석 마일스톤처럼 **이미 쌓인 과거 상태 수백 건**이 한꺼번에 울리는 걸 막는 장치인데, 이 점검은 주체가
`makeedu` 하나뿐이라 막을 폭탄이 없고, 시드를 두면 **정작 첫 로그인 실패가 통째로 침묵한다.**
⚠️ 알림은 **원장(master)** 에게만 가고, 컴퓨터 알림 + 화면 중앙 팝업까지 뜬다(벨 배지만으론 지나친다).

## 주의

- `compare-withdrawal-dates.mjs`는 **날짜만** 고친다. `status`·퇴원 사유는 건드리지 않는다.
- 매칭 우선순위 = **원생번호 → 전화 → 이름**(양쪽 모두 유일할 때만). 형제가 같은 번호를 쓰면 그 번호는 **버린다**(뒤바꾸면 최악).
- `withdrawn.json`에는 **보호자·원생 전화번호와 퇴원 사유**가 들어 있다(실 PII). `.makeedu-tmp`는 gitignore 대상이며, 외부로 보내지 말 것. **AI 프롬프트에 넣지 말 것.**
  (수납 임포터는 이 파일에서 **원생번호만** 읽는다 — 나머지 열은 건드리지 않는다.)
- 적용 후 첫 정기 실행 로그에서 두 줄을 확인할 것:
  · `퇴원 목록: N명 — 삭제 판정 5번째 가드 ON`
  · `── 월별 대조 …` 표가 **전부 ✅** 인지. 🔴가 있으면 그 달 금액이 makeedu와 다르다는 뜻이다.
- 스크랩 목록이 하나 늘어 실행이 조금 길어진다(현재 53~76초). `sync-all.cjs`의 자식 timeout은 8분이라 여유는 충분하다.
