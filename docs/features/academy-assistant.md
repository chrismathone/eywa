## 1. 흐름

`POST /api/assistant/ask`(NDJSON 흐름 — `protocol.ts`):
1. 문(`gate.ts`) → 지점 AI 라이선스(`requireAiLicense`) → 15분(`ASSISTANT_RUNNING_MS`) 넘은 '도는 중' 줄을 실패로 닫기 → 하루 100번 · 자리 확인(`store.admission` — 같은 대화가 도는 중 · 동시 3개 참) → 대화·'도는 중' 줄 저장(빈 자리 `run_slot`부터). 🔴 **동시에 3개까지 · 대화마다 하나**(§7-3) — 두 탭에서 동시에 물어도 DB 고유 색인 둘(`assistant_messages_running_slot_idx` 사람·자리 · `assistant_messages_running_thread_idx` 대화, 멈춤 누른 질문은 제외 · s2_0033)이 막는다(앱 확인만으로는 경쟁 상태). 막히면 `429 { code: "busy" }` — 실패가 아니라 안내.
2. 비서 DB 연결(`executor.ts`) — 먼저 보기 갱신(바뀌었을 때만, service_role RPC).
3. AI 루프(`agent.ts`, 조회·차례 한도 없음 — §7-2 · 마무리 = 고정 기한 200초 전(차례 도중이면 다음 조회를 쓰던 응답을 끊고 기록에 넣지 않은 채 곧장 보고서를 부탁) 또는 직전 입력 15만 토큰('적음'은 7만) 초과 또는 원장이 누른 '바로 결과 보기'(§7-3) · 그 뒤 조회·표 구조·전수 조회 요청은 실행하지 않음) — 도구 `describe_table` · `run_sql` · `survey_entity` · `render_report`. 표 구조 조회·SQL 검사기의 일시 오류는 그 도구만 실패로 돌려준다(질문 전체를 버리지 않는다).
   - 캐시 — 시스템 앞부분(도구 + 시스템) + 요청 최상위 `cache_control`(대화 기록 — 앞 차례 조회 결과가 차례마다 다시 가므로).
   - 진행 단계 `step` 이벤트 — 스트림의 `content_block_start`(도구 입력 쓰기 시작)에 단계를 열고, `inputJson`으로 들어오는 `purpose`를 바로 붙인다.
4. 답 저장(보고서 · 조회 · 단계 · 사용량) · 감사 `assistant_ask` · 사용량 장부(`recordUsage`, feature `academy_assistant`, 키 그룹 `ASSISTANT` — 끝까지 못 받은 차례의 토큰도 적는다(⚠️ 그 차례는 message_start 시점 값이라 출력 토큰이 거의 0 — 알려진 한계) · 사람이 누른 멈춤은 실패로 적지 않는다 · 고정 기한은 늘 실패로). 저장이 실패하면 표·차트 자료를 뺀 보고서로 한 번 더 저장하고, 그래도 안 되면 상태만 '실패'로 닫고(`markFailed`) 화면에도 실패로 보낸다(보인 답과 저장본이 어긋나지 않게 · 감사 outcome도 실제 저장 결과).
- 🔴 화면 연결이 끊겨도 끝까지 돌고 저장한다(`after`). 멈춤 = 사람이 누른 '멈춤'(`cancel_requested_at`, 2초마다 확인) 또는 **고정 기한 760초**(`ASSISTANT_HARD_DEADLINE_MS` — 라우트 기한 800초에 함수가 죽으면 저장·감사·사용량이 통째로 빠지므로 스스로 끊고 실패로 저장).
- 멈춤 순서 — 화면은 서버에 **알림이 끝난 뒤** 흐름을 끊는다(그 사이 '멈추는 중…' — 바로 다시 물어도 '앞 질문을 만드는 중'에 걸리지 않게). 번호(`started`)로 보내고, 실패하면(세션 만료·500·망) 화면이 보낼 때 만든 번호로 `POST /api/assistant/messages/<clientRef>/stop?by=ref` 한 번 더 · `keepalive`(동시에 여러 질문이 돌아 옛 '지금 도는 내 질문'(`current`)은 어느 것인지 몰라 없앴다). 번호를 받기 전에 누르면 기다렸다가 번호가 오자마자 알리고, 15초가 지나도 안 오면 `clientRef`로. 멈춘 질문은 마무리 중이어도 바로 다시 물을 수 있다.
- 다시 읽기 — 저장본이 '도는 중'이면 3초마다 `GET /api/assistant/threads/[id]?status=1`(도는지만)으로 묻고, 끝났으면 대화 전체를 한 번 읽는다(최대 15분 — 매번 표·차트 자료를 받지 않게).

## 2. DB 안전장치 — 막는 것은 DB 권한이다(프롬프트가 아니라)

SQL = `supabase/migrations/s2_0031_academy_assistant.sql`(번호는 병합 때 확정) · 되돌리기 = `scripts/_oneoff/revert-s2_0031-academy-assistant.sql`. 동시 3개·바로 결과 보기 = `s2_0033_assistant_parallel_finish.sql` · 되돌리기 = `scripts/_oneoff/revert-s2_0033-assistant-parallel-finish.sql`(앱을 먼저 되돌린 뒤).

- **로그인 역할 `aywa_assistant`** — `LOGIN NOINHERIT`, 어떤 역할의 구성원도 아니다(`set role`로 올라갈 곳이 없다) · 쓰기 함수·쓰기 권한 0 · 8초 · 연결 12개(s2_0033 — 동시 질문(사람당 3 · 여러 지점·사람 합계)과 정리 중인 질문의 조회 거래가 겹쳐 4개에서 올림 · 조회는 앱이 늘 읽기 전용 거래로 연다 — 역할 기본값으로 걸지 않는다: 마이그레이션의 읽기 전용 설정은 지점 보기 가드가 막는다). 🔴 그래도 모든 역할은 PUBLIC의 구성원이다(적대 리뷰 1번) — 그래서 아래 'PUBLIC 실행권 회수'와 사후 확인을 둔다. env `ASSISTANT_DATABASE_URL`(거래 방식 풀러 6543 · 비밀번호는 저장소 밖).
- **보기 `assistant.<표>`** — `refresh_views()`가 public의 지점 칸 있는 표마다 만든다(소유자 postgres · `security_barrier` · `where tenant_id = (select bound_tenant())` — initplan이라 한 번만 계산). 지점 칸 없는 셋은 부모로(`consultation_ai_analysis` · `notice_popup_translations` · `tenants` 내 줄). 나머지 지점 칸 없는 표(슈퍼관리자 · 연동 PC 배포 등)는 학원 자료가 아니라 없다.
  - 비밀 칸 = 이름 패턴(`token|secret|password|passwd|p256dh|api_key|signature`, `_hash`, `auth`) + 명시 목록(`push_subscriptions.endpoint`) · 가림 = `tenant_settings.data`의 `operations.seatPins` · 제외 표 = 비서 대화 · 옛 대화형 비서 대화 · 운영 콘솔 보기 기록.
  - 🔴 **빠짐없이** = 질문마다 `assistant_refresh_views_if_stale()` — public 표·칸(타입)·정책 표의 지문이 바뀌었으면 다시 만든다(새 표 · 새 칸이 다음 질문부터 보인다).
- **지점 묶기 = DB가 서명한 증표**(적대 리뷰 2번 반영 — 처음 설계는 같은 역할이 bind를 부르는 방식이라 읽기 전용 한 겹에 달려 있었다):
  - 앱 서버가 서버 키로 `public.assistant_issue_binding(지점)`(service_role만 실행) → 증표 `<지점>.<만료 epoch>.<HMAC-SHA256>`(5분 · 서명 키는 `assistant_private.signing_key` — 누구에게도 권한 없음).
  - 조회 한 번 = `begin read only` → `set_config('assistant.binding', 증표, true)`(매개변수 — 다른 세션의 질의문에 안 보인다) · 8초 · search_path → `bound_tenant()`가 이 지점인지 확인(아니면 멈춤 — '0명'으로 답하지 않게) → EXPLAIN VERBOSE → 세이브포인트 안 조회 → `pg_advisory_unlock_all()` → rollback.
  - 비서 역할은 쓰기 함수가 하나도 없고 증표를 만들 수 없다 — set_config로 다른 값을 넣어도 서명이 안 맞아 null → 모든 보기 0행.
- **PUBLIC 실행권 회수**(적대 리뷰 1번) — 운영 확인 2026-11-06: PUBLIC이 실행할 수 있는 public 보안 정의자 함수 25개(트리거 14 · 일반 11 — `auth_*` · `is_super_admin` · `operator_view_tenant`), 모두 anon·authenticated·service_role·postgres에 명시 실행권이 따로 있다. → 트리거가 아닌 11개만 PUBLIC 실행권을 회수한다(명시 실행권 그대로 — 앱·로그인 사용자 영향 없음 · 되돌리기가 기록대로 되살린다). 🔴 정정(2026-11-06): 연동 PC 역할 `eywa_sync_agent`는 이 함수들을 PUBLIC으로 불렀다(정책의 겉함수 `auth_tenant_id()` 속) — 적용 직후 연동 PC의 ClassNote 발송 · 학부모 글 감지가 1시간 40분 멈췄고 s2_0032가 그 역할에 명시 실행권을 줬다(함정 #155). 사후 확인: 비서 역할이 부를 수 있는 보안 정의자 함수 = `bound_tenant()` 하나. ⚠️ `net.*`(pg_net)은 Supabase가 관리해 손대지 않는다 — 요청 함수는 큐 insert라 읽기 전용이 막고, `worker_restart` 같은 것은 앱 검사 + 실행 계획 검사가 막는다.

## 3. DB 지도 · 온톨로지

- `catalog/tables-a.ts`·`tables-b.ts` — 표마다 `label`(진행 단계 칩) · `ko`(한 줄) · `notes`(상태 값 뜻 · 소프트 삭제 · 금액 단위 · 날짜 칸) · `columns`. 표 목록 + `ko`는 시스템 프롬프트(캐시), 나머지는 `describe_table`.

  - **리뷰 반영(11-09)**: ① 날짜 칸은 '일이 일어난 날' 먼저(성적 taken_on · 시험 test_date · 보강 makeup_date · 학부모 글 posted_at … 비면 입력 시각으로 메운다) → 시작·끝이 있는 줄(수강 start/end · 위임 from/to · 시간표 valid_from/to 등)은 **기간이 겹치는 줄** → 입력 시각(created_at). 결재·제출·완료 같은 처리 시각은 쓰지 않는다(대기 중인 줄이 기간에서 빠졌다) ② 강사는 `…_by` 칸 전부(대신 보강 taught_by · 후속조치 handled_by …, 고친·처리 흔적 updated_by·moved_by·cancelled_by 등은 뺌) + **이 기간에 맡은(맡았던) 반을 거친 표**(onto_class_teachers 중 맡은 기간이 조회 기간과 겹치는 반 · 폐지·보강용 반·기간 전에 끝난 반 제외 — `taughtClassesSql` · 반 id를 늘어놓지 않고 전수 조회 SQL의 `with` 절이 같은 조건으로 다시 고른다(검사기 8,000자 상한) · 영상 숙제 검사·반 출결처럼 강사 칸이 없는 반 자료 · '맡은 반을 거쳐'로 따로 센다 · 그 반의 기간 자료 전체라 다른 강사 몫도 섞인다고 AI에게 알린다) · 이름이 같은 사용자가 있으면 이름 글자(teacher_name)로는 세지 않는다 ③ 문서에 `internal`로 적힌 표(알림 구독·연동 코드 등)는 세지 않는다 ④ 대상 확인 — id가 그 종류의 표(students·classes·users)에 없으면 돌려보내고, 이름은 DB 이름으로 ⑤ 없는 날짜(평년 2월 29일)·시작 > 끝은 받지 않는다 ⑥ 반씩 쪼개기는 그 표 탓일 수 있는 조회 오류에만(실행기가 오류를 `query`/`connection`으로 가른다 — SQLSTATE가 없거나 08·57P·25P·53300이면 연결 쪽 · 바로 실패 — AI가 run_sql로 잇는다) · 실행 횟수 상한(묶음 수 × 9) · 전수 조회 한 번 2분 · 멈춤·마무리 시각이면 남은 묶음은 '세지 못함' ⑦ '자세히 봄' = 그 전수 조회 **뒤의** 조회가 읽은 표(대상 id를 찾던 앞 조회는 세지 않는다 · 대상이 여럿이면 SQL에 그 대상 id가 든 조회만, 아무 id도 없으면 가장 최근 대상) · 같은 표의 '직접'과 '맡은 반' 줄은 따로(`key`) · 여러 원본을 합친 보기(반 담당)는 원본을 봤다고 '자세히 봄'이 되지 않는다 ⑧ 전수 조회 단계는 제 종류(`survey`) — '조회 N번'에 세지 않고 표 구조 확인과 묶여 '다시 시도'로 읽히지 않는다.
  - AI는 이 지도를 받고 '기간 안 자료 있음' 표를 **하나도 빠짐없이** run_sql로 본다(안 볼 표는 까닭과 함께 '이번에 깊이 보지 않은 자료'). 보고서 끝에 서버가 **'확인한 자료 범위'**(센 표 수 · 자료 있는 표마다 기간 건수·최근 · ✓ 자세히 봄 / 건수만 셈 · 세지 못함)를 붙인다 — 원장이 빠진 것을 직접 본다.
- **한도 없앰** — 조회 횟수(12) · 차례(14) 한도를 뺐다. 추론 강도는 모델·생각 깊이로만 나뉜다. 남은 물리적 한계 둘: ① 실행 시간 — 라우트 `maxDuration` 800초(Vercel Pro 최대) · 고정 기한 760초 · 그 200초 전부터 마무리(더 조회하지 않고 보고서 — 차례 도중이면 쓰던 응답을 끊는다: 차례가 끝나기를 기다리면 보고서 쓸 시간이 모자라 모은 결과가 통째로 사라졌다 · 적대 리뷰 11-09) ② AI가 한 번에 읽는 분량 — 직전 차례 입력이 15만 토큰을 넘으면 같은 마무리('적음' Haiku는 10만 토큰을 넘으면 단가가 5배라 7만 — 판정은 직전 차례 입력이라 한 차례 조회 결과가 더 붙을 여유 3만). 마무리 뒤 3차례 안에 보고서가 없으면 멈춘다. '도는 중'으로 보는 시간 15분.

## 7-3. 동시에 3개 · 바로 결과 보기 · 목록에서 지우기(11-06 밤 · SQL s2_0033)

- **동시에 3개까지**(원장 *"대화를 여러개 동시에 시작할 수 있는지 … 정상적인 동작으로 인식되게"* → '동시에 3개까지'를 고름 — 한도를 없애 답 하나가 최대 13분쯤 걸린다).
  - 대화마다 하나(같은 대화의 둘째 질문은 앞 답을 모르고 답하게 된다) · 사람당 셋. DB 색인 둘이 마지막에 가른다(§1) — 앱은 빈 자리(`run_slot`)로만 넣고, 23505가 자리 색인이면 다음 자리 · 대화 색인이면 `busy_thread`.
  - 화면(`assistant-state.ts`): `inflight`가 차례 배열 · 대화마다 제 손잡이(`use-assistant.ts` `Run` — 흐름 · 질문 번호 · `clientRef` · 번호 전 멈춤/마무리). 멈춤·마무리는 그 대화의 차례로.
  - **다른 탭·기기·새로 고침 뒤에도 정상으로 보이게** — 목록 응답에 `running`(멈춤 누른 것·15분 넘은 것 제외) · 저장본 '도는 중'도 센다(`runningThreadKeys`). 그 대화에서는 보내기를 막고 "이 대화는 아직 앞 질문의 답을 만드는 중…" · 셋이면 "답은 동시에 3개까지…". 그래도 서버가 `busy`로 받지 않으면 빨간 실패 카드 대신 보낸 차례를 거두고(`ask/rejected`) 입력칸 아래 안내 + **보낸 글을 입력칸에 되돌린다**(그사이 새로 쓴 글은 덮지 않는다) + 목록을 다시 읽는다. 다른 탭에서 도는 대화가 목록에 있으면 판이 열린 동안 15초마다 목록을 다시 읽어 끝난 것을 푼다.
- **'바로 결과 보기'**(원장 *"'여기서 조회 끝내고 바로 결과 출력' 버튼 만들자. 그럼 조회 멈추고, 지금까지 조회한 내용으로만 결과 출력"*) — 입력칸의 '멈추기' 옆. 조회를 하나 마친 뒤 누를 수 있다(근거 없는 보고서를 막는다).
  - `POST /api/assistant/messages/[id]/finish`(번호 전이면 `?by=ref`) → `wrap_requested_at` → 도는 쪽(`ask.ts`)이 2초마다 보고 `wrapSignal`을 끊는다.
  - `agent.ts` — 마무리 까닭 `user`: AI가 다음 조회를 쓰는 중이면 그 응답을 끊고 **기록에 넣지 않는다**(덧붙이기만 — 생각 블록이 어긋나지 않는다) → 마지막 사람 차례에 마무리 부탁을 붙여 곧장 보고서. 이미 보고서를 쓰기 시작한 응답은 끊지 않는다. 남은 도구 호출은 `cause: "user"`(화면은 옅은 멈춤 '여기서 조회를 끝냄' — 막힘이 아니다) · 전수 조회는 남은 묶음을 세지 않고 '세지 못함'으로 남긴다(빠진 것을 숨기지 않는다).
  - 보고서 위 한 줄(`cutShort` — 서버가 붙인다): '바로 결과 보기'로 여기서 조회를 끝내고 정리한 답 · 시간이 다 돼 · 읽은 자료가 많아. 감사 `assistant_ask` metadata에도 `cutShort`.
  - '멈추기'는 그대로 질문째 버린다('질문을 멈췄습니다').
- **목록에서 지우기**(원장 *"대화 지우기도 현재 대화 가장 위로 올라가야 지울 수 있는데, 대화 목록에서 x 버튼 마우스 오버시에 나오도록"*) — 목록 행에 마우스를 올리면(키보드 초점 · 터치 화면은 늘) 날짜 자리에 x → 그 행이 '지울까요?' 확인으로 바뀐다(초점 '취소' · Esc는 확인만 닫고 초점은 x로). 대화 머리의 '대화 지우기'는 뺐다. 도는 대화는 x 없음. x는 여는 버튼 옆 형제라 버튼 안 버튼이 아니다 — 앱 규약 '목록 행 안 아이콘 버튼 없음'의 원장 지시 예외.
- 로컬 시험(PGlite · 운영 표 구조) 22건(옛 앱이 자리 번호 없이 넣은 줄 · 되돌린 뒤 새 칸 없음 포함): 자리 1~3 · 넷째는 자리 색인 · 자리 4는 check · 빈 자리여도 같은 대화 둘째는 대화 색인(메시지에 색인 이름) · 멈춘·끝난 질문은 자리를 비움 · `client_ref`로 마무리 표시 · 두 번 적용 · 되돌리기(사람당 하나만 남김) → 다시 적용.
- **적대 리뷰 반영(11-09)**: ① 도는 대화는 지우지 않는다(서버 `deleteThread`도 409 — 지우면 목록에서 사라져 멈출 화면이 없는 질문이 자리를 최대 13분 차지했다 · 확인을 열어 둔 사이 돌기 시작하면 확인을 거둔다) ② 다른 대화로 옮긴 뒤 끝난 대화가 '도는 중'으로 남아 자리를 세던 것 — 판이 열린 동안 15초마다 목록 + 그 대화들의 '도는지'를 다시 읽는다(`staleRunningThreadIds`) ③ 멈추면 목록 '도는 중'을 바로 내리고, 멈춘(정리 중인) 질문은 저장본·`?status=1`에서도 도는 것으로 보지 않는다 ④ '바로 결과 보기'는 조회를 마쳤거나 전수 조회를 시작한 뒤(표 구조만 본 것은 자료가 아니다) ⑤ 이 화면이 받지 않는 도는 질문(다른 탭·새로 고친 뒤)에도 '바로 결과 보기' · '멈추기'(질문 번호로) ⑥ 번호 전 멈춤이 화면 번호로도 못 찾으면 끊지 않고 번호를 45초 더 기다린다(끊으면 서버만 돌며 자리를 쥔다) ⑦ 배포 전에 열린 옛 화면의 `messages/current/stop`은 가장 최근 질문 하나를 멈춘다 ⑧ 받지 않은 질문의 글은 보낸 대화를 보고 있을 때만 입력칸에 되돌리고, 안내는 자리가 나면 내린다 ⑨ 목록 조회와 '도는 대화' 조회는 함께(하나가 실패해도 목록은 낸다) ⑩ 늦게 온 목록이 방금 생긴 대화를 빼지 않는다 ⑪ 지운 뒤 초점은 '새 질문' · 지우는 중 Esc는 확인을 닫지 않는다 · 목록을 접으면 확인도 닫는다 · 입력칸 알림은 늘 있는 `aria-live` 칸 ⑫ 연결 상한 12. 재리뷰 반영: 원장이 끝낸 단계 표식(`cause: user`)을 화면이 버리지 않는다 · 자리 없음 안내는 목록을 다시 읽기 전까지만(그 뒤엔 목록이 말한다) · 다른 곳에서 지운 대화(404)는 도는 표시를 풀고 목록에서 뺀다 · 번호 전 멈춤은 번호가 언제 와도 그 번호로 · 늦게 온 목록이 방금 한 지우기·이름 바꾸기를 되돌리지 않는다 · 자료를 읽기 전에 누른 '바로 결과 보기'는 첫 자료를 읽은 뒤에 든다(다른 탭 버튼 포함).
- 적용 순서: **원장 승인 → s2_0033 운영 적용 → 앱 배포**(새 앱은 새 칸을 쓴다). SQL만 들어간 몇 분은 옛 앱이 `run_slot` 없이 넣어 사람당 하나 막기가 앱 확인뿐이다(대화마다 하나는 색인이 막는다).

- 질문 만들기는 순수(`suggestions.ts` `buildSuggestions`) — 심한 순 6개, 모자라면 고정 문장(신호가 다룬 주제의 고정 문장은 뺀다). 질문 글엔 원생 이름·연락처를 넣지 않는다(반 이름·건수까지). 각 질문 밑에 숫자 근거 한 줄. AI는 부르지 않는다.
- 하루 한 번: `GET /api/assistant/suggestions` — 화면이 사람·지점 표(scope = tenant:user 해시)와 한국 날짜로 묶음을 브라우저에 두고 `?have=`로 알리면 서버는 세지 않는다. 날짜가 바뀌면 새로 센다 · '새로 고침'(`?refresh=1` · 30초 연타 막기)은 지금 다시 센다. 같은 인스턴스는 같은 지점을 30분(새로 고침 1분) 기억한다. 🔴 서버가 scope를 확인하기 전엔 브라우저 묶음을 보이지 않는다(같은 컴퓨터의 다른 사람에게 지점 숫자가 비치지 않게).
- NEW = 직전 묶음에 없던 **주제**(`key` — 결석 · '○○반 출석률' · 미납 …) · 숫자만 바뀐 질문은 NEW가 아니다 · 묶음이 바뀐 그날에만 보이고 고정 문장엔 안 붙는다(리뷰 11-09 — 글로 가르면 매일 거의 다 NEW였다). 본 것은 브라우저에 둔다(기기를 바꾸면 처음부터 — 편의 표시라 계정에 두지 않았다). 처음엔 직전 묶음 = 고정 문장. 계산이 실패한 고정 문장 묶음은 저장하지 않고 NEW도 없다.
- 운영 실측(읽기 전용 · 재원 333명 지점 · 11-06): 신호 7개 모두 검사 통과 · EXPLAIN 비용 ≤ 3.7천 · 합계 약 1.3초 — 결석 3번 이상 57명 · 출석률 하락 반 1곳(93%→74%) · 석 달 상담 없는 재원생 72명 · 미납 9건(93만 원 · 2달 넘은 2건) · 신규 상담 20건 중 등록 6건 · 30일 퇴원 12명(그 전 6개월 월 25.8명이라 낮은 순위) · 내신 기록 없음.
- 첫 화면 추천 버튼 글이 가운데로 보이던 것(버튼 기본 정렬) → `text-left`.
- **적대 리뷰 반영(11-09)**: 결석은 빠진 수업 단위(원생·반·날짜 — 영어 두 교시가 부풀었다) · 출석률 하락 반은 원생 3명 이상 반만(1:1 반 이름에 원생 이름) · 석 달 상담 없음에서 등록 석 달 안 된 원생 제외 · 퇴원은 퇴원일이 이번 달 1일~오늘(운영실 카드는 퇴원월 — 수강료를 낸 마지막 달 — 기준이라 숫자가 다를 수 있다 · 질문의 실마리) · 신규 상담은 상담 뒤 일주일 지난 것만 · 내신은 '적어 둔 시험 일정 기준'을 밝힌다 · AI 라이선스가 꺼진 지점은 세지 않는다 · 같은 지점 동시 요청은 한 번 · 일부 신호만 센 묶음은 1분만 기억하고 화면도 오늘 묶음으로 저장하지 않는다 · 세지 못하면 보던 좋은 묶음을 덮지 않는다 · 판을 다시 열어 날짜가 바뀌었으면 다시 받는다(판은 한 번 열면 붙어 있다) · 응답 20초 · NEW 글씨는 `text-xs`(14px 바닥).
