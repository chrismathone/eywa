## 확인한 영향 범위와 테스트 한계

- **원본 보존과 초기 생성:** 중앙 저장은 resolveSettings 결과로 전체 문서를 다시 만들지 않고 원본 base를 펼친다(`src/features/owner/server/actions.ts:188`, `:235`). 역할 저장·예약 그룹 저장도 원본을 펼친다(`src/features/owner/server/setting-role-actions.ts:39`; `src/features/owner/server/scheduled-groups.ts:109`). 슈퍼관리자 생성의 rev 없는 INSERT는 새 tenantId의 최초 행 생성이다(`src/features/super-admin/server/actions.ts:81`); 데모 INSERT도 행 없음에서만 실행한다(`src/features/demo-roster/dashboard-apply.ts:64`, `:68`). tenant_id는 PK여서 기존 행을 덮는 upsert가 아니다(`supabase/migrations/0033a_tenant_settings.sql:9`). configure의 행 생성도 충돌 시 아무것도 쓰지 않는다(`supabase/migrations/0346l_makeup_cmd_configure.sql:29`). 검토한 현재 src writer에는 기존 rev를 지우는 다른 통째 교체 경로를 발견하지 않았다. 설정 문서 자체의 내보내기·복제 경로는 이번 src 검색에서 식별하지 못했으며, 외부 도구의 보존 여부는 **미확인**이다.
- **순번을 올리지 않는 변경의 경계:** 시트 SQL이 고치는 integrationGroupsEnabled/integrationGroups/integrationShowOthers는 과목 면의 canonical에서 제외하는 시간표 키다(`src/features/timetable/server/master-sheet-store.ts:372`; `src/features/owner/operations-slice.ts:36`, `:161`). 같은 순번의 역순 읽기가 이 칸에 한정되면 면의 소유 값/token을 바꾸지 않으며, 과목 저장은 fresh의 시간표 칸을 보존한다(`src/features/owner/operations-slice.ts:72`, `:93`). makeups RPC도 두 편집 면의 소유 칸을 고치지 않는다(`supabase/migrations/0346l_makeup_cmd_configure.sql:77`, `:82`). **데모 weekdayGrouping은 이 전제를 만족하지 않는 E2의 실제 예외**다.
- **일반 소비처·프리셋·감사로그:** deepMerge는 기본값의 키만 순회하고 resolveSettings는 그 결과를 반환하므로 새 최상위 rev가 일반 TenantSettings 화면 모델에 섞이지 않는다(`src/features/owner/resolve.ts:21`, `:112`; 모델 `src/features/owner/settings-types.ts:752`). preset 판정은 stored.preset만 읽는다(`src/features/owner/preset.ts:22`). 감사로그의 비교 입력도 전체 data가 아닌 해당 섹션 두 값이므로 rev 자체의 증가가 변경 건수에 들어가지 않는다(`src/features/owner/server/actions.ts:256`; `src/features/owner/settings-diff.ts:318`). 추가 대시보드 가드는 dashboard 변경에만 발화하고(`supabase/migrations/0327a_dashboard_settings_guard.sql:27`), 보강 가드는 makeups/modules를 검사한다(`supabase/migrations/0344b_makeup_settings_periods.sql:37`, `:41`). **rev를 문제 삼는 실제 가드는 E1의 0335a 잔여 문서 비교**다.
- **0/undefined·삭제·PIN:** props 채택은 `version ?? confirmedVersion`, 성공/삭제 채택은 `nextVersion !== undefined`라 0이 빠지지 않는다(`src/app/(shell)/owner/_components/use-section-draft.ts:67`, `:80`, `:88`). 이미 없는 과목 제거의 무쓰기 응답도 원본의 현재 rev를 반환한다(`src/features/owner/server/actions.ts:217`); 삭제 결과는 숫자 version을 그대로 연결한다(`src/features/owner/server/subject-actions.ts:160`, `:170`; 화면 adopt `src/app/(shell)/owner/_components/subjects-section.tsx:440`). 편집 읽기·token·version은 운영 저장 권한자에게만 전달하는 분기다(`src/app/(shell)/owner/page.tsx:143`, `:146`, `:211`, `:225`). rev는 PIN과 독립적인 저장 횟수여서 이를 추가해 PIN 원문을 전달하는 경로는 생기지 않았다(`src/features/owner/server/actions.ts:235`; `src/features/owner/server/queries.ts:132`). 읽기 전용은 undefined이며, 행 부재 0과 구별된다.
- **보강 테스트의 효력과 빈틈:** 실제 중앙 액션에서 N→N+1·시계 역행·부분 쓰기 보존·unchanged·첫 INSERT를 검사한다(`src/features/owner/server/operations-save.test.ts:435`, `:449`, `:459`, `:469`, `:476`). 훅과 실제 두 가드의 첫 저장 테스트는 D2의 다음 제출까지 확인하므로 헛도는 단언이 아니다(`src/app/(shell)/owner/_components/section-form-guards.test.tsx:311`). 그러나 저장 모의는 DB 권한 트리거 없이 UPDATE 값을 그대로 채택하며 기본 행위자는 master다(`src/features/owner/server/operations-save.test.ts:16`, `:49`, `:52`). writer 가드도 rev 증가 문자열/jsonb_set 존재만 확인한다(`src/features/owner/tenant-settings-writers.test.ts:64`, `:71`). 따라서 **12파일 통과가 E1을 배제하지 않는다**. 같은 순번 훅 테스트도 새 props 한 번만 받으므로 E2의 역순 token 변경을 검사하지 않는다(`src/app/(shell)/owner/_components/use-section-draft.test.tsx:288`).
- **운영 전제:** 수동 스크립트/외부 복원에서 옛 data를 통째로 다시 쓰면 rev 보존을 보장할 수 없다. 현재 writer 가드도 이 영역을 검사하지 않고, 옛 순번 되쓰기 금지·앱/cron과 동시 실행 금지를 전제로 명시한다(`src/features/owner/tenant-settings-writers.test.ts:13`). 1d의 경미 D3는 이 전제 아래 후속이며, 이번 검토에서 스크립트를 실행하지 않았다.
