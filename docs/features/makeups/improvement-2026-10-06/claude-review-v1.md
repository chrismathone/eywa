## 3. 필수 수정 (이것이 반영돼야 APPROVE)

### P0-A. 새 조회 필드가 출결 저장 경로를 막지 않게 한다

근거: 파서는 한 줄이 틀리면 전체를 실패시키고(`command-parse.ts:132-135`), 그 실패는 출결 저장·보강 보고서 저장·예약 취소를 막는다(`gates.ts:28, 70, 112, 132`, `completion.ts:43`). 계획은 "신규 필드 부재를 감지한다"고만 적고 **어느 소비처가** 그 감지를 쓰는지 정하지 않았다. 새 칸을 파서의 필수값으로 만들면 SQL 적용 전 구간에 켜진 지점의 수학 출결 저장이 통째로 막힌다. SQL은 원장이 손으로 적용하므로 앱과 DB 사이에는 늘 간격이 있다.

계획에 넣을 문장:
1. 기본 줄 파서(`participant()`)는 새 칸을 **선택값**으로만 읽는다. 새 칸이 없거나 값이 낯설어도 줄을 거절하지 않는다.
2. 진행 상태는 **요청한 호출만** 받는다: 필터에 `with_progress: true`를 넣은 호출(대시보드 예정·학생 예정·일정 보기)에만 DB가 진행 칸을 계산해 싣고, 응답 최상위에 `progress_contract: 1`을 싣는다. 출결 문·이행 훅·명단·시수 마스터는 이 값을 요청하지 않는다(응답 모양·비용 불변).
3. 구 스키마 판별은 줄의 칸 유무가 아니라 **최상위 표식 유무**로 한다. 요청했는데 표식이 없으면 그 화면의 새 참여 줄만 '확인 필요'로 표시한다(`null` 실시 기록과 "칸이 없음"을 줄 단위로는 구분할 수 없다).
4. 모르는 참여 상태를 `"unknown"`(= 아직 기록 전)으로 접는 지금의 폴백(`command-parse.ts:104`)을 진행 분류에는 쓰지 않는다. 진행 분류는 원문 값을 보고, 낯선 값은 '확인 필요'다.
5. "DB 먼저, 앱 나중"은 권장 순서일 뿐 전제가 아니다. 앱은 구·신 스키마 양쪽에서, 구 앱은 신 스키마에서 동작해야 한다고 적는다.
6. 배선 시험: 새 칸이 있는 응답과 없는 응답에서 `gates.ts`·`completion.ts`·`roster-merge.ts`의 결과가 같음을 시험으로 고정한다.

### P0-B. 진행 상태 정의를 "순서 있는 판정"으로 다시 쓴다

계획의 표는 행이 서로 겹치고 순서가 없다. 실제 SQL과 대조하면 세 곳이 틀린다.

1. **반전 판정 근거가 틀렸다.** 계획은 "가장 최근 인정 반전 존재 여부"를 추가한다고 했는데, 실시 기록의 `reversed`는 인정 반전(`0346g:52`)뿐 아니라 **노쇼 정정**(`0346e:114-115`)에서도 생긴다. 실시 기록 상태로 판정하면 "노쇼 → 다시 왔다로 정정 → 새 초안"인 참여가 '재검토 필요'로 잘못 분류된다. 반전은 `makeup_recognitions.kind = 'reverse'`의 존재로 판정한다고 적는다.
2. **"연결한 기존 완료 예약"이 예정으로 되살아난다.** 이미 `done`인 예약을 연결하면 참여는 `unknown`이고 날짜는 과거다(`0346i:104-118`). 계획의 표대로면 '지난 예약·기록 확인 필요 → 보강예정 포함'이 된다. P1이 연결을 권장하므로 연결할수록 대시보드 '지남'이 늘어난다 — P0가 고치려는 것과 같은 종류의 오류다. 이 경우를 표에 한 줄로 넣는다: 살아 있는 `imported` 연결 + 기존 예약 `done` + 참여 `unknown` → **'기존 완료 근거 확인'**, 보강예정 제외, 확인 위치는 대사(`legacy_done_review`). 이 판정에 필요한 "연결된 기존 예약의 상태"를 조회 계약에 추가한다(앱의 기존 예약 조회는 `reserved`만 읽어 알 수 없다).
3. **도달할 수 없는 조건과 빠진 조건.** "초안/보완 요청에 실제 분량·근거가 있음"은 왔다/일부 기록과 같은 트랜잭션에서만 생기므로(`0346e:124-139`, `0343b:82`) 따로 둘 조건이 아니다. "보고서 첨부·초안만 있고 참여는 미기록"인 상태는 명령으로 만들 수 없다. 반대로 0분 인정(`0346f:143`), 왔다/일부인데 살아 있는 실시 기록도 반전도 없는 모순 상태는 표에 없다.

계획의 표를 아래 순서 판정으로 바꾼다(위에서부터 처음 맞는 줄):

| 순서 | 조건(DB 값) | 분류 | 보강예정 |
| --- | --- | --- | --- |
| 1 | 진행 표식 없음 · 낯선 상태값 · 아래 어느 줄에도 안 맞는 모순 | 확인 필요 | 숨기지 않고 따로 표시(예정 수에 섞지 않는다) |
| 2 | 참여 `cancelled` | 취소·변경됨 | 제외 |
| 3 | 참여 `no_show` | 미참석 | 제외 |
| 4 | 왔다/일부 + 살아 있는 실시 기록 `verified` | 검토 완료(인정 합 0분이면 그렇게 표기) | 제외 |
| 5 | 왔다/일부 + `submitted` | 검토 대기 | 제외 |
| 6 | 왔다/일부 + `draft`·`returned` | 실시 기록·보완 필요 | 제외 |
| 7 | 왔다/일부 + 살아 있는 실시 기록 없음 + 반전 인정 행 있음 | 인정 정정됨 · 실시 기록 다시 필요 | 제외 |
| 8 | `unknown` + 살아 있는 `imported` 연결 + 기존 예약 `done` | 기존 완료 근거 확인 | 제외 |
| 9 | `unknown` + 회차 `confirmed` + 오늘 이후 | 예약 | 포함 |
| 10 | `unknown` + 회차 `confirmed` + 오늘 이전 | 지난 예약·기록 확인 필요 | 포함 |

회차가 `cancelled`·`rescheduled`인데 참여가 살아 있거나, 회차 `finished`인데 참여가 `unknown`이면 1번이다. "오늘"은 DB의 한국 날짜(`actor().today`)로 판정하고 응답에 싣는다.

### P0-C. 진행 판정을 한 곳에 둔다 — 케이스 목록과 두 벌이 되지 않게

근거: 케이스 목록은 이미 같은 사실로 `record_missing`(지난 미기록, 또는 왔는데 초안/보완 요청/실시 기록 없음)과 `review_pending`(제출됨)을 정한다(`0348a:34-42`). 인정 반전 뒤 상태는 지금 **'실시 기록 필요'**로 분류된다(반전된 기록은 조인에서 빠지고 `coalesce(..., 'draft')`가 된다). 계획의 '재검토 필요'는 같은 참여를 일정 보기에서 다른 이름·다른 업무로 부르게 된다.

계획에 넣을 문장:
1. 진행 판정은 SQL 도우미 한 개(예: `makeup_private.participant_progress`)에 두고 참여 조회와 일정 RPC가 같이 쓴다. TypeScript는 값을 한글 문구로 바꾸기만 한다(화면별 재판정 금지).
2. 일정의 5·6·7·10번 줄과 케이스 목록의 `review_pending`·`record_missing`이 같은 참여 집합을 가리킴을 pgTAP 시험으로 묶는다. 케이스 목록 함수는 이번에 바꾸지 않는다.
3. 7번 줄의 다음 업무는 기존 그대로 '실시 기록'(다시 기록 → 제출 → 다른 관리자 검토)이라고 적는다. 새 업무 이름을 만들지 않는다.

### P1-A. '기존 예약 연결 필요 N건'을 나눠 세고, 연결 권한을 DB에서 받는다 (코디네이터 점검 3)

근거: 기존 예약 후보는 상태·보강일 제한이 없다(`0348e:57-64`). 상태는 `reserved`·`done`뿐이고 취소는 삭제다(`0264a:53-54`). 그대로 세면 지난달에 이미 이행한 수학 예약이 전부 "연결 필요"가 된다. 연결은 `wide` 권한만 되는데(`0346i:27`) 화면은 `canWriteTenant`로 버튼을 보여 준다(`candidates/page.tsx:46`) — 강사는 누르면 항상 거절당하는 버튼을 본다.

계획에 넣을 문장:
1. 후보 조회에 기존 예약 상태·보강일 조건을 추가하는 **읽기 마이그레이션**을 P1 파일 목록에 넣는다(지금 목록에는 SQL이 없다).
2. 세 갈래로 센다: 앞으로의 예약(`reserved`, 보강일 ≥ 오늘) / 지난 미이행(`reserved`, 보강일 < 오늘) / 이행된 이력(`done`). 상단의 '연결 필요 N'은 앞의 둘만이다. `done`은 "이행된 기존 예약 M건 — 연결은 선택이며 연결하면 완료 근거 확인 업무가 생긴다"로 따로 둔다.
3. 문구에 범위를 적는다: 수학만, 이 계정이 볼 수 있는 반만.
4. 연결 가능 여부는 조회 응답의 권한 힌트(예: `permissions.link_legacy` = 지점 전체 운영 + 모드 `on`)로 받는다. 거짓이면 연결 버튼·링크를 어디에도 두지 않고 "관리자가 연결합니다"만 보인다. 기존 예약 저장 성공 화면의 연결 진입도 같은 힌트를 쓴다(예약을 주로 만드는 강사에게는 안 보이는 것이 맞다고 적는다).
5. 수용 기준 5의 "취소 이력"을 지운다. 기존 예약에는 취소 상태가 없다.

### P1-B. 접수 명령이 결석을 직접 확인한다 (코디네이터 점검 2)

근거: 출결 근거 접수는 넘겨받은 행의 상태만 본다(`0346a:116-127`). 후보 화면의 조건(칸의 최신 행, 그날 시수 행 없음)과 다르다. 접수 뒤 정정은 트리거가 보지만(`0349b`), **접수 전에 이미 정정된** 결석 행으로 접수하면 대사 항목이 생기지 않는다. 수동 대사를 실행하기 전까지 아무도 모르고, 승인은 원결석을 다시 보지 않는다. 화면에서만 다시 조회해 검증하면 열어 둔 탭·연속 클릭·직접 호출로 지나간다. 그 결과는 근거 없는 건이 승인 대기에 서고 관리자가 분량을 승인할 수 있다는 것이다.

계획에 넣을 문장(둘 다):
1. 새 마이그레이션으로 `cmd_intake`의 **거절 조건만** 강화한다: `source_kind = attendance`이면 그 행이 칸의 최신 행이 아니거나, 그날 그 반에 유효한 시수 행(출석·지각·조퇴·보강)이 있으면 거절한다. 판정은 후보 조회와 **같은 도우미**를 쓴다(후보에 뜬 것은 접수되고, 접수되는 것은 후보에 뜬다).
2. 원수업 반·날짜가 있는 모든 접수(수동 포함)는 건을 만든 같은 트랜잭션에서 `observe_attendance_cell`을 한 번 부른다. 이미 출석인 날이면 `source_conflict`가 바로 열린다(거절하지 않는다 — 예정 결석·휴강은 정상).
3. "writer·장부 산식은 변경하지 않는다"는 문장을 "접수 명령의 거절 조건 강화와 관측 호출 추가. 출결·시수·급여·청구·권리 잔량 쓰기는 없다"로 고친다.
4. 이 변경을 받지 않기로 하면 수용 기준 7을 "화면이 막는다"로 낮추고, 승인 화면에 원결석의 지금 출결 상태를 보여 주는 항목을 P2에 넣는다. 둘 중 하나를 명시한다. 권장은 1~3이다.

### P1-C. 연결된 기존 예약은 새 참여가 말한다 — 우선 규칙과 범위 차이 (코디네이터 점검 1)

확인: 참여 기록·취소·변경은 같은 트랜잭션에서 기존 예약 행을 `done`으로 바꾸거나 삭제한다(`0346e:141-146`, `0346d:34-39`). 즉 예약 행의 **반영 지연은 없다**(반영 작업 `projection_jobs`는 출결 효과용이다). 그래도 규칙은 필요하다: 위 P0-B의 8번(연결한 완료 예약)과, 손으로 고친 데이터 같은 모순 때문이다.

계획에 넣을 문장:
1. 살아 있는 연결이 있는 기존 예약 행은 **그 자체로 줄을 만들지 않는다**. 그 줄의 표시 여부와 상태는 새 참여의 진행 판정이 정한다. 이 제거를 새 참여의 예정 여부 판정보다 **먼저** 한다(지금 코드 순서 — 기존 예약 먼저 넣고 같은 키의 새 참여를 건너뜀 — 를 뒤집는다).
2. 연결이 없는 기존 예약과 새 참여가 같은 날 같이 있는 경우(`legacy_multi_same_day`, `0346i:86-95`)는 서로 다른 약속이므로 두 줄로 둔다.
3. 대시보드의 범위 차이를 정한다. 지금은 DB가 돌려준 새 참여를 앱의 반 집합으로 다시 거른다(`makeup-upcoming.ts:97`). 그래서 (가) 담당 반이 없는 배정 강사는 자기가 맡은 보강이 카드에 안 뜨고, (나) 출결 반이 없는 참여는 누구에게도 안 뜬다. 각각 "보인다(어떤 표기로)" 또는 "이번 범위 밖(일정 보기에서 본다)" 중 하나를 적는다.
4. "시간표는 native 예약의 legacy 반영을 유지한다"에 한계를 적는다: 투영 행이 없는 참여(출결 반을 나중에 정한 것, 원수업일 = 보강일)는 시간표 보강 탭에 없다(`0346c:145-150`).

### P1-D. 메모 정책을 서버에서 강제하고 범위를 정한다

근거: 메모 필수는 지금 HTML `required`뿐이다(`intake-form.tsx:54`). 서버 액션 스키마(`schemas.ts:52`)와 SQL(`0346a:153`)은 요구하지 않는다. 계획의 "예정 결석·휴강·추가 지도는 기존 메모 요건 유지"는 지금도 화면에만 있는 요건이다. "일반 결석 접수의 메모는 선택"은 출결 근거가 없는 수동 결석 접수까지 포함하는지 불분명하다 — 포함하면 근거도 설명도 없는 건이 승인 대기에 선다.

계획에 넣을 문장: 메모 선택은 `source_kind = attendance`이고 사유가 결석일 때만이다. 수동 접수는 사유와 무관하게 메모 필수다. 이 규칙을 서버 액션의 `missingKeys("intake")`에 넣고 단위 시험으로 고정한다. DB는 바꾸지 않는다고 적는다.

### P1-E. 진입·복귀·embed를 기존 부품으로 정한다

근거: 계획은 "안전한 내부 return 경로"라고만 적었다. 이 앱은 창(iframe)과 원래 화면이 별도 문서이고, "새 X" 진입의 기본은 autoClose 창이며(`open-window-button.tsx:14-47`), 보강 화면의 기존 `back` 값은 필터만 담고 URL로 쓰지 않는다(`list-navigation.ts:17-22`). Next 문서도 믿을 수 없는 URL을 `router.push`에 넘기지 말라고 한다.

계획에 넣을 문장:
1. 복귀 값은 URL이 아니다. 허용된 출처 키(`attendance`·`onescreen`)와 형식이 검증된 값(반 id·날짜·학생 id)만 받고, 목적지는 서버가 다시 만든다. 그 밖은 버리고 보강 상세로 간다.
2. 창 모드에서는 접수를 기존 창 열기 부품으로 autoClose 창에 연다(원래 창은 그대로 남는다). 단일 화면 방식에서만 1의 복귀를 쓴다.
3. 원래 화면의 갱신은 기존 `publishMutation` 신호로 한다. 창 안 이동은 `withEmbed`·`EmbedLink`를 쓴다.
4. 강사뷰(원스크린 미니셸)에서 `/makeups/new`가 실제로 열리는지 구현 전에 확인한다(아래 §6의 미확인 항목).
5. 강사뷰에 새로 넣는 문구는 화면 언어(한국어/English) 양쪽을 낸다. 일반 지점 화면 문구에 내부 역할 이름을 쓰지 않는다.

### P1-F. 일정 RPC 사양의 구멍을 메운다

1. **강사·강의실이 없는 줄은 미연결 예약만이 아니다.** 연결한 기존 예약의 회차도 강사·강의실이 없다(`0346i:101-103`, `0343b:16`). '실시 강사 미지정' 표기를 두고, 강사·강의실 필터를 걸었을 때 이 줄들이 빠진다는 것과 그 수를 화면에 보인다(조용히 빠지면 요약과 목록이 어긋난다).
2. **과목 범위.** 미연결 기존 예약은 영어에도 있고 대시보드·시간표에 뜬다. 후보·일정 조회는 수학만 본다. 일정 보기 제목과 설명에 "수학"을 적고, 대시보드 '보강예정'(전 과목)과 숫자가 같다고 주장하지 않는다. 수용 기준 6의 "실제 count 일치"는 **어느 화면끼리** 같아야 하는지 이름으로 적는다.
3. **강사 범위.** 기존 예약 줄의 범위를 DB의 오늘 기준 담당 반으로 할지 앱의 이번 주 반 집합으로 할지 하나로 정한다. 일정 RPC는 DB 범위를 쓰고, 대시보드와 다를 수 있는 경우(주 중 담당 변경)를 적는다.
4. **지점 격리.** 기존 예약의 FK는 지점을 묶지 않는다. 후보 조회처럼 학생·반을 이 지점 것으로 다시 조인한다(`0348e:69-71`).
5. **분량.** 줄마다 예정 분·실제 분·인정 분을 보인다. 여러 건에 나눈 분량은 범위 안 건만 보인다(참여 조회의 기존 방식, `0348c:67-71`).
6. **이력 줄.** 취소·변경된 참여는 기본으로 빼고 '이력 포함'을 켰을 때만 보인다고 적는다(같은 약속이 옛 줄·새 줄 두 번 세지지 않게).
7. **기간 밖 미기록.** 조회 기간(최대 31일) 밖의 '지난 예약·기록 확인 필요'는 일정에 안 보인다. 그 수를 따로 보이거나, 케이스 목록의 '실시 기록 필요'가 그 역할을 한다고 적는다.
8. **구 스키마.** 일정 RPC가 없으면 일정 보기만 "DB 설정 적용 후 사용"으로 뜨고, 기존 업무 목록은 그대로 열린다. 두 조회를 한 번에 묶어 한쪽 실패가 페이지를 죽이지 않게 한다.
9. **업무 담당자.** 한 참여에 건이 여럿이면 담당자도 여럿이다. 범위 안 건의 담당자를 모두 보인다고 적는다.

### P1-G. 배포·되돌리기·성능

1. 참여 조회는 출결 저장마다 불리는 함수다. 바꾼 뒤 로그인 역할(RLS 적용 역할)로 실행 계획을 재고, 바꾸기 전과 비교한 값을 남긴다. 진행 칸은 요청한 호출에서만 계산한다(P0-A 2).
2. 되돌리기 SQL을 적는다: 0348c·0348e·0346a를 다시 실행하면 이전 정의로 돌아간다는 것과, 새 파일 머리에 "앞 파일을 손으로 다시 실행했으면 이 파일도 다시 실행한다"를 넣는다(0350b·0350e의 선례).
3. 새 마이그레이션 끝에 `makeup_private` 전체 권한 회수 문과 스키마 새로 고침 알림을 넣는다(기존 파일의 관례).
4. 번호는 병합 시점에 다음 빈 번호로 정한다. `tests/makeup-db`의 실행 순서와 경로 참조를 함께 고친다.
5. 적용은 `db push`가 아니라 파일 단위 실행이다(계획의 "전체 db push를 피한다"를 이 표현으로 고정).

### P1-H. 수용 기준에 추가할 사례

지금 12개 기준은 방향은 맞지만 위 결함을 잡지 못한다. 아래를 번호를 붙여 넣는다.

1. 구 스키마 + 새 앱, 새 스키마 + 구 앱 각각에서: 수학 출결 저장, 출결 이행 훅, 보강 보고서 저장, 원스크린 명단, 대시보드 카드, 학생 예정 배너가 동작한다. 구 스키마에서 새 참여 줄은 '확인 필요'이고 0건·완료로 보이지 않는다.
2. 노쇼 → 왔다로 정정 → 초안: '실시 기록·보완 필요'다('인정 정정됨'이 아니다).
3. 인정 반전: 일정은 '인정 정정됨 · 실시 기록 다시 필요', 케이스 목록은 '실시 기록 필요' — 같은 참여다. 다시 기록 → 제출 → **다른** 관리자 검토 → '검토 완료'. 그 전후로 출결 행·시수·급여·청구 조회 결과가 같다.
4. 0분 인정으로 검토: '검토 완료(인정 0분)', 예정 아님, 남은 의무는 케이스에 남는다.
5. `done`인 기존 예약을 연결: 대시보드 '지남'이 늘지 않는다. '기존 완료 근거 확인'으로 보이고 대사에 `legacy_done_review`가 있다. 이행 이력 수 −1, 연결 필요 수 변화 없음.
6. `reserved`인 기존 예약을 연결: 연결 필요 −1, 대시보드·학생 예정·일정에서 한 줄.
7. 같은 날 미연결 기존 예약 + 새 참여(`legacy_multi_same_day`): 두 줄, 합치지 않는다.
8. 출결 반 없는 참여: 일정에 '출결 반 확인 필요'로 보인다. 반을 정한 뒤에도 시간표 보강 탭에는 없음을 기록한다.
9. 연결한 기존 예약의 회차: '실시 강사 미지정'. 강사 필터를 걸면 빠지고 그 수가 보인다.
10. 담당 반 0개인 배정 강사: 일정에서 자기 참여가 보인다. 대시보드는 P1-C 3에서 정한 대로다.
11. 열어 둔 탭에서 접수: 화면을 연 뒤 출결이 출석으로 정정되면 명령이 거절한다. 정정 전의 옛 행 id로 접수하면 거절한다. 출석인 날의 수동 접수는 건이 생기고 `source_conflict`가 바로 열려 있다.
12. 범위 강사: 연결 버튼·링크가 어디에도 없다. 직접 호출하면 권한 거절 문구가 뜬다.
13. 모드 on / draining / off 각각에서: 출석부·강사뷰의 접수 진입, 기존 예약 저장 뒤 연결 진입, 일정 읽기, 연결 필요 수, 대시보드 카드.
14. 낯선 참여 상태값·낯선 실시 기록 상태값: '확인 필요'(예약으로 보이지 않는다).
15. 수동 결석 접수를 메모 없이 서버 액션에 직접 보내면 거절된다. 출결 근거 결석 접수는 메모 없이 저장된다.
16. 복귀 값에 외부 주소·`//`·`javascript:`·허용 밖 경로를 넣으면 버리고 보강 상세로 간다. 창 안에서는 embed가 유지된다.

## 4. 코디네이터 추가 점검 4건에 대한 답

| 점검 | 소스로 뒷받침되는가 | 필수인가 | 반영 위치 |
| --- | --- | --- | --- |
| (1) 연결된 기존 예약을 먼저 누르고 새 참여 판정 | 부분적으로 그렇다. 우선 규칙은 필요하다. 다만 "반영 지연" 전제는 틀리다 — 예약 행은 명령과 같은 트랜잭션에서 바뀐다. 실제로 어긋나는 경우는 **완료된 예약을 연결한 참여**(예약 `done`, 참여 `unknown`)다. `released` 연결은 예약 행이 삭제돼 남는 줄이 없다 | 필수 | P0-B 2, P1-C |

## 5. 권고 (승인 조건 아님)

- 계획 P0의 "`session_state`, `classroom_id`를 추가한다"는 사실과 다르다. SQL은 이미 반환하고 TypeScript가 버린다. 실제로 새로 필요한 것은 실시 기록 상태, 인정 분 합, 반전 인정 유무, 연결된 기존 예약의 상태, 서버의 오늘이다. 문장을 바로잡으면 마이그레이션 범위가 분명해진다.
- 진행 칸은 참여마다 상관 서브쿼리를 여러 개 두지 말고 살아 있는 실시 기록 한 줄을 lateral 조인으로 읽는다.
- P2에서 원결석에 미연결 기존 예약이 이미 있으면 강사는 연결할 수 없다. "이 결석에는 기존 보강 예약이 있습니다 — 관리자가 연결합니다" 안내를 끝 상태로 정해 둔다.
- 기본값의 "후보가 정확히 하나"는 검색어 없이 조회한 `total = 1`로 판정한다고 적는다(선택지 조회가 `total`을 준다).
- 대시보드 팝업의 "자동 이행 안내" 문구는 연결된 줄(검토 절차)과 미연결 줄(출결 저장 시 자동 이행)을 줄 단위로 나눠 적는다.
- 수용 기준 11의 "393개 스키마 체인"은 감사 때의 수치다. 구현 때 다시 세어 적는다.

## 6. 확인한 것과 가정

**소스로 확인한 계획의 주장(맞음)**
- 완료 건이 대시보드에 남는 원인: 기존 예약은 `done`이 빠지지만 새 참여는 `cancelled`만 빠진다.
- 기존 예약은 새 장부에 자동으로 들어오지 않는다. 연결은 명시적 명령이고 승인 대기로 들어간다.
- 명단·출결 문·보고서·영상 숙제는 완료된 참여를 거르지 않는다(`cancelled`만 뺀다). 계획대로 건드리지 않으면 이력은 남는다.
- 접수 SQL은 메모를 요구하지 않는다. 같은 원수업의 동시 접수는 잠금과 유니크로 한 건이 된다.
- 예약·검토·반전·면제는 출결·시수·급여·청구를 쓰지 않는다. 실제 강사는 자기 기록을 검토할 수 없다. 범위 강사는 본인이 맡는 회차만 잡을 수 있다.
- 담당 반이 없는 배정 강사도 참여 조회 범위에 든다(맡은 회차).
- 모드 `draining`은 접수·예약·변경·연결을 거절하고, `off`는 조회까지 거절한다.
- 선택지 조회의 직원 목록은 범위 강사에게 본인만 준다. 관리자에게는 전 직원이므로 "관리자 본인을 실시 강사로 넣지 않는다"는 기본값 규칙이 필요하다.

**확인하지 못한 것(가정)**
- 강사뷰 미니셸·창 안에서 `/makeups/new`가 열리는지. 감사는 강사 계정의 직접 접수를 확인했지만 미니셸 경로 제한은 내가 읽지 않았다.
- 참여 조회 함수를 바꿨을 때의 실제 성능. 측정하지 않았다.
- 운영 DB의 실제 건수(미연결 기존 예약 중 `done`의 비중 등). DB를 읽지 않았다.
- 출석부·원스크린 화면 쪽 진입 버튼을 넣을 정확한 컴포넌트. 계획이 파일을 특정하지 않았고 나도 그 화면 컴포넌트는 읽지 않았다.
- P1-B의 관측 호출을 명령 안에서 불렀을 때의 실제 동작. 소스로는 충돌이 없어 보인다 — 같은 요청의 재전송은 명령 본체에 들어가기 전에 저장된 결과를 돌려주므로(`0347a_makeup_command.sql:46-57`) 관측은 첫 실행에서 한 번만 돈다. 실행해 확인하지는 않았다.
