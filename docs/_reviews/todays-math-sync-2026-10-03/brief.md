# 에이와 오늘의수학 연동 계획 검토 요청

2026-10-03. 사용자 요청은 **Claude와 Grok이 협의한 최종 계획을 먼저 제시하고, 사용자 확인 후 구현**하는 것이다. 이번 작업은 코드 읽기·설계·문서 작성만 허용한다. 제품 코드, SQL 마이그레이션, 운영 DB, 환경변수, 활성화 스위치, 배포는 변경하지 않는다. 다른 에이전트를 추가 실행하지 않는다.

## 사용자 요구사항

1. 에이와 지점의 오늘의수학 활성화를 켜면 대상 선생님 계정을 자동 활성화한다. 없는 계정은 생성하고, 기존 계정은 이메일을 기준으로 매핑한다.
2. 활성화를 끄면 그 지점에 연동된 모든 선생님 계정을 **삭제하지 않고 정지**한다. 자동 생성 계정과 연결한 기존 계정 모두 포함한다. 기존 로그인 세션과 직접 로그인도 차단하고 자료·매핑을 보존한다.
3. 퇴사·복직·반 이동·담당 변경 등 다양한 변경 경로를 빠짐없이 반영한다. 중복·누락·순서 역전·장애 후 재처리도 포함한다.
4. 에이와 로그인 후 바로가기를 누르면 오늘의수학에 자동 로그인되어 자기 반을 볼 수 있어야 한다.
5. 기존 Vercel Pro와 Supabase 안에서 구현한다. 별도 유료 큐·SSO 서비스·상시 서버·새 인프라 설치를 요구하지 않는다. 사용량 증가와 추가 청구가 전혀 없다고 보장하지 않는다.
6. 정상 상태에서 수초 내 반영을 목표로 하되, 측정하지 않은 지연을 보장값처럼 쓰지 않는다. 웹훅 수신·권한 차단·열린 화면 갱신·장애 복구 시간을 구분한다.
7. 계정 보호 및 기존 수동 정지를 유지한다. ON 재실행으로 퇴사자·수동 정지 계정·과거 거절/삭제 계정을 임의로 되살리지 않는다.

## 조정자의 초기 설계 가설

검토에서 수정 가능하다. 동의만 하지 말고 실제 코드와 실패 사례로 반박하라.

- 에이와를 재직·지점 계약·반/수강 관계의 원본으로 한다. 오늘의수학의 개인 자료, 비밀번호, 수동 정지, 검수 권한 등은 별도 소유 필드로 둔다.
- 여러 UI 액션에 개별 HTTP 호출만 붙이지 않는다. 커밋과 함께 내구성 있는 outbox/변경 버전을 기록해 관리자 액션·QR 가입·수입 스크립트·크론·직접 SQL의 실제 변경도 포착한다.
- 웹훅은 상태 변경 알림이며 최소 식별자만 전송한다. 대상은 인증된 현재 상태/일관된 스냅샷을 읽어 멱등 반영한다. 전달 완료와 적용 완료를 구분하고 재시도·재대조·충돌 기록을 남긴다.
- 동일 이벤트 중복과 오래된 상태의 역전 방지, 지점별 직렬화와 원본 버전 재검증이 필요하다. OFF/퇴사 후 늦게 도착한 ON/입사 이벤트가 계정을 복구하지 못해야 한다.
- 연동 정지는 별도 원인으로 기록하고 유효 접근 권한을 계산한다. 단순히 `suspendedAt = null`로 복원하지 않는다. 에이와에서 삭제되어도 대상은 정지/보관, 삭제 전파 금지.
- 지점 OFF 때도 정지 알림과 제어 상태 API는 동작해야 한다(기존 데이터 API의 503만으로는 정지 전파가 안 됨).
- 사용자 UUID+지점 ID 연결, 최초 이메일 매핑 확인, SSO 전 현재 자격 확인, 짧은 1회용 코드 또는 token 재사용 방지, 안전한 고정 redirect, 비밀번호 없는 자동 발급 계정 지원을 계획한다.
- 전수 대조는 페이지 실패를 삭제로 오인하지 않도록 완전한 스냅샷 이후에만 누락 판단한다. 대조의 체크포인트/해시에는 직접 SQL·예약 효력일·표에서 삭제된 행도 포함되어야 한다.
- 보호 우선: 접근 취소는 웹훅 정상 속도와 별도로 지연 상한을 설계한다. 원본 장애 시 허용할 최대 자격 유효기간과 만료 후 차단의 가용성 비용을 명시한다.
- 배포는 additive schema → 수신/검증 → 발신 관찰 → dry-run 매핑/대조 → 승인된 지점 canary → OFF/퇴사/재시도 실측 → 확대 순서. 롤백이 정지를 해제하거나 기존 자료를 삭제하지 않아야 한다.

## 검토 결과에 반드시 포함할 것

1. 현재 코드 근거(경로·함수)와 빠진 기능.
2. 사건별 기대 결과와 변경 포착 위치. 예정 변경/취소, 대강·인수인계, 다중 반·다중 담당/지점 충돌, 삭제/복구, 회원 이메일 변경 포함.
3. 결정해야 할 데이터 소유권·불변 조건·실패 정책. 추천 기본값과 근거를 적고 사용자 결정이 필요한 쟁점은 최소화한다.
4. 현실적인 단계별 구현 범위·의존성·테스트 수용 조건·배포/롤백·상태 관찰.
5. 기존 Pro 자원 내 설계와 지연 측정 계획. 외부 서비스 강제 도입이나 무조건 무료/즉시/정확히 한 번 전달 보장 금지.
6. 첫 검토의 결론은 승인 가능한 계획으로 만들기 위해 반드시 해결할 차단점과 권고를 구분한다. 이후 통합안 재검토를 요청할 수 있다.
