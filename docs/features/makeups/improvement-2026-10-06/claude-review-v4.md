경고 방식에서는 겹친 경우에 승인이 먼저 이뤄지고 관리자는 그 직후에 경고를 본다. 이것은 사람이 한 승인이고 시스템이 자동으로 권리를 준 것이 아니다. 확인 항목이 열려 있는 동안 그 건은 닫히지 않는다. 119행이 "승인 성공을 근거 문제 없음으로 표현하지 않는다"고 적은 것이 필요한 조건이고, 들어 있다.

## 5. 범위·호환·안전의 경계

이 계획이 지키는 것으로 확인한 경계:

- 수학 시범 범위만. 영어의 기존 보강·출결은 그대로다.
- 자동 권리 발급·자동 인정·자동 이관·자동 승인·기한 소멸·환불/청구·학부모 자동 안내가 없다.
- 출결·시수·급여·청구 산식을 쓰거나 바꾸지 않는다. 출결 저장 경로(0349b)는 정의가 바뀌지 않는다.
- 독립 검토(실제 강사는 자기 기록을 검토할 수 없음)와 분량 승인 정책은 그대로다. 승인에 더해지는 것은 관측과 경고뿐이고 거절 조건은 늘지 않는다.
- 쓰기 쪽 변경은 두 명령에 한정된다: 접수의 거절 조건 강화와 관측 호출, 승인의 관측과 경고. 나머지는 읽기 계약과 화면이다.
- 구 스키마와 새 앱, 새 스키마와 구 앱 양쪽에서 동작해야 한다는 것을 전제로 삼는다(적용 순서에 기대지 않는다).
- 모드 on / draining / off의 기존 계약을 따른다. 설정을 자동으로 바꾸지 않는다.
- 일반 지점 화면 문구에 내부 역할 이름을 쓰지 않는다. 원문 코드는 한글 문구로 바꿔 표시한다.

## 6. 권고 (승인 조건 아님 — 구현 때 반영하면 좋은 것)

1. 117행의 "원수업 칸에 닿는 전체 **허용** 대상"에서 "허용"은 빼는 편이 정확하다. 잠금은 행위자의 읽기 범위가 아니라 관측이 실제로 잠그는 집합 전체여야 한다. 승인은 지점 전체 권한자만 하므로 지금은 결과가 같다.
2. 관측 함수가 보는 "출석인 날"은 그날 그 반의 **가장 나중 행**이다(`0349b:32-35`). 접수 검증과 후보 조회는 "유효한 시수 칸이 하나라도 있는 날"이다. 교시가 둘 이상인 날에는 둘이 다를 수 있다. 0349b를 바꾸지 않기로 했으므로 이 차이를 검증 기록에 적고, 기준 11의 수동 접수 사례는 관측 함수의 기준으로 판정한다.
3. 열린 source_conflict는 자격 거절도 막는다(`0346b:100`). 출석인 날에 수동 접수한 건은 확인 항목을 처리한 뒤에야 거절할 수 있다. 기존 동작이지만 접수 때 바로 열리게 되므로 더 자주 만난다. 화면 안내에 넣는다.
4. `/makeups`의 업무 목록과 새 일정은 로그인 계정의 DB 범위를 따른다(강사뷰 축이 아니다). 기존 목록과 같은 계약이라는 것을 일정 화면 설명이나 검증 기록에 적는다.
5. 승인 화면에 원수업 칸의 지금 출결 상태를 미리 보여 주면 겹친 경우를 승인 전에 알아챌 수 있다. 필수는 아니다.
6. 잠글 집합을 미리 계산한 뒤 관측이 다시 계산하는 사이에 새 건이 생기면 늦게 잠기는 행이 있을 수 있다. 명령 쪽의 재시도 가능한 실패이고 출결 저장에는 닿지 않는다. 병행 시험 관문에서 본다.
