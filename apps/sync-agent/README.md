## 운영자 사용

1. 웹 `학원 설정 → 연동 → 연동 PC`에서 설치 파일을 받고 12자리 연결 코드를 발급한다. 연결 코드는 15분 동안 한 번 사용할 수 있다.
2. 설치한 `AYWA 연동`을 열어 코드를 입력하고 화면의 지점 이름을 확인한다. 앱만 설치하거나 지점만 연결해서는 업무가 시작되지 않는다.
3. 기존 워커가 현재 작업을 마치고 종료하면 **기존 설정·기록 가져오기**로 기존 `.env.local`이 있는 폴더를 선택한다. 지점이 다른 설정은 거부한다. 기존 폴더는 보존하고, 새 폴더에 이미 있는 처리 기록은 덮어쓰지 않는다.
4. 계정을 확인하고 **이 PC에서 연동 시작**을 누른다. 알려진 기존 예약 작업을 끄고, 남은 구 실행과 서버의 최근 활동이 없는지 확인한다. 이전 활동이 감지되면 3분 뒤 다시 확인한다.
5. 웹과 PC 양쪽에서 켜 둔 연동만 실행된다. 실제 발송·자동 동기화·답글 모드 등의 기존 업무 설정도 계속 적용된다. 메이크에듀의 정기 동기화는 06:00/18:00, 접속 점검은 08:30 KST다.
6. **makeedu 다시 로그인**(2026-11-06 · 다음 판부터): makeedu가 자동 로그인에 사람 확인(reCAPTCHA)을 요구하면 자동 동기화는 저장된 로그인 상태(세션)를 재사용하고, 세션이 끊기면 ID/PW로 한 번만 시도한 뒤 **자동 로그인을 멈춘다**(같은 계정으로 다시 시도하지 않는다 · 메이크에듀 칸에 '자동 로그인 멈춤 · 사유'가 뜨고 원장 벨이 하루 한 번 울린다). 메이크에듀 칸의 **makeedu 다시 로그인**을 누르면 보이는 브라우저 창이 login.do를 연다 — 아이디는 미리 채워져 있고(관리 코드로 설정을 연 10분 안이면 비밀번호도), **로그인 버튼과 사람 확인은 사람이 누른다**. 재인증 화면이 나오면 그 창에서 거기까지 마친다. 5분 안에 메인 화면에 닿으면 그 세션을 저장하고 사람 확인·재인증 멈춤을 풀며 "다시 로그인되었습니다 — aywa의 '지금 동기화'로 바로 가져올 수 있습니다"가 뜬다. 창을 닫거나 5분이 넘으면 실패 사유가 뜨고 멈춤은 그대로다. **비밀번호 계열(로그인 정보·인증정보가 올바르지 않음)·계정 계열(미인증·호출정보·요금제·사용 기한·알 수 없는 응답) 멈춤은 다시 로그인으로 풀리지 않는다** — 관리 코드로 설정을 연 뒤 '연동 계정'에 메이크에듀 **비밀번호**를 저장하면(같은 값이어도 · 계정 계열은 makeedu에서 해결한 뒤) 풀린다(아이디만 저장해서는 안 풀린다 · 그동안 저장 세션은 계속 쓴다 · 이 멈춤 중에는 사람 창에 저장 비밀번호를 미리 채우지 않는다). 사람 창의 성공은 주소가 아니라 main.do 로그인 확인으로 정한다(로그인 화면을 벗어나는 탐색마다 한 번 · 5분 동안만). 저장 직후 정기 실행과 같은 headless로 그 세션을 한 번 더 점검해, 거절되면 "자동 실행에서 그 세션을 쓸 수 없습니다 — makeedu 문의"로 끝내고 멈춤을 풀지 않는다. 제출마다 캡차 토큰 유무·`loginBrowserRuntime` 값만 `makeedu.log`에 남기고(본문·토큰·비밀번호는 남기지 않음), 캡차를 풀었는데도 다시 사람 확인을 요구하면 "makeedu가 이 창의 로그인을 받지 않습니다 — makeedu 문의"로 바로 끝낸다. 📌 새 판으로 업데이트한 직후 바로 'makeedu 다시 로그인'을 누르면 자동 시도 없이 세션이 생긴다. 세션을 깨우는 타이머는 없다(원장 결정 — 하루 1번이면 된다): 08:30 접속 점검과 06:00/18:00 정기 동기화가 저장 세션을 먼저 쓰며 확인·갱신하고, 08:30 점검은 매번 `makeedu.log`에 '세션 살아 있음/끊김 — 로그인 후 N시간' 한 줄을, 끊긴 걸 처음 알면 '세션 수명 — 세션 저장 후 N시간' 한 줄을 남긴다.

PC 설정은 웹에서 발급한 별도 12자리 **관리 코드**로 10분 동안 연다. Windows 로그인 시 실행, 트레이 시작, 전체/연동별 일시 중지와 자동 다운로드를 설정한다. **1.0.3부터 업데이트 확인·적용·예약·취소에는 관리 코드가 필요 없다.** 웹에서 업데이트를 허용한 연결 PC에서 새 버전마다 **지금 업데이트** 또는 **날짜·시간 지정**을 선택한다. 계정·연동 옵션 변경의 잠금은 유지한다. 창 닫기는 트레이 유지이며 **작업을 마치고 종료**가 실제 종료다.

웹의 **실행 로그**에서 한국시간 날짜·연동·오류 필터로 최근 기록을 보고 이전 100건으로 이동한다. PC의 **로그 폴더 열기**는 `%LOCALAPPDATA%\AYWA\Sync\tenants\<tenant-id>\log\YYYY-MM-DD\`를 연다. `app.log`, `classnote.log`, `makeedu.log`의 날짜와 행 시각은 KST다. 상세 로그는 PC에 두고 웹에는 고정된 처리 단계·오류 요약만 보낸다. 자격증명은 마스킹하고 파일은 20MiB마다 나눈다. 예전 상태 폴더의 로그를 삭제하거나 새 로그로 덮지 않는다.

Google 계정과 영상 저장 폴더는 기존 웹의 `숙제영상 드라이브`에서 관리한다. 기존 PC의 Google 환경 설정은 가져오기에서 허용된 항목만 이전한다. gcloud 인증을 쓰는 PC는 같은 Windows 사용자와 설치된 gcloud가 필요하다. 과거 Drive 영상을 옮기거나 폴더를 바꾸지 않는다.

PC 교체는 웹에서 현재 PC 연결 해제 → 실행 만료 확인 → 새 코드 발급 순서다. 복사 설치나 같은 PC 중복 실행도 동시에 업무를 맡을 수 없다. 새 기기에 다른 지점의 계정·작업 기록을 자동으로 넘기지 않는다.

## 실행·저장·업데이트

- 안정된 진입점 `AywaSync.exe`(실행기)가 `AywaSyncRuntime.exe`(본체)를 실행한다. 각 업무 프로세스와 브라우저·영상 도구는 Windows Job Object 안에서 실행된다.
- 🔴 실행기는 앱 안 업데이트가 받지 않는다(본체만 `versions/<순번>`). 1.0.13부터 본체가 설치 폴더 실행기를 자기 버전의 더 높은 판으로 바꾸고(`lib/launcher.cjs` · 판 = `native/Bootstrap.cs`의 `LauncherVersion` = 포장 폴더 `aywa-launcher.json`), 옛 판 실행기가 띄운 본체는 업데이트 때 새 실행기(`--handover` — 앞 실행기의 잠금이 풀리길 120초 기다린다)를 띄우고 0으로 끝낸다. **실행기 동작을 바꾸면 `LauncherVersion`을 올린다** — 안 올리면 현장 PC 실행기가 안 바뀐다.
- `%LOCALAPPDATA%\AYWA\Sync`에 연결·설정·기기별 로그·지점별 작업 상태를 둔다. 계정/기기 비밀은 Windows DPAPI로 암호화한다. 재설치·업데이트가 지점 상태를 초기화하지 않는다.
- 서버 실행 임대는 90초이고 20초마다 갱신한다. PC는 단조 시계와 10초 여유를 사용한다. 갱신 실패·절전·임대 소실은 프로세스 트리 종료로 이어진다. 정상 중지·업데이트는 작업 사이에서 멈추고 진행 영상·첨부 복구를 기다린다.
- 새 정식 버전은 6시간 간격으로 확인하고 자동으로 다운로드한다. 다운로드 완료 알림과 앱 화면에서 그 버전에 한해 **지금 업데이트** 또는 **날짜·시간 지정**을 선택해야 적용된다. 선택이 없으면 계속 기다린다. 기존 버전의 자동 적용 시간대 설정은 다운로드 설정으로만 이전한다.
- 1.0.3부터 다운로드 MB와 압축 해제·검증 파일 수의 진행률을 구분한다. 수신이 90초 멈추면 중단하며 전체 다운로드는 20분으로 제한한다. 실패 이유는 고정 문구로 앱과 웹 로그에 남기고 **새 버전 확인**으로 재시도한다. 진행 중에는 중복 다운로드·적용을 막는다. 대기 상태에는 다운로드 중이라는 안내를 표시하지 않는다.
- 날짜·시간은 PC 현지 시간으로 입력하고 절대 시각으로 저장한다. 예약 변경·취소와 현재 작업 완료 대기 중 취소를 지원한다. 예정 시간부터 현재 작업을 마치고 적용한다. 폴링 지연은 최대 2분 허용하지만, PC 종료·절전·연결 끊김으로 놓친 예약은 재접속 직후 실행하지 않는다. 예약이 미래라면 재시작 후 유지하고, 적용 대기 중 재시작한 경우에는 다시 선택해야 한다.
- 예약은 버전 순번과 버전에 묶인다. 더 새 버전이 준비되면 이전 선택을 재사용하지 않는다. 웹에서 업데이트를 끄면 적용하지 않는다. 다운로드가 끝난 버전도 다음 새 버전 확인을 계속하며 RSA 서명, 버전 순번, 만료일, 전체 ZIP과 각 파일의 SHA-256, 파일 경로를 검증한다. 적용 직전에도 서명·만료·실패 격리를 다시 확인한다.
- 새 버전 시작은 최대 180초 동안 확인한다. 실패하면 이전 버전으로 되돌리고 실패한 순번을 격리한다. 롤백은 처리한 업무 데이터를 되돌리지 않는다.
- 웹에는 지점에 귀속된 구조화 로그를 보낸다. 학생 이름·연락처·글 본문·비밀번호·원시 stdout은 보내지 않는다. 웹 로그는 30일, 로컬 전송 대기열은 최대 1,000건이다. 기존 업무 로그의 보관 설정은 가져온 값을 유지한다.
- 새 EXE에 DB 접속 비밀번호, 서비스 키, 공용 내부 인증키를 넣지 않는다. 정확히 등록된 SQL 템플릿과 이름 있는 서버 처리만 허용하며 DB 역할의 RLS가 지점 경계를 강제한다.

정상 완료를 기다리는 중에 OS가 종료되거나 전원이 끊길 수 있다. 이 경우 기존 업무의 큐·잠금·외부 중복 대조·영상 재개 상태로 복구한다. 이미 외부 서비스가 접수한 요청을 되돌렸다고 표시하지 않는다.

## 빌드

Windows x64, Node/npm, .NET Framework C# 컴파일러가 필요하다. 루트 저장소 의존성과 이 디렉터리의 의존성을 먼저 설치한다.

```powershell
cd F:\eywa\apps\sync-agent
npm ci
# FFmpeg의 ffmpeg.exe와 ffprobe.exe가 들어 있는 디렉터리 — 🔴 essentials 빌드(각 약 105MB · 1.0.8·1.0.9와 같은 9.0.2).
# full 빌드(각 약 211MB · WinGet Gyan.FFmpeg)를 쓰면 zip이 600MiB 버킷 제한을 넘어 게시(--apply)에서 멈춘다(2026-10-29).
$env:EYWA_AGENT_FFMPEG_DIR = 'C:\tools\ffmpeg\bin'
$env:EYWA_AGENT_SEQUENCE = '18'
npm run prepare:runtime
npm test
npm run package
node test/package-audit.cjs
node test/ui-smoke.cjs --packaged
node test/bundled-runtime.cjs
```

`prepare:runtime`은 기존 실행기에서 125개 소스를 추적해 복사하고, 직접 DB 클라이언트를 서버 어댑터로 바꾸며, 고정 버전 의존성·Chromium·FFmpeg와 네이티브 실행기를 준비한다. 새 소스를 추가하면 SQL 카탈로그와 필요한 RLS 표 목록도 검토한다. `after-pack.cjs`는 패키저가 생략하는 중첩 의존성을 명시적으로 포함한다. `bundled-runtime.cjs`는 업데이트 테스트(`test/update.test.cjs`)를 **포장된 Electron 실행기 안에서도** 돌린다 — 업데이트는 Electron 안에서 돌고 그곳의 `fs`는 `*.asar`를 폴더로 다뤄서, 일반 node 테스트만으로는 '모든 PC 업데이트가 압축 해제에서 실패'하는 버그(1.0.1~1.0.4)가 안 보였다.

서명 개인키 기본 위치는 `%LOCALAPPDATA%\AYWA\ReleaseKeys\sync-agent-private.pem`이다. **저장소나 배포 묶음에 넣지 말고 별도로 백업한다.** 다른 빌드 PC에서는 `EYWA_AGENT_SIGNING_KEY_FILE`로 같은 키를 지정한다. 키를 새로 생성하면 이미 설치된 앱은 새 서명을 신뢰하지 않는다. ⚠️ `prepare:runtime`은 지정한 키 파일이 **없으면 새 키를 만든다** — 실행 전에 키 파일이 있는지 먼저 확인한다.

다음 버전은 `package.json` 버전과 `EYWA_AGENT_SEQUENCE`를 모두 높인다. 같은 순번의 게시 파일을 교체하지 않는다. 현재 설치기는 Windows Authenticode 인증서로 서명되지 않았다. 자체 RSA 업데이트 서명과 Windows 게시자 서명은 별개다.

## 서버 반영과 최초 게시

1·2번 웹/API와 DB 배포는 2026-10-08, 1.0.1 최초 게시와 실제 PC 전환 및 1.0.2·1.0.3 게시는 2026-10-09, 1.0.4·1.0.5 게시는 2026-10-15, 1.0.6·1.0.7 게시는 2026-10-16, 1.0.8 게시는 2026-10-21, 1.0.9 게시는 2026-10-29, 1.0.10·1.0.11 게시는 2026-11-02, 1.0.12·1.0.13 게시는 2026-11-04 진행했다(1.0.12는 같은 날 회수). 1.0.14 게시는 2026-11-04 저녁 진행했다. 1.0.15 게시는 2026-11-05 진행했다. 1.0.16 게시는 2026-11-05 저녁 진행했다. 이미 연결된 PC의 새 버전 적용은 PC 앱에서 버전별로 선택한다. 구버전에서 다운로드 준비에 실패하면 같은 Windows 계정으로 최신 설치 파일을 덮어 설치할 수 있다. 기존 연결·계정·작업 상태는 보존한다.

1. 기존 DB 백업/배포 절차로 다음 마이그레이션을 순서대로 반영한다: `0399a`, `0400a`, `0401a`, `0402a`, `0403a`, `0406a`, `0407a`. 새로운 제어 표·역할 정책·기존 정책 helper 권한과 로그 인덱스이며 현재 시간표·학생·수납을 초기화하지 않는다.
2. 웹/API를 배포한다. 서버 `DATABASE_URL`의 역할은 새 `eywa_sync_agent` 역할로 전환할 수 있어야 한다. `SYNC_AGENT_CODE_SECRET`은 서버에만 두는 안정된 난수 비밀이다. 미설정 시 기존 서버 서비스 키를 사용하므로 가능하면 별도 비밀을 지정한다.
3. 변경 불가능한 HTTPS 파일 경로를 정하고 아래와 같이 배포 묶음을 만든다. 현재 게시한 경로는 서비스 저장소의 `sync-agent-releases/18/`이다. 다음 릴리스는 새 순번의 경로를 사용한다. 실제 업로드 위치가 다르면 새 공개 전에 URL과 서명을 다시 만든다.

```powershell
$env:EYWA_AGENT_RELEASE_BASE_URL = 'https://YOUR-STORAGE-HOST/path/18/'
node release.cjs
node test/release-acceptance.cjs
node register-release.cjs
```

4. 생성된 `dist/release/18/AywaSync-Setup-1.0.16.exe`, `AywaSync-1.0.16.zip`, `release.json`, `checksums.json`을 해당 HTTPS 경로에 게시한다. 현재 Supabase 경로에서는 `node --env-file=../../.env.local publish-release.cjs`로 검증 계획을 확인한 뒤 `--apply`를 추가하면 전용 공개 버킷에 TUS 방식으로 올린다. 서명·로컬 해시·프로젝트 주소를 먼저 검사하고 같은 경로의 다른 파일은 덮어쓰지 않는다. 중단된 업로드 상태는 저장소의 무시된 `work/sync-agent-publish/`에 둔다. EXE/ZIP은 리다이렉트 없이 200 응답이어야 한다. 현재 전용 버킷 제한은 600MiB이며, 전역 제한이 그 이상이어야 한다. 기존 첨부파일 버킷의 제한은 변경하지 않는다.
5. `node register-release.cjs --verify-remote`로 게시된 EXE와 ZIP 전체 해시를 확인한다. 검증된 버전·순번·명세·서명·설치 링크로 등록 SQL 파일을 준비하고, Supabase CLI의 `db query --file`로 같은 앱 프로젝트의 정식 릴리스 행을 등록한다. 등록은 표 잠금 안에서 순번·버전 재사용을 거부해야 한다. 등록 후 웹 다운로드와 자동 업데이트 조회에 나타난다. 기본 `register-release.cjs` 실행은 로컬 검증뿐이다.
6. 최초 실제 연동 PC에서 설정/기록을 가져오고 구 워커 종료를 확인한 뒤 전환한다. 실제 외부 계정·IP 허용·Drive 권한·재시작을 확인한다. 이전 PC의 오래된 예약 작업과 공유 DB 자격증명 사용처를 정리한 후 구 설치를 제거한다.

구형 워커는 새 프로토콜을 모르므로 서버의 기기 등록만으로 과거에 배포한 DB 비밀번호를 무효화할 수 없다. 기존 파일과 공유 자격증명을 그대로 둔 채 “어떤 구 PC도 다시 실행할 수 없다”고 보장하지 않는다.

## 검사

- `npm test`: 임대 경쟁·만료, 브로커 인증, Windows 자식 프로세스 종료, 서명/압축 파일 검증, 실제 부트스트랩 복구, 기존 설정 이관.
- `node test/controller-smoke.cjs`: 가짜 서버를 사용한 실제 Electron 등록·암호화·중복 실행·연결 해제. 외부 업무는 시작하지 않는다.
- `node test/update-controller.cjs --packaged`: 실제 EXE 화면에서 버전별 예약·취소·즉시 선택, 작업 완료 대기, 실패 후 자동 재시도 금지와 웹 OFF를 검증한다. 외부 서버·계정·실제 설치 적용은 가상 대체한다.
- `node ../../scripts/_sync-agent/control-db-check.cjs`: 명시적으로 라벨이 붙은 로컬 PostgreSQL 시험 컨테이너에서 실제 서버 함수/SQL 검증. 운영 DB를 사용하지 않는다.
- 루트에서 `node scripts/_sync-agent/dryrun.cjs`: 환경변수 제거 및 Node 외부 통신 차단 후 기존 업무 회귀 검사. 전체 저장소 검사나 실제 외부 계정 인수 시험과는 범위가 다르다.

수동 복구·초기 데이터 정리 스크립트는 기존 저장소에 보존되어 있다. 이를 설치 시 자동 실행하거나 PC에서 임의 스크립트를 실행하는 기능은 제공하지 않는다.
