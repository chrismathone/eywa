## 2026-10-19 원생 형제 = 학부모 휴대폰·이름 자동 판정 + 수정 화면에서 지정(0376a)

- 원장 *"학생에게 학부모 이름 또는 전화번호가 일치하는 다른 학생이 있으면 형제로 표시해줄것"* · *"수동 배정도 가능하게 해주고. (수동 이전에 매핑되는 학생 있으면 자동 추천 및 입력)"* · *"프로필에 붙여"*.
- 판정은 [`siblings.ts`](../../src/features/students/siblings.ts) 한 곳 — 학생 상세 '프로필'의 형제 줄 · 학생 수정 화면의 형제 칸 · 저장이 지난다. 자동 판정은 저장하지 않고 볼 때마다 계산한다:
  - 학부모 휴대폰이 같다 → 형제(숫자만 · +82→0 · 휴대폰만 — 콜&상담 같은 학생 판정과 같은 열쇠 `phoneKeyOf`)
  - 학부모 이름이 같고 연락처가 부딪히지 않는다(한쪽이라도 휴대폰이 없다) → 형제
  - 🔴 학부모 이름만 같고 휴대폰이 서로 다르면 형제로 치지 않는다 — 수정 화면에 '확인 후보'로만(눌러야 들어간다). 침산 실측: 이름만 같은 17쌍이 전부 휴대폰이 6~8자리 달랐고 아이 성도 대부분 달랐다(다른 집 학부모의 같은 이름).
  - 🔴 학생 이름이 같으면(동명이인 접미사 A·B 무시) 형제가 아니다 — 같은 아이의 중복 기록(실측 8쌍). 시험용·중복 병합된 원생은 뺀다.
- 사람이 정한 것이 자동 판정보다 앞선다 — 표 `student_siblings`(0376a): `linked=true` 형제로 지정 · `linked=false` 자동 판정을 끈 짝. 수정 화면은 자동 판정을 '자동 추천'으로 미리 넣는다. 🔴 저장은 **화면에서 바꾼 것만** 쓴다(`planSiblingSave`): 더한 원생 = 지정 · 뺀 자동 추천 = '형제 아님'(다시 안 들어온다) · 뺀 지정 = 줄 삭제 · 손대지 않은 자동 추천은 저장하지 않고 계속 자동 판정(연락처를 고치면 따라 바뀐다 — 잘못된 번호로 묶인 짝이 굳지 않는다 · 열어 둔 사이 다른 원생 화면에서 바꾼 짝도 덮지 않는다). 짝은 한 줄이라 어느 쪽 화면에서 저장해도 양쪽에 보인다(형제의 형제까지 잇지는 않는다).
- 프로필 줄은 형제가 있을 때만 · 이름 + 학교학년(재원이 아니면 상태 · 강사 영어 화면은 영어) · 누르면 따로 창. 🔴 원생 표 RLS는 지점 단위라 강사에게도 담당 밖 원생이 읽힌다 — 형제 줄은 **학생 상세를 열 수 있는 형제만**(`canViewStudentDetail` — 상세와 같은 판정). 저장 = 학생 수정 저장과 함께(원생 정보 변경 권한 · 감사로그 `student_siblings_update`) · 형제 저장이 실패해도 학생 저장은 끝내고 알린다.
- 침산 실측(2026-10-19): 원생 826명 중 270명(재원 131명)에게 형제가 붙는다 · 한 원생의 형제 최다 2명 · 확인 후보가 뜨는 원생 27명.

## 2026-10-19 신규 콜&상담 '같은 학생' 판정 = 한 벌 · 이름+보호자 휴대폰도 열쇠 · 새 상담 작성 중 이전 상담 안내

- 원장 *"같은 학생이 상담을 여러번 올 경우 체크할 수 있는 방법 잇는지 확인"* → *"1~2번"*(연락처로도 묶기 · 작성 중 안내).
- 판정은 [`same-person.ts`](../../src/features/enrollment/same-person.ts) 한 곳 — 카드 'N건' 배지 · 상세 '같은 학생의 다른 신규 콜&상담' · 상담 준비 브리프의 이전 접수 · 새 상담 작성 중 안내(`/api/enrollment/prior-consults`)가 모두 이 함수를 지난다(조회는 [`findSamePersonConsultations`](../../src/features/enrollment/server/same-person-query.ts)). 예전엔 세 곳이 따로 적혀 조금씩 달랐다(목록은 이름 띄어쓰기를 무시, 상세는 글자 그대로).
- 열쇠 셋 중 하나라도 같으면 같은 학생(목록에선 이어진 것끼리 한 묶음): ① 연결된 원생 ② 이름+학교+학년(둘 다 비면 열쇠 아님) ③ **이름+보호자 휴대폰**(숫자만 · +82→0 · 01로 시작하는 10~11자리만). ③ 덕분에 해가 바뀌어 학년이 오른 재방문·학교 표기가 다른 접수가 묶인다(침산 실측 206명·448건 → 262명·575건).
- 🔴 **열쇠가 같아도 반대 증거가 있으면 잇지 않는다**([[#132]] 김근우 — 이름·학교·학년이 같아도 보호자 연락처가 다르면 다른 아이): 서로 다른 원생에 연결된 묶음은 어떤 열쇠로도 안 잇고, 이름+학교+학년은 양쪽 휴대폰이 하나도 안 겹치면 안 잇는다(원생 연결은 연락처가 달라도 잇는다 — 보호자 둘이 각자 번호를 적는다). 강한 열쇠부터 잇는다(원생 연결 → 이름+휴대폰 → 이름+학교+학년). 🔴 **애매하면 잇지 않는다** — 한 열쇠에 근거 있는 묶음(원생 연결·휴대폰)이 서로 부딪히면 그 열쇠로는 아무것도 안 잇는다(연락처 없는 접수는 어느 아이 것인지 모른다 · 먼저 본 쪽에 붙이면 두 아이의 상세가 같은 상담을 서로 제 것이라 한다). 판정은 행 순서와 무관하다(카드와 상세가 같은 답). 침산 실측: 이 규칙으로 갈라진 14명 중 대부분은 번호가 6~8자리 다르다(한 자리 오타로 보이는 2건은 갈라진 채 둔다). 같은 숫자만 늘어놓은 번호(`010-0000-0000`)도 열쇠가 아니다.
- 🔴 이름만으로는 묶지 않는다(동명이인 [[#132]]) · 🔴 일반전화(학원 대표번호 등)는 열쇠가 아니다 — 이름 4~6개가 함께 쓰는 번호가 있어 같은 이름의 다른 아이를 묶을 수 있다. 형제자매는 이름이 달라 따로 남는다. 묶음은 **표시만** — 원생 연결·병합은 하지 않는다(병합은 `merge-plan.ts`의 동일인 검증이 이름·학교·과목·날짜로 따로 막는다).
- 작성 중 안내는 이름 + (휴대폰 또는 학교·학년)이 있을 때만 묻는다 · 학교는 저장할 때와 같은 표기로 바꿔 비교 · 연락처는 돌려주지 않는다 · 권한 = 신규 콜&상담 열람 · 건수는 전체(목록은 최근 10건) · 누르면 따로 창(쓰던 작성 창은 그대로).
- 카드 'N건'은 불러온 목록(기간 안) 안에서 센다 · 상세 '다른 상담'은 기간 없이 찾고, 묶음이 원생 연결을 얻으면 그 원생의 상담을 한 번 더 찾는다(이름 표기가 다른 같은 원생).

## 2026-10-15 원생 상태 변경의 개인별 기능 권한

- `permissions.specialAccess.studentStatusManagerIds`는 원생 메뉴 전체 권한과 사무실 DB 역할에 더해 직접 퇴원·휴원·재개·복구, 전체·부분·단일 수강 종료·대기, 퇴원일·예약·취소를 처리할 사람을 지정한다. 원장과 기존 보호 계정의 권한 및 읽기 전용 보호는 유지한다.
- 기존 raw 필드 누락만 기존 방식을 유지한다. 원장이 전용 전환 버튼으로 담당자를 정해 저장하면 명단을 적용하며, 명시 빈 배열·잘못된 값은 권한을 주지 않는다. 신규 지점은 빈 명단이다. 기존 방식인 동안 원생 메뉴 권한을 바꾸려면 먼저 명시 전환해야 한다. 옛 폼의 관련 변경은 거절하고, 무관한 저장은 누락·명단·빈 배열을 보존한다.
- 기본 정보 수정에서 빠진 상태·퇴원일은 보존한다. 별도 자격이 없으면 옛 폼이 보내는 실제 상태·퇴원일 변경도 거절한다. 신규 등록·웹 엑셀의 초기 휴원·퇴원·퇴원일, 웹 시간표 가져오기의 직접 수강 종료도 같은 자격이 필요하다. 반 이동은 휴원 상태를 상속한다.
- 수강 날짜 수정은 기존 독립 자격과 담당 범위를 유지한다(빈 종료일↔날짜 포함). 반 이동·예정 배정 취소·이력 삭제도 기존 권한을 따른다. 수강 직접 삭제 대신 검증 RPC를 쓰며 기존 연결 기록 보호와 감사 스냅샷을 유지한다. SQL의 전용 NOLOGIN/NOBYPASSRLS 실행 역할은 기존 authenticated 테넌트·사무실 RLS를 그대로 통과한다.
- 승인된 퇴원보고서의 요청·작성·승인·최종 적용, 예약 cron·시스템 동기화·반 운영기간 종료는 기존 신뢰 경로를 따른다. 직접 상태 변경 명단을 승인자 명단으로 사용하지 않는다.
