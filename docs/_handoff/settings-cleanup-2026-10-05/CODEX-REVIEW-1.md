## 2. §5의 질문 5개에 대한 답

### Q1. P1-A에 구멍이 있는가? 더 단순하고 안전한 대안은?

**있다. 면별 소유권은 유효하지만 초안 그대로는 저장값 유실 0을 보장하지 못한다.** 다음을 설계 계약으로 추가해야 한다.

1. **baseline과 draft는 한 쌍으로 유지한다.** 현재 두 폼의 `useState(initial)`은 새 initial을 자동 반영하지 않는다(`src/app/(shell)/owner/_components/operations-section.tsx:43`, `src/app/(shell)/owner/_components/subjects-section.tsx:72`). 다른 창이 값을 바꾼 뒤 이 창에서 서버 refresh가 일어나면 baseline prop만 최신이고 draft는 옛 상태일 수 있다. 이 조합은 검사에 통과해 다른 창의 변경을 되돌린다. 반대로 baseline을 처음 값으로 영구 고정하면 자기 첫 저장 후 두 번째 저장이 거절된다. `navigation-section.tsx:27`의 방식처럼 로컬 baseline을 유지하고, 깨끗한 draft만 새 initial과 함께 갱신한다. dirty인 동안 외부 refresh만으로 baseline을 전진시키지 않는다. 저장 성공은 **제출한 스냅샷**에 대해 확정하고 저장 도중 추가된 편집까지 저장됨으로 표시하지 않는다(`src/app/(shell)/owner/_components/section-form.tsx:62`, `src/app/(shell)/owner/_components/section-form.tsx:79`). 설치된 Next 가이드도 refresh가 기존 useState를 유지함을 명시한다(`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/use-router.md:46`).

2. **정상 저장 거절의 구체적인 반례: 레거시 과목의 testMax 누락.** 과목 배열은 그대로 교체되며 normalizeSubjects는 교시·가로줄·step만 주입한다(`src/features/owner/resolve.ts:25`, `src/features/owner/resolve.ts:62`). testMax 없는 옛 english 행을 화면이 읽은 뒤 시간표에서 강사 순서만 저장하면, 그 액션이 전체 operations를 saveOwnerSection으로 보내고 Zod가 `testMax:5`를 추가한다(`src/features/owner/server/subject-actions.ts:368`, `src/features/owner/server/subject-actions.ts:391`; `src/features/owner/server/actions.ts:106`; `src/features/owner/settings-types.ts:143`). 6개 시간표 필드를 제외해도 testMax의 부재→5 차이는 남아 과목 면의 정상 저장을 거절한다. weekdayGrouping의 스키마 기본값도 같은 부류다(`settings-types.ts:138`). 비교 함수는 서버/화면이 같은 함수를 쓰는 데 그치지 말고, **스키마 기본값·읽기 승격을 같은 의미로 정규화**해야 한다. 객체 키는 canonical 순서를 쓰고, 과목/교시 배열 순서는 의미가 있으므로 유지한다. 주입 전후 객체의 속성 배치도 달라질 수 있다(`resolve.ts:61`).

3. **정상 동시 편집도 면 단위로는 거절한다.** 한 창이 공휴일을 고치고 다른 창이 PIN을 고치면 같은 operations 면이므로 초안은 충돌 처리한다. 서로 다른 두 과목의 라벨 변경도 subjects 면 전체 비교에서는 충돌이다. 이는 보수적인 정책으로 받아들일 수 있으나 “같은 면의 모든 변경을 거절한다”는 제품 선택을 명시한다. baseline 불일치를 우회하려고 최신 baseline만 갈아끼우면 위 1번 유실로 바뀐다. 과목 행/필드별 patch로 더 좁히는 것은 후속 단계로 둬도 된다(편집 위치: `src/app/(shell)/owner/_components/operations-section.tsx:130`, `src/app/(shell)/owner/_components/operations-section.tsx:161`, `src/app/(shell)/owner/_components/subjects-section.tsx:74`).

4. **PIN baseline은 새로운 유출 통로다.** operations 면의 revision에 seatPins를 직렬화하고 서버가 원본 settings에서 만든 문자열을 무조건 prop으로 보내면, redacted initial이어도 실제 PIN이 baseline prop/RSC에 들어간다. 현 보호는 렌더 전에 PIN을 지우는 것이다(`src/features/owner/seat-pin-view.ts:20`, `src/features/owner/seat-pin-view.ts:37`; `src/app/(shell)/owner/page.tsx:135`). **쓰기 가능한 사용자에게만 baseline을 내려준다.** 읽기 전용에 평문 revision 또는 추측 가능한 PIN 해시를 보내지 않는다. PIN을 소유하지 않는 subjects 면은 서버 fresh PIN을 보존한다. 병합 후에만 검증하면 원래 요청의 13자 redacted 표식이 버려져 기존 방어가 사라질 수 있으므로, 원 요청의 표식 거절 또는 동등한 권한 전환 방어를 명시하고 기존 테스트의 기대를 의도적으로 유지한다(`src/features/owner/server/seat-pin-save.test.ts:120`). 빈 문자열은 삭제/접속 끄기이며 기본값으로 바꾸지 않는다(`src/features/owner/settings-types.ts:272`).

5. **prepareSectionForSave의 raw 입력 의미를 유지한다.** 침산에서는 periodStyle/schoolSaveAliases를 반드시 제거하고, 일반판의 구폼에서 빠진 두 키는 저장값을 보존한다(`src/features/owner/preset.ts:130`). 병합용 resolve 결과를 그대로 rawInput인 것처럼 쓰면 원래 요청에 키가 있었는지 구분할 수 없다. 원 요청, 파싱 결과, fresh 저장값, 병합 후보를 구분하여 prepare의 기존 계약을 유지한다. 두 키와 terms는 현재 운영 폼이 직접 편집하지 않으므로 face 목록에서 빠진 것 **자체는 오류가 아니다**(`src/app/(shell)/owner/_components/operations-section.tsx:75`, `src/app/(shell)/owner/_components/operations-section.tsx:122`; `src/features/owner/settings-types.ts:258`, `src/features/owner/settings-types.ts:268`). 그러나 어느 면을 저장해도 기존 값이 보존되는 회귀 사례는 필수다. resolve가 지우는 부서 record를 먼저 고치지 않으면 subjects 저장도 그 record를 {}로 만들 수 있다(`src/features/owner/resolve.ts:21`; `src/features/owner/generic-defaults.ts:35`).

6. **6개 시간표 필드는 “없어짐”까지 fresh가 이겨야 한다.** `saveTeacherViewOrder`는 빈 순서를 undefined로 만들어 JSON에서 키를 제거한다(`src/features/owner/server/subject-actions.ts:385`, `src/features/owner/server/subject-actions.ts:390`). incoming에 옛 teacherViewOrder가 남고 fresh에 키가 없을 때, fresh의 존재하는 키만 spread하면 옛 순서가 부활한다. incoming에서 6개를 먼저 제거한 다음 fresh의 값/부재를 복사한다. `integrationOthersTitle`의 제거도 같은 계약이다(`subject-actions.ts:488`). 새 과목을 “그대로” 받는다는 규칙도 과목 폼이 소유하지 않은 보관함 도장/그룹 값을 받아야 하는지 명시한다(도장은 서버가 찍는 계약: `subject-actions.ts:441`, `subject-actions.ts:474`).

7. **자체 흡수 직후 저장은 별도 조정이 필요하다.** 서버는 fresh 과목 행을 즉시 제거한다(`src/features/owner/server/subject-actions.ts:143`, `src/features/owner/server/subject-actions.ts:267`). 클라는 해당 index의 행만 빼고 savedNonce를 올리며, 나머지 draft는 유지한다(`src/app/(shell)/owner/_components/subjects-section.tsx:78`, `src/app/(shell)/owner/_components/subjects-section.tsx:396`). baseline을 유지하면 자기 삭제 이후 저장도 거절되고, 새 prop baseline을 무조건 받으면 다른 미저장 값이 최신 서버 변경을 덮을 수 있다. 가장 작은 안전한 정책은 **다른 변경이 dirty면 먼저 저장한 후 흡수/삭제**하도록 하는 것이다. 다른 편집을 유지하려면 삭제 후 서버 canonical 상태를 받아 key 기준으로 draft와 baseline을 명시적으로 조정해야 한다. 현재 savedNonce가 다른 미저장 편집까지 markSaved하는 문제도 고친다(`src/app/(shell)/owner/_components/section-form.tsx:97`). 다른 창의 오래된 과목 목록은 삭제/흡수된 과목을 재등록하지 못하도록 계속 거절한다. 신규 과목 추가의 허용과 stale 삭제 과목 부활의 거절을 구분한다.

8. **face는 서버가 검증할 요청 형식이다.** operations 섹션에서만 operations/subjects 두 값을 허용하고, face가 있으면 baseline도 필수로 받는다. 잘못된 face나 baseline 누락을 legacy 전체교체로 흘려보내지 않는다. 현재 서버는 section·schema·쓰기권한을 먼저 검증한다(`src/features/owner/server/actions.ts:73`, `src/features/owner/server/actions.ts:84`). 새 계약도 같은 권한 검사를 유지하며, face 문자열 자체를 권한 근거로 삼지 않는다. baseline은 인증 수단이 아니라 정상 클라이언트의 충돌 방지 정보다.

9. **최종 쓰기 시점의 경합은 별개다.** 면 baseline이 같고 병합이 올바르더라도 조회 이후 외부 쓰기가 들어오면 별도 CAS가 필요하다. 중앙 액션의 updated_at 조건은 유지하고, 모든 in-scope writer가 같은 토큰을 갱신하도록 맞춘다. cron과 시트 경로에 관한 구체적 반례는 R1에 적었다.

**더 단순한 대안:** 우선 operations 전체의 canonical baseline을 navigation과 같은 draft/baseline 수명으로 붙여 stale 전체 저장을 보수적으로 거절하고, P1-D와 PIN 보호부터 완성한다. 이 경우 시간표 저장도 충돌로 간주한다고 명시하면 비교/병합 예외는 줄어든다. 다만 외부 writer/CAS와 내부 caller 문제까지 해결해야 안전하며, 오탐 없는 면별 병합의 대체라고 과장하지 않는다. 사용자 편의까지 이번에 해결하려면 면별 병합을 채택하되 **실제 저장 의도별 중앙 patch 계약**으로 내부 호출자도 함께 옮기는 쪽이 낫다. DB RPC나 필드별 revision 열을 신설하는 대안은 이번 마이그레이션 금지 범위 밖이다.

### Q2. 역할·권한 면에서 버튼을 감추고 baseline을 붙이면 충분한가?

**그대로는 부족하다.** 버튼 숨김은 한 화면의 중복 입구를 없애는 조치이며, 다른 면/다른 창의 대화상자는 계속 overrides를 바꾼다(`src/app/(shell)/owner/page.tsx:174`; `src/features/owner/server/setting-role-actions.ts:36`). 여기에 표가 overrides·userOverrides·specialAccess 전체를 함께 저장한다(`src/app/(shell)/owner/_components/permissions-section.tsx:150`). 두 창에서 각각 개인 예외와 민감 기능 명단을 고치면 overrides는 같아서 초안의 검사에 통과하고 앞 저장을 되돌릴 수 있다.

따라서 실제 저장 대상 전체에 canonical baseline을 붙이거나 세 영역을 독립 patch로 저장한다. clean 판정도 matrix 하나만 보면 안 된다. 권한 표의 역할 토글 복원 ref까지 새 확정 상태와 맞추고(`permissions-section.tsx:128`), dirty refresh·자기 저장 후 재저장을 검증한다. 침산 specialAccess 제거/구폼 누락 보존과 운영자 설정 경계는 그대로 유지한다(`src/features/owner/preset.ts:64`; `src/features/owner/server/platform-settings.ts:34`). 대화상자 설명은 “새로 허용한 직급은 변경 가능, 기존 조회 전용 권한은 유지”처럼 실제 동작을 담는다(`src/features/owner/setting-roles.ts:23`).

### Q3. 데이터 정리 액션을 admin으로 유지하는 판단이 맞는가?

**맞다.** 현재 4개 파괴적 액션은 admin 쓰기 권한을 요구한다(`src/features/admin/server/actions.ts:30`, `src/features/admin/server/actions.ts:122`, `src/features/admin/server/actions.ts:207`, `src/features/admin/server/actions.ts:273`). owner 쓰기로 바꾸면 “설정을 위임했다”는 기존 정책을 “원생 병합/영구 삭제도 위임했다”로 확장한다. 이번 정리 범위에서 바꿀 근거가 없다.

UI 플래그도 같은 canWriteTenant(admin)를 사용하고, 데이터 정리의 외부 fieldset은 owner 쓰기 때문에 그 플래그를 다시 덮지 않게 조정한다(`src/app/(shell)/owner/page.tsx:184`). 조회·개별 상세 링크는 별개다. bulkDelete는 이미 2단 확인이 있으므로 이를 일관된 확인 문장으로 개선한다(`src/app/(shell)/admin/cleanup/_client.tsx:196`). “전체 학원 작업이므로 scoped를 허용해도 되는가”는 별도 정책 검토로 남기되, 이번에 UI만 canManage로 바꾸어 서버와 어긋나게 하지 않는다(`src/lib/auth/perm-matrix.ts:131`, `src/lib/auth/perm-matrix.ts:149`).

### Q4. 범주 5개·순서 유지·리다이렉트는 기존 가드와 충돌하지 않는가?

**5범주와 기본 순서 유지에는 동의하며, 구현 순서/후보 판정에 조건이 있다.** 범주는 권한 단위로 쓰지 않는다. generic 전용 modules는 현재 navigation 다음, dashboard 전에 삽입되므로 초안에 적은 dashboard→기능 순서는 실제 “순서 유지”와 다르다(`src/app/(shell)/owner/page.tsx:65`). 공용 목록으로 파생할 때 기존 genericOnly·masterOnly·icon·개별 설정 menuKey를 버리지 않는다(`src/lib/menu-hub.ts:249`, `src/lib/menu-hub.ts:264`; `src/lib/settings-role-catalog.ts:46`). 사용자 지정 이름·배치는 기본 라벨 위에 계속 적용되어야 한다(`src/lib/menu-hub.ts:358`; `src/components/face-tabs.tsx:92`).

리다이렉트는 지금 requireAccess(menu)가 먼저 종료하므로, 인증된 현재 사용자와 **getUserPermMatrix의 최종 권한**으로 후보를 고른 후 도착 면의 requireAccess를 적용해야 한다(`src/lib/auth/require-access.ts:20`; `src/lib/auth/perm-matrix.ts:82`). 역할 override만으로 계산하면 개인 예외·꺼진 모듈·계정 보호를 놓친다. 후보는 실제 표시/조회 가능한 면으로 좁혀야 한다: audit/dashboard 전용 계정 조건, modules의 generic+전용 계정 조건, 기존 alias 이동을 포함한다(`src/app/(shell)/owner/page.tsx:106`, `src/app/(shell)/owner/page.tsx:125`, `src/app/(shell)/owner/page.tsx:179`). 아무 후보가 없으면 기존 가드를 사용하고 자기 주소 리다이렉트 루프를 만들지 않는다. embed 문맥은 유지한다(`src/app/(shell)/owner/_components/duplicates-face.tsx:20`).

꺼진 모듈에 대한 기존 404 정책을 홈/다른 면 이동으로 바꾸지 않는다(`src/lib/auth/require-access.ts:30`). import는 버튼별 canManage를 유지하지만, 현재 허브 진입 자체는 owner 권한이다(`src/app/(shell)/owner/page.tsx:112`; `src/app/(shell)/owner/_components/import-hub-face.tsx:19`). fieldset 제거가 “owner 없이도 모든 import 허브 진입 허용”까지 뜻하는 것은 아니다. 그런 확장 의도가 있으면 후보 정책과 페이지 게이트를 별도로 명시해야 한다. 순수 함수 테스트에 개별 설정만 위임·readonly·개인 예외·전용 면·generic/침산·후보 없음·embed를 넣는다.

### Q5. 빠진 위험·순서·범위 조정은?

**P1-D를 앞당기고, P1-A에는 클라이언트 상태와 모든 현행 저장자의 계약을 포함하며, P1-C에는 최소 부분실패 처리를 넣는다.** 범주/문구 정리는 그 이후 별도 커밋으로 진행한다. 3단계와 섹션 간 필드 이동·DB 트랜잭션 도입은 초안처럼 분리한다. 구체적 범위와 검증 조건은 아래와 같다.

## 3. 빠진 위험·범위 조정 제안

### R1. 외부 writer는 면 병합으로 보호되지 않는다 — P1-A에 포함

cron은 data 전체를 읽어 교체하며 select에 updated_at도 없고 update에 CAS/토큰 갱신도 없다(`src/features/owner/server/scheduled-groups.ts:46`, `src/features/owner/server/scheduled-groups.ts:87`, `src/features/owner/server/scheduled-groups.ts:92`). 다음 두 방향이 모두 가능하다: cron이 읽은 뒤 owner가 저장하면 cron이 그 값을 덮는다; owner가 읽은 뒤 cron이 저장하면 owner의 updated_at 조건이 cron 변경을 못 보고 그룹을 덮을 수 있다. 시트 반영은 JSONB 필드 갱신이지만 SQL에 updated_at 갱신이 없어서 후자의 경로가 남는다(`src/features/timetable/server/master-sheet-store.ts:370`; `src/features/owner/server/actions.ts:202`).

저장소의 최초 tenant_settings DDL은 updated_at default만 둔다(`supabase/migrations/0033a_tenant_settings.sql:8`). **실제 DB에 별도 timestamp 트리거가 있는지는 미확인**이므로 실제 사고를 단정하지 않는다. 앱 코드만으로 일관성을 확보하려면 cron의 CAS·충돌 반환과 모든 해당 writer의 토큰 갱신을 함께 넣는다. cron의 캐시 무효화 책임도 호출부에 있다는 계약을 유지한다(`scheduled-groups.ts:19`). 구폼을 기존 전체교체로 계속 허용한다면 “그 경로까지 유실 0”은 완료 기준에서 주장할 수 없다. 강한 보장이 필요하면 구폼의 무기준값 저장을 새로고침 안내로 거절하는 것이 더 안전하다.

### R2. 보호와 비교 테스트는 실제 경계를 검증해야 한다

현재 seat-pin-save 테스트는 모의 DB를 사용한다(`src/features/owner/server/seat-pin-save.test.ts:40`). 새 순수 병합 함수 테스트만으로는 서버 raw→parse→fresh→merge→prepare→CAS와 클라이언트 draft/baseline 경계가 검증되지 않는다. 합성 데이터로 다음 사례를 구현 리뷰의 필수 확인에 넣는다(이번 검토에서는 실행하지 않았다).

- 같은 면/다른 면 동시 저장, 자기 저장 후 재저장, dirty 상태에서 외부 refresh, 저장 중 추가 편집, 이전 PIN이 빈 문자열인 경우.
- 레거시 과목(testMax/weekdayGrouping 누락)의 시간표 순서 저장 전후 revision 동등성, english 읽기 기본값 주입, generic 과목에 침산 필드가 주입되지 않음(`src/features/owner/resolve.ts:53`; `src/features/owner/settings-types.ts:138`).
- 시간표 순서/기타 제목 키가 없어졌을 때 stale incoming 값 부활 금지, 새 과목/순서 변경/다른 창 흡수 직후 저장, 자체 흡수+다른 미저장 변경.
- 읽기 전용 RSC/props/hidden JSON에 PIN 또는 PIN 포함 baseline이 없음, 렌더 후 쓰기권한 변경에도 redacted payload가 PIN을 손상시키지 않음(`src/features/owner/seat-pin-view.ts:11`).
- prepare의 침산 키 제거·generic 구폼 누락 보존, 부서 record/terms/꺼진 모듈 설정 보존, 현행 서버 caller와 cron/시트의 최종 CAS 충돌.
- 권한 개인 예외/민감 명단의 다른 창 변경, 전체 clean 판정, 숨겨진 운영자 설정 변경 거절(`src/features/owner/server/platform-settings.ts:37`).

### R4. 페이징만 고치면 스케줄 진단의 의미 차이는 남는다

findOrphans는 스케줄 존재 여부만 보며 validFrom/validTo를 전혀 필터하지 않는다(`src/features/admin/server/queries.ts:271`). 화면은 “주간 스케줄 없음·시간표에 표시되지 않음”이라고 말한다(`src/app/(shell)/admin/cleanup/_client.tsx:85`). 이력만 있는 반이 정상으로 분류되는 반대 방향의 누락도 가능하다(`src/lib/db/schema.ts:504`). 이번에 날짜 판정을 바꾸려면 “오늘 유효한 스케줄인가, 미래 예약도 인정하는가”를 별도 정의한다. 아니면 “스케줄 기록 없음”으로 문구를 실제 판정에 맞추고 후속 이슈로 둔다. 새 throw는 DataFace가 그대로 await하여 면을 실패시킬 수 있으므로 면 안에서 오류 상태로 받는다(`src/app/(shell)/owner/_components/data-face.tsx:9`). bulkDelete의 invoices whitelist도 청크 안 무페이징 조회가 남아 있으나 이번에 삭제 로직을 만지면 함께 좁게 검토할 대상이다(`src/features/admin/server/actions.ts:283`).

### R6. 구현 순서·남길 범위

권장 순서: **P1-D → P1-A(폼 상태·PIN·caller·writer 포함) → P1-B → P1-C → P2 → 3단계 시각 검증**. P1-D와 P1-A를 한 커밋으로 묶는 것도 가능하다. P1-C의 표 확장·트랜잭션화와 3단계 화면 재배치는 분리한다. 2단계 전체를 “라벨·문구만”이라고 부르지는 않는다: P2-B는 접근 경로를, P2-D는 가시성과 진입점을 바꾼다(`src/app/(shell)/owner/page.tsx:113`; `src/app/(shell)/owner/_components/import-hub-face.tsx:41`; `src/app/(shell)/kiosk-settings/page.tsx:73`). 변경된 경계별 검증으로 나누는 것이 검토 가능하다.

합의 가능 여부: 조건부(P1-A의 canonical 비교·draft/baseline 수명·PIN 비노출·흡수 후 조정·현행 caller 및 외부 writer 경합 보완, P1-B의 전체 권한 payload 보호, P1-C의 최소 오류·부분완료 처리, P2-B의 실제 허용 면과 기존 가드 보존)
