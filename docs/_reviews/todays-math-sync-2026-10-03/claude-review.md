# 에이와 ↔ 오늘의수학 계정·지점 연동 계획 — 독립 검토 (Claude)

2026-10-03 · 계획 검토 전용(코드·SQL·환경변수·배포 변경 없음) · 대상 문서 `brief.md`

## 0. 결론

**조정자의 초기 가설은 방향은 맞지만, 지금 그대로는 승인할 수 없다.** 아래 차단점 9개가 풀려야 한다. 가장 무거운 셋은 이렇다.

1. **이메일 자동 매핑은 양쪽 모두에서 뚫린다.** 에이와 이메일이 미확인이라는 것은 이미 알려져 있고, 이번에 **오늘의수학 가입도 이메일을 확인하지 않는다**는 것을 확인했다. 누구든 강사 이메일로 오늘의수학에 먼저 가입해 두면, 지점을 켜는 순간 그 계정이 강사의 반·학생에 연결된다(B1).
2. **정지를 지금의 `suspendedAt` 한 칸으로 구현하면 요구 2와 요구 7이 서로를 깬다.** 게다가 계정 주인이 스스로 연결을 풀면(`DELETE /api/account/eywa-link`) 지점 OFF·퇴사 정지가 닿지 않는다(B2).
3. **자동 생성한 계정은 지금 코드로는 로그인도 못 하고, 로그인해도 자기 반이 없다.** 비밀번호 없는 계정은 SSO가 거절하고, 모든 반은 계정 하나(`EYWA_SYNC_OWNER_EMAIL`)가 소유하며, 동기화 대상 반은 손으로 적은 2개뿐이다(B3).

사용자가 정해야 하는 것은 5가지로 줄였다(§4.3). 그중 둘은 **이미 기록된 결정을 뒤집는 것**이라 조용히 넘어가면 안 된다 — "자동 가입 없음·이메일은 신원 아님"(2026-09-26, `docs/decisions/tenant.md`)과 "동기화는 이수진T 반 2개만"(2026-08-25, 오늘의수학 `syncScope.ts`).

## 2. 차단점

### B1. 이메일 매핑은 양쪽 모두 미확인이다

**근거**
- 에이와: 본인이 확인 없이 이메일을 바꾼다 — `updateMyEmail`(`src/features/staff/server/me-actions.ts:28-75`, `email_confirm: true` :52). 관리자·이력서 경유 변경도 같다 — `applyStaffEmailChange`(`account-actions.ts:138-217`). 계정 생성 7곳 전부 `email_confirm: true`(`staff/server/actions.ts:147`, `public-intake-actions.ts:98`, `resume-actions.ts:238`, `excel-import/importers/staff.ts:279`, `super-admin/server/actions.ts:90`, `demo-roster/demo-staff.ts`, `scripts/provision-admin7099.ts`).
- 오늘의수학: 가입이 이메일을 확인하지 않는다 — `POST /api/auth/signup`(`src/app/api/auth/signup/route.ts:27-79`)은 아무 이메일 + 자기 비밀번호로 `pending` 계정을 만든다. `User.email`은 전역 유일(`prisma/schema.prisma:170`), 로그인은 이메일로 찾는다(`src/lib/auth.ts:117`).

**실패 사례**
1. *역방향(기존에 알려진 것)*: 에이와 직원이 자기 이메일을 오늘의수학 원장 이메일로 바꾼다 → 이메일 매핑이 원장 계정을 그 직원에게 연결.
2. *선점(이번에 확인)*: 외부인·퇴사자가 오늘의수학에 재직 강사의 이메일로 먼저 가입한다(확인 메일이 없어 성공) → 지점 ON 때 "기존 계정은 이메일로 매핑"이 그 계정을 강사의 에이와 id에 묶고 승인·반 배정까지 한다 → 공격자는 **자기가 정한 비밀번호로 직접 로그인**해 그 강사 반의 학생을 본다. 강사가 퇴사하기 전에는 정지도 걸리지 않는다.
3. *이메일 재사용*: 퇴사자 A를 `deleteStaff`로 지운 뒤 같은 공용 주소로 B를 등록 → 이메일 매핑이 A의 옛 계정(A의 작업실 문서·장바구니·비밀번호 포함)을 B에게 연결. 요구 7("과거 삭제 계정을 되살리지 않는다") 위반이기도 하다.

**해결**
- 연결이 생기는 길을 셋으로 고정한다: ① `created` — 새 계정 자동 생성(비밀번호 없음), ② `password_proof` — 지금 있는 흐름(오늘의수학 비밀번호로 로그인 후 [연결], `api/account/eywa-link/route.ts`), ③ `admin_confirmed` — 오늘의수학 최고관리자가 후보를 보고 명시 확정(감사 기록).
- **이메일 일치는 후보 큐에만 넣는다.** 일치하는 계정이 있으면 자동 연결도, 자동 생성도 하지 않는다(이메일 유일 제약 때문에 어차피 같은 이메일로 못 만든다). 상태를 "연결 필요"로 두고, 그 사람이 바로가기를 누르면 지금의 비밀번호 1회 연결 화면으로 간다.
- ③의 후보 조건: `approvalStatus = approved` ∧ 정지·삭제 아님 ∧ `eywaUserId` 비어 있음. **`pending`·`rejected` 계정은 후보에서 뺀다**(선점 공격의 계정이 정확히 `pending`이다).
- 같은 저장소 선례: 슬랙 사람 연결이 이미 "이메일 일치는 후보일 뿐"이고 방법을 `code | owner_email`로 기록한다(`0298a_slack_rules_inbox.sql`의 `slack_user_links.method`).

### B2. 정지 사유 분리 · 자가 해제 회피 · 보호 계정

**근거**
- 오늘의수학의 정지는 `suspendedAt` 한 칸이고, 관리자 화면이 그대로 지운다 — `suspendedAt: update.suspended ? new Date() : null`(`src/app/api/admin/users/[id]/route.ts:196-198`).
- 계정 주인이 스스로 연결을 푼다 — `handleDelete`(`src/app/api/account/eywa-link/route.ts:169-198`)가 `eywaUserId: null`로 만든다.
- 마지막 활성 원장은 정지할 수 없고(`[id]/route.ts:153-183`), 최고관리자 계정은 이 화면에서 못 바꾼다(:93-99).
- 차단을 실제로 집행할 자리는 이미 있다 — `jwt` 콜백이 세션을 읽을 때마다 DB에서 `deletedAt`·`suspendedAt`·`sessionVersion`을 다시 본다(`src/lib/auth.ts:225-245`). 직접 로그인(:117-121)과 SSO(`eywaSso.ts:162`)도 같은 칸을 본다.

**실패 사례**
1. 연동 정지와 수동 정지가 같은 칸이면: ON 재실행이 `suspendedAt = null`로 풀 때 **수동 정지까지 풀린다**(요구 7 위반). 반대로 관리자가 수동 해제를 누르면 **지점 OFF 중인 계정이 풀린다**(요구 2 위반).
2. 퇴사가 예정된 강사가 미리 자기 연결을 푼다 → "연동된 계정" 집합에서 빠진다 → 퇴사·지점 OFF 정지가 닿지 않고, 비밀번호가 있는 기존 계정이면 직접 로그인이 계속된다. 반 소유도 그대로다.
3. 지점 OFF가 연결된 계정 전원을 정지시키면 오늘의수학 최고관리자(동기화 소유자 `EYWA_SYNC_OWNER_EMAIL`일 가능성이 높다)까지 잠겨 **오늘의수학 전체를 관리할 사람이 없어진다.**

**해결**
- 연동 상태를 사용자 행과 **분리된 표**에 둔다(가칭 `EywaAccountBinding`): `eywaTenantId`, `eywaUserId`(유일), `userId`(오늘의수학, 유일·null 허용), `method`(B1의 셋), `blockReasons`(집합: `branch_off`·`staff_inactive`·`staff_pending`·`staff_deleted`·`not_eligible`·`source_stale`), `appliedVersion`, `revocationGen`, `checkedAt`.
- **유효 접근 = 삭제 아님 ∧ 수동 정지 아님 ∧ 승인됨 ∧ 연동 사유 집합이 비어 있음.** 이 판정을 위 세 자리(직접 로그인·SSO·`jwt` 콜백)에 똑같이 넣는다. 정지를 걸 때 `sessionVersion`도 올린다.
- 해제 규칙: 연동은 **자기가 넣은 사유만** 뺀다. ON은 `branch_off`만, 복직은 `staff_inactive`만 뺀다. `suspendedAt`·`approvalStatus`·`deletedAt`은 연동이 절대 쓰지 않는다. 이러면 요구 2와 7이 동시에 선다.
- **관리 대상 연결은 본인이 못 푼다.** `DELETE /api/account/eywa-link`는 연동이 관리하는 계정이면 거절하고, 해제는 최고관리자만 한다. 해제해도 표의 행은 지우지 않고 "분리됨" 표식만 남긴다(다시 붙는 것을 막는 근거).
- 보호: `isSuperAdmin` 계정은 연동 정지 대상에서 뺀다(사유는 기록하되 접근은 막지 않고 충돌 목록에 올린다). 지점 원장(`owner`)은 OFF 때 정지해도 된다 — 지점 전체를 끄는 것이 OFF의 뜻이고, 최고관리자는 남는다. 이 예외를 불변 조건으로 적어 둔다.
- 표의 `userId`는 사용자 삭제에 `SetNull`이어야 한다. 오늘의수학에는 사용자를 하드 삭제하는 스크립트가 있다(`scripts/admin/reorganize-accounts.ts:141,244`) — `Cascade`면 삭제 표식이 함께 사라진다(B9).

### B3. 자동 생성 계정이 로그인·승인·"자기 반"에 닿지 못한다

**근거**
- 비밀번호 없는 계정은 SSO가 거절한다 — `if (!user?.passwordHash || …) return null`(`src/lib/eywaSso.ts:162`). 이미 연결된 계정이 거절되면 연결 안내도 없이 `/login`으로 간다(`api/sso/eywa/route.ts:44-60, 72`) — 비밀번호가 없으니 막다른 길이다.
- 새 계정의 기본값은 승인 대기(`schema.prisma:208`)이고 승인 전에는 API가 403이다(`src/lib/accountAccess.ts:56`).
- 모든 반은 계정 하나가 소유한다 — `runSync.ts:135-142`가 `EYWA_SYNC_OWNER_EMAIL` 계정을 찾고 :352에서 생성 때만 `userId`를 넣는다. 갱신은 소유를 안 바꾼다(:355, 주석 "소유 이관은 수동").
- 강사는 자기 소유 반만 본다 — `ownedRowsWhere`가 `{ userId: viewer.id }`(`src/lib/ownerScope.ts:77-84`).
- 동기화 대상은 손으로 적은 2개 반이다 — `EYWA_SYNC_CLASSES`(`src/lib/eywa/syncScope.ts:44-55`, 원장 확정 2026-08-25).
- 학생은 한 반에만 속한다 — `Student.classId`(`schema.prisma:370`) + `eywaStudentId` 유일(:378) + 주반 규칙 `primaryClassOf`(`syncPlan.ts:45-54`). `runSync.ts` 주석은 여러 반 학생이 실측 69%라고 적는다.
- 시험지는 반과 사람 양쪽에 묶인다 — `Test.userId` + `Test.classId`(`schema.prisma:965-966`).

**실패 사례**: 지점을 켜서 수학 강사 10명의 계정을 만든다 → 전원이 SSO에서 거절된다. 거절을 고쳐도 승인 대기에 막힌다. 승인까지 고쳐도 2개 반 담당이 아닌 8명은 빈 화면을 본다. 2개 반의 담당조차 반 소유자가 아니라 못 본다. 요구 4는 네 겹으로 막혀 있다.

**해결(계획에 반드시 들어가야 하는 것)**
1. SSO 허용 조건을 "비밀번호 있음"에서 "유효 접근(B2) ∧ 연결됨"으로 바꾼다. 비밀번호 로그인 쪽은 그대로 `passwordHash`를 요구한다(자동 생성 계정은 SSO 전용). 오늘의수학에는 비밀번호 찾기·메일 발송이 없고, 비밀번호 변경은 현재 비밀번호를 요구한다(`api/account/password/route.ts`) — 자동 생성 계정이 스스로 비밀번호를 만드는 길은 없다. 그대로 둔다.
2. 자동 생성 계정은 `approved` + 지점 소속 + `branchRole: teacher` + `isAdmin: false`로 만든다(최소 권한 — §4.2).
3. 반 소유 규칙: 오늘의수학 `Class.userId` = 에이와 `classes.teacher_id`(담임)에 연결된 계정. 담임이 비었거나 연결이 없으면 지점의 "보관 소유자"(지금의 동기화 소유자) 계정. 담임이 바뀌면 소유를 옮긴다.
4. 소유를 옮길 때 그 반에 묶인 시험지(`Test.classId`)의 `userId`를 어떻게 할지 정해야 한다. 안 옮기면 **옛 담임이 떠난 반의 시험지를 계속 보고, 새 담임은 지난 시험지를 못 본다.** 추천 기본값: 같은 트랜잭션에서 함께 옮기되 예측 회차 시험지(`predictionRunId` 있음)는 개인 작업물이라 남긴다. `ownerScope.ts`는 판정이 한 곳에 모여 있고 변이 시험이 걸려 있어, 이 변경은 오늘의수학 저장소 쪽 결정이 먼저다.
5. 동기화 범위와 학생 다중 반은 사용자 결정이다(§4.3의 결정 3·4).

### B4. 지점 연결키가 없고 대사가 전역이다

**근거**
- `Branch`에 에이와 지점 키가 없다(`schema.prisma:154-162`).
- SSO는 `EYWA_SSO_TENANT_IDS`가 비면 모든 지점의 표를 받는다(`eywaSso.ts:115-120`). 표의 `tenantId`를 계정의 지점과 견주지 않는다.
- 에이와 명단 API는 env `TODAYS_MATH_TENANT_ID` 한 지점만 준다(`roster/route.ts:31`). 그런데 스위치는 어느 지점이든 켤 수 있다(`toggleTenantLicense`, `super-admin/server/actions.ts:412-447`).
- 오늘의수학 대사가 지점을 안 가린다 — 퇴원 표시 `eywaStudentId: { not: null, notIn: [...rosterIds] }`(`runSync.ts:402-408`), 진도 전체 삭제 `eywaReportId: { not: null }`(:414-416), 잠금 키도 하나(:48-54).

**실패 사례**: 두 번째 지점을 붙여 그 지점 명단으로 동기화를 돌리면 **첫 지점 학생 전원이 퇴원 표시되고 진도가 전부 지워진다.** 계정 쪽도 같다 — 지점 키 없이 "그 지점에 연동된 계정"을 고를 수 없다.

**해결**
- `Branch.eywaTenantId`(유일)를 더하고, 연동 표(B2)에도 지점 키를 둔다. "지점 OFF 대상" = 연동 표의 지점 키가 그 지점인 행(오늘의수학 `branchId` 기준이 아니다 — 기존 독립 계정을 연결해도 소속을 자동으로 옮기지 않기 때문이다. 관리자 화면도 반이 있는 계정의 소속 변경을 막는다, `[id]/route.ts:141-151`).
- 매핑이 없는 지점은 **연동하지 않는다**(fail-closed). 에이와에서 켜도 계정 동기화는 "지점 매핑 없음" 충돌로만 남는다.
- SSO는 표의 `tenantId`가 연동 표의 지점 키와 같을 때만 통과시킨다.
- 학생·진도 대사를 지점 범위로 좁히는 것은 **두 번째 지점을 붙이기 전의 선행 조건**으로 계획에 적는다(이번 1차 범위가 한 지점이면 구현은 뒤로 미뤄도 되지만, 미뤘다는 사실과 금지 조건을 문서에 남긴다).

### B5. 변경 포착 — 쓰기가 없는 시간 전이, RPC, 삭제

**근거와 빠지는 경로**

| 분류 | 경로 | 근거 |
|---|---|---|
| 쓰기 없는 시간 전이 | 라이선스 만료일 경과 | `licenseAllows`가 `expires_at`을 읽는 순간에 판정(`src/lib/license/rule.ts:19-24`). 만료는 UPDATE 없이 일어난다 |
| 〃 | 위임 기간의 시작·끝 | `class_delegations.from_date~to_date` 양끝 포함 + `revoked_at`(`schema.ts:2298-2322`) |
| 〃 | 교시 담당의 미래 배치 | `class_schedules.valid_from/valid_to` 행 분할(`handover.ts:32-100`) |
| 〃 | 수강의 미래 시작·미래 종료·휴원 | 정본 판정은 `isEnrollmentActiveOn`(`src/features/enrollments/eligibility.ts:28-34`) |
| 앱 액션을 안 거치는 쓰기 | 수강 이동·예약 변경 RPC | `move_enrollments_batch`·`move_class_enrollments_batch`·`change_scheduled_enrollment`·`close_ended_class_period_enrollments` |
| 〃 | 담당 과목 일괄 변경 RPC | `absorb_subject_key`가 `users.subjects[]`를 한 문장으로 바꾼다(`owner/server/subject-actions.ts:235`) |
| 〃 | cron | 예약 담임 적용 `apply-due-class-updates`(00:30 KST), 퇴원 예약 `apply-due-withdrawals` |
| 〃 | 운영자 콘솔 | `setUserActive`(`super-admin/server/actions.ts:285-330`), `changeUserRole`(:190-244) |
| 〃 | 엑셀 가져오기·스크립트·직접 SQL | `excel-import/importers/staff.ts`, `scripts/*` |
| 삭제 | 직원 하드 삭제 | `deleteStaff`(`account-actions.ts:335-401`) — 지워진 행은 "현재 상태 읽기"에 안 나온다 |
| 〃 | 지점 삭제 | `tenants` 삭제는 `users`·`tenant_licenses`를 cascade로 지운다 |

퇴사 경로만 해도 넷이다: `deactivateStaff`(`staff/server/actions.ts:611-680`), `handoverAndDeactivate`(:703-865), `setUserActive`, 그리고 삭제. 담임 변경 경로는 `updateClass`·`applyHandover`(`classes/server/actions.ts:374, 966`)·`reassignHomeroom`(`handover.ts:109-133`)·cron·시간표 편집이다. 액션마다 HTTP 호출을 붙이는 방식은 이 목록을 다 못 덮는다 — 가설의 이 부분에 동의한다.

**추가로 확인한 불일치**: 에이와 명단 API는 `end_date is null`만 본다(`integrations/todays-math/service.ts:57-71`). 정본 판정과 달라서 **미래에 시작하는 수강은 일찍 들어오고, 미래 종료가 찍힌 수강(예약 반 이동의 옛 반)은 종료일 전에 빠지고, 휴원 중인 수강도 들어온다.** "반 이동을 빠짐없이 반영"이 요구이므로 계정 연동과 같은 계획에서 고쳐야 한다(오늘의수학 직결 전송 `transport.ts:132-145`도 같은 조건이다).

**해결**
- **DB 트리거 → 인박스(같은 트랜잭션)** 로 잡는다. 대상: `users`(insert · delete · `status`·`system_role`·`subjects`·`email`·`display_name` 변경), `tenant_licenses`(`feature = 'todays_math'`의 insert·update·delete), `classes`(`teacher_id`·`is_active`·`closed_at`·`subject`·`class_name`), `class_schedules`, `class_delegations`, `enrollments`. 슬랙 인박스(`0298a`)와 같은 규약: 식별자만 싣고, 원본 쓰기를 막지 않는다.
- **삭제는 트리거가 삭제 표식을 남긴다**(지점·사용자 id만). 지점 cascade 삭제에서 인박스 행까지 함께 지워지지 않도록 인박스의 지점 FK는 cascade로 두지 않는다.
- **시간 전이는 트리거로 못 잡는다.** 그래서 대상(오늘의수학)이 읽는 상태 API는 저장된 값을 그대로 주지 않고 **요청 시점의 날짜·시각으로 계산한 유효 상태**를 준다(만료일·유효기간·위임 기간 반영). 날짜가 넘어가는 순간의 변화는 주기 대조(§7)가 수렴시킨다.
- 트리거가 예외를 삼키는 설계라 누락이 있을 수 있다 → 주기 전수 대조가 안전망이다. 대조는 한 스냅샷을 끝까지 받은 뒤에만 "없다"를 판정한다(가설에 동의).

### B6. 버전·순서 축이 없고, 빠른 OFF→ON이 합쳐진다

**근거**: 지금 연동에는 버전이 없다. `updated_at`은 커서로 쓸 수 없다 — 슬랙 설계가 이미 적어 둔 대로 `now()`는 트랜잭션 시작 시각이라 늦게 커밋된 행이 커서 뒤로 떨어진다(`0298a` 머리말).

**가설의 구멍 두 개**
1. *"원본 버전 재검증"에 쓸 번호를 누가 매기나.* 인박스의 자동 증가 id를 버전으로 쓰면 같은 문제가 난다 — 트랜잭션 A가 10번을 받고 늦게 커밋하는 사이 B의 11번이 먼저 커밋되면, "지금까지의 최대 번호 = 11"로 찍은 스냅샷은 10번의 변경을 담지 못했는데 번호상으로는 최신이다.
2. *"현재 상태를 읽어 반영"만으로는 OFF→ON이 사라진다.* OFF 직후 ON이 오면 대상이 읽는 현재 상태는 ON이다. 그 사이의 세션 취소가 일어나지 않는다. 퇴사→복직도 같다. 조정자의 "정지 세대(revocation generation)" 제안에 동의한다.

**해결**
- 버전은 변경 트랜잭션이 아니라 **지점 리스를 쥔 발신기**가 매긴다: 리스 획득 → 미처리 인박스 행 집기 → 지점 상태 행의 `version`을 1 올리고 스냅샷 생성 → 알림. 리스가 직렬화하므로 번호가 단조롭다. 인박스는 "최대 번호"가 아니라 **행 상태(대기/처리됨)** 로 소진한다.
- 대상은 지점 단위 잠금 안에서 `appliedVersion < snapshot.version`일 때만 적용한다. 늦게 도착한 옛 스냅샷은 버린다.
- **정지 세대**: 지점마다, 사용자마다 카운터를 둔다. OFF로 가는 전이·퇴사로 가는 전이 때 트리거가 같은 트랜잭션에서 1 올린다(덧셈이라 순서가 뒤집혀도 결과가 같다). 스냅샷에 싣고, 대상은 받은 값이 저장된 값보다 크면 **최종 상태가 활성이어도** `sessionVersion`을 올린다. 상태는 현재값으로, 취소는 횟수로 전달하는 구조다.
- 중복 알림은 버전 비교로 무해하다. 알림 본문에는 지점 id와 버전만 싣는다(가설에 동의).

### B7. 상태 API가 "꺼짐"과 "모름"을 가르지 못하면 장애가 전원 정지가 된다

**근거**
- `isFeatureOptedIn`은 조회가 실패하면 **꺼짐**을 돌려준다(`src/lib/license/server.ts:55-58, 60-63`). 메뉴를 감추는 용도로는 맞는 기본값이다.
- 명단 API는 꺼진 지점에 503을 낸다(`roster/route.ts:39-41`). 오늘의수학은 비-200을 실패로 본다(`transport.ts:65-68`).
- 직결 전송은 스위치를 보지 않는다 — `fetchViaDb`(`src/lib/eywa/transport.ts:117-206`)는 `EYWA_DATABASE_URL`로 에이와 DB를 직접 읽고 `tenant_licenses`를 조회하지 않는다.

**실패 사례**
1. 새 상태 API가 `isFeatureOptedIn`을 그대로 쓰면, 에이와 DB가 잠깐 흔들린 순간 "꺼짐"이 나가고 **오늘의수학이 지점 전원을 정지시킨다.**
2. 반대로 지금의 503 규약을 그대로 쓰면 OFF가 "실패"로 읽혀 정지가 전파되지 않는다(가설이 이미 짚었다).
3. 오늘의수학이 직결 전송으로 돌고 있다면 지점을 꺼도 학생·진도는 계속 넘어간다. 운영 값은 확인하지 못했다.

**해결**
- 상태 API 규약: **꺼짐 = 200 + `enabled: false`**(권위 있는 답), **조회 실패 = 5xx**(답 없음 — 대상은 아무것도 바꾸지 않는다), 인증 실패 = 401. 스위치가 꺼져 있어도 이 API와 알림은 동작한다.
- 이 API는 `isFeatureOptedIn`을 쓰지 않고, 오류를 던지는 전용 조회를 쓴다.
- 대상은 "꺼짐"을 받았을 때 직전 상태가 "켜짐"이면 **한 번 더 확인하지 않고 바로 정지**한다(보호 우선). 대신 정지는 되돌릴 수 있는 사유 추가일 뿐이라 잘못 걸려도 다음 스냅샷이 푼다.
- 직결 전송은 계정 연동을 켜기 전에 API 전송으로 통일하거나, 직결 쪽에도 스위치 조회를 넣는다.

### B8. SSO 표가 재사용되고, 비밀 규칙이 양쪽에서 다르다

**근거**
- 표는 1회용이 아니다 — `jti`를 기록하지 않는다(`eywaSso.ts:17` 머리말 "1차안"). 만료 60초 + 시계 오차 30초(:30)라 실효 90초 동안 다시 쓸 수 있다. 표는 주소(`?token=`)에 실린다(`launch/route.ts:38-40`).
- 비밀 규칙이 다르다 — 에이와는 앞뒤 공백을 지우고 32자 이상을 요구한다(`connected-apps/sso.ts:24, 42-45`). 오늘의수학은 지우지 않고 16자 이상이다(`eywaSso.ts:29, 185`).
- 다른 계정으로 로그인돼 있어도 표의 계정으로 조용히 바꾼다(`api/sso/eywa/route.ts` 머리말 ⑴).

**실패 사례**
1. 자동 생성 계정은 비밀번호가 없어 **표가 유일한 자격**이다. 접근 기록이나 브라우저 기록에 남은 주소를 90초 안에 다시 열면 그 사람으로 들어간다.
2. 배포 환경변수 끝에 줄바꿈이 붙으면(에이와에서 실제로 겪은 사고 — `docs/gotchas.md` #72) 에이와는 지운 값으로 서명하고 오늘의수학은 줄바꿈이 붙은 값으로 검증한다 → 항상 서명 불일치인데 화면은 그냥 로그인 화면이라 원인이 안 보인다.
3. 직원 A가 자기 표 주소를 B에게 눌리게 하면 B의 브라우저가 A 계정으로 바뀌고, B가 만든 자료가 A 계정에 쌓인다.

**해결**
- 오늘의수학 DB에 1회용 기록 표(`jti` 기본키 + 만료 시각)를 두고, 세션 발급 전에 유일 삽입이 성공해야 통과시킨다. 기존 DB 안에서 끝난다. **자동 생성보다 먼저 배포한다.**
- 비밀 규칙을 양쪽 같게 한다(공백 제거 + 32자).
- 다른 계정으로 로그인돼 있을 때는 "○○ 계정으로 전환합니다" 확인을 한 번 거친다(권고 수준).
- 연결됐지만 정지된 계정이 SSO로 오면 로그인 화면이 아니라 "지금은 이용할 수 없습니다" 안내로 보낸다.

### B9. 삭제와 재생성 — 되살리기 금지와 흔적 보존

**근거**: 에이와 `deleteStaff`는 `auth.users`와 `public.users`를 모두 지운다(`account-actions.ts:372, 378-382`). 재입사자는 새 uuid를 받는다. 오늘의수학 `User`를 지우면 반·학생·시험지가 cascade로 지워진다(`schema.prisma:320, 401, 1003`).

**실패 사례**
1. 전수 대조가 "에이와에 없는 연결"을 "모르는 것"으로 보고 넘기면 삭제된 퇴사자가 영영 정지되지 않는다. 반대로 "명단에 없으니 삭제"로 읽으면 요구 2의 "삭제 금지"를 어긴다.
2. 오늘의수학에서 손으로 지운(`deletedAt`) 계정이나 거절한 계정을, 대조가 "계정 없음"으로 보고 새로 만들면 되살리는 것이다.

**해결**
- 에이와 삭제 = 연동 표에 `staff_deleted` 사유를 넣고 **행을 영구 보존**. 오늘의수학 계정·자료는 건드리지 않는다. 삭제 전파 금지(가설에 동의).
- 같은 사람이 재입사해 새 uuid가 오면 **새 연결**이다. 옛 계정으로 잇는 것은 최고관리자의 명시 작업으로만 한다.
- 대상 계정이 `deletedAt`이거나 `rejected`인 연결은 "대상 쪽에서 닫힘" 충돌로 보고만 하고, 새 계정을 만들지 않는다(`eywaUserId` 유일 제약이 이미 중복 생성을 막는다 — 연결 값을 지우지 않는 한).
- 연동이 관리하는 오늘의수학 계정은 하드 삭제하지 않는다는 것을 불변 조건으로 적는다.

## 3. 권고 (차단은 아니지만 계획에 넣을 것)

- **R1. 발급 대상을 메뉴 노출 규칙과 분리한다.** 노출 규칙(`connectedAppVisibleTo`, `apps.ts:58-62`)은 과목이 없는 직원을 전부 통과시킨다 — 원장·사무·상담·회계·열람 전용까지다. 이 규칙으로 계정을 미리 만들면 쓰지 않을 계정이 학생 정보에 닿는 채로 쌓인다. 추천은 §4.3 결정 2.
- **R2. 발급에서 빼야 하는 계정을 명시한다.** `system_role = student`(직원 표에 학생 로그인도 있다, `schema.ts:21-30`), `status ≠ active`, 로그인 계정이 없는 데이터 전용 직원(`account-actions.ts:31-33`의 404 경로), `@imported.local` 같은 임시 주소.
- **R3. 이름·이메일 전파 규칙.** 오늘의수학 이름은 50자(`schema.prisma:173`)라 잘라 넣어야 한다. 자동 생성 계정의 이메일은 표시용이다 — 에이와에서 이메일이 바뀌면 따라 바꾸되, 다른 계정과 겹치면 옛 값을 두고 충돌로 올린다. **이메일 변경으로 연결이 바뀌는 일은 없다.**
- **R4. 소유자 판정을 이메일에서 id로.** `isEywaOwner`(`src/lib/eywa/owner.ts`)와 `runSync.ts:135`는 이메일로 소유자를 찾는다. 관리자 화면이 이메일을 바꿀 수 있어(`[id]/route.ts:195`) 바뀐 날 동기화가 멈춘다.
- **R5. 토글은 지금처럼 DB 쓰기만 한다.** `toggleTenantLicense`에서 외부 호출을 기다리지 않는다. 운영자 콘솔의 카드에 "전달됨 / 적용됨 / 충돌 N건"을 따로 보여 준다. 일반 지점 화면에는 이 상태와 플랫폼 역할 이름을 노출하지 않는다(에이와 `AGENTS.md` 문구 원칙 · 지점/운영자 설정 분리).
- **R6. 알림 서명용 비밀은 새로 둔다.** `EYWA_SSO_SECRET`·`TODAYS_MATH_API_KEY`·`CRON_SECRET`과 따로 돌아야 한다(에이와 `contract.ts` 머리말의 "회전이 따로" 규약).
- **R7. 에이와는 SQL을 손으로 적용한다.** 새 표·트리거를 읽는 코드는 표가 없어도 죽지 않아야 한다(`docs/gotchas.md` #95). 특히 전 직원이 매일 지나는 경로(셸 레이아웃의 `getMyConnectedApps`)에 새 표 조회를 넣지 않는다.
- **R8. 위임·교시 담당은 1차에서 다루지 않는다고 명시한다.** 단일 소유 모델(`Class.userId`)로는 표현할 수 없다. 조용히 빠지는 것이 아니라 "담임만"이라고 문서와 운영자 화면에 적는다.
- **R9. 에이와 구현 전 확인.** 응답 뒤 실행·라우트 규약은 `node_modules/next/dist/docs/`를 먼저 읽는다(양쪽 `AGENTS.md`).

## 4. 소유권 · 불변 조건 · 실패 정책

### 4.1 누가 무엇의 원본인가 (추천 기본값)

| 항목 | 원본 | 대상 쪽 규칙 |
|---|---|---|
| 지점 사용 여부 | 에이와 `tenant_licenses`(todays_math) | 연동 사유 `branch_off` |
| 재직 상태 | 에이와 `users.status` | 사유 `staff_inactive`·`staff_pending` |
| 사람의 신원 | 에이와 `users.id` | 연동 표의 유일 키. 이메일은 표시·후보 |
| 반 담임 | 에이와 `classes.teacher_id` | `Class.userId` 이관 |
| 학생·수강 | 에이와(정본 판정 `isEnrollmentActiveOn`) | 기존 동기화 |
| 비밀번호 · 수동 정지 · 승인/거절 · 삭제 | 오늘의수학 | 연동이 쓰지 않는다 |
| 지점 내 권한(`isAdmin`·`branchRole`) · 검수 권한(`role`) · 메뉴 제한 | 오늘의수학 | 생성 때 최소값만 넣고 이후 안 건드린다 |
| 개인 자료(작업실·장바구니·문항·예측 회차) | 오늘의수학 사용자 | 어떤 사건에도 이동·삭제 없음 |

### 4.2 불변 조건

1. 에이와 사용자 하나 ↔ 오늘의수학 계정 최대 하나, 반대도 같다. 두 지점에 겸직하는 사람은 에이와 계정이 둘이고 오늘의수학 계정도 둘이다(에이와는 계정 = 지점 1:1 — `super-admin/server/actions.ts:205-214`).
2. 연결은 이메일 일치만으로 생기지 않는다.
3. 연동은 `suspendedAt`·`approvalStatus`·`deletedAt`·`passwordHash`를 쓰지 않는다.
4. 연동 사유는 넣은 주체만 뺀다. 사유가 하나라도 있으면 접근 없음.
5. 정지·삭제·OFF·롤백 어느 것도 오늘의수학의 행을 지우지 않는다.
6. 적용은 버전이 클 때만. 정지 세대가 크면 최종 상태와 무관하게 세션을 끊는다.
7. "없다"는 판정은 완전한 스냅샷을 받은 뒤에만 한다. 조회 실패는 "꺼짐"이 아니다.
8. 최고관리자 계정은 연동으로 잠기지 않는다.
9. 자동 생성 계정은 최소 권한(`teacher`)으로 태어난다. 에이와 역할이 올라가도 오늘의수학 권한은 자동으로 오르지 않는다(에이와 원장이 누군가를 관리자로 올리는 것만으로 오늘의수학 지점 전체 열람이 열리면 안 된다).

## 7. 기존 자원 안의 전달 구조와 지연 측정

**구조(새 서비스 없음)**
- 빠른 길: 에이와 앱 액션이 응답 뒤 발신기를 한 번 찌른다(슬랙의 `pokeSlack` 규약과 같은 자리). 발신기가 지점 리스를 잡고 오늘의수학 알림 주소를 부른다 → 오늘의수학이 같은 호출 안에서 에이와 상태 API를 읽고 적용한다.
- 느린 길: 앱을 안 거친 변경(직접 SQL·RPC·cron·스크립트)은 에이와의 분 단위 cron이 인박스에서 집는다. 에이와에는 이미 1분 cron이 있다(`vercel.json`의 `slack-dispatch`).
- 안전망: 오늘의수학이 주기적으로 상태 API를 당겨 온다. 오늘의수학에는 지금 하루 1회 cron 둘뿐이라 **새 cron이 필요하다**(Pro에서 분 단위가 되지만 호출 수가 늘어난다 — 1분 주기면 월 약 4만 3천 회, 5분이면 약 8천 6백 회).
- 바로가기 시점: 로컬 상태가 "없음·정지"인데 표가 유효하면 그 자리에서 한 번 조회한다(5.4의 45).

**정직하게 구분할 것**: 앱에서 누른 변경만 "수 초"를 기대할 수 있다. 앱 밖 변경은 cron 주기만큼(1~2분) 늦는다. 날짜가 넘어가서 생기는 변화는 대조 주기만큼 늦는다. 전달은 "적어도 한 번"이고, 정확히 한 번은 보장하지 않는다 — 대신 적용이 멱등이다.

**조정자의 "60초 자격 유효기간" 제안에 대한 의견**: 방향에 동의하되 **두 단으로 나눠야 한다.**
- 60초를 "이 시간이 지나면 접근 차단"으로 쓰면 에이와가 1분만 멈춰도 오늘의수학 연동 계정 전원이 수업 중에 끊긴다.
- 그래서 **재확인 주기(짧게, 60초 안팎)** 와 **재확인 실패 허용 한도(길게, 결정 5)** 를 따로 둔다. 재확인은 사용자마다가 아니라 **지점 단위 한 번**으로 전원을 갱신한다(지점 직원은 수십 명이라 스냅샷이 작다).
- 재확인을 요청 처리 중에 하면 그 요청이 에이와 왕복만큼 느려지고 동시에 여러 요청이 몰린다. cron으로 당기는 편이 단순하다. 요청 중 재확인은 바로가기 시점 한 곳으로 한정한다.
- 기준 시각은 응답을 받은 시각이 아니라 **요청을 보낸 시각**으로 잡는다(두 서버의 시계 차이와 응답 지연이 유효기간을 늘리지 못하게).
- 이렇게 하면 에이와가 살아 있을 때의 차단 지연 상한은 "재확인 주기 + 조회 시간"이고, 알림이 통째로 유실돼도 같다. 이 숫자는 canary에서 재기 전에는 약속하지 않는다.

**측정 계획**: 구간마다 시각을 남긴다 — ① 원본 커밋(트리거에서 `clock_timestamp()`; `now()`는 트랜잭션 시작 시각이라 쓰지 않는다) ② 발신 시작 ③ 알림 2xx ④ 대상 적용 커밋 ⑤ 정지된 세션의 첫 거절. canary에서 사건 종류별 30회 이상, 중앙값과 95%를 구간별로 보고한다. 웹훅 수신·권한 차단·열린 화면 갱신·장애 복구는 다른 구간이므로 한 숫자로 합치지 않는다(요구 6).

**비용**: 새 유료 서비스는 없다. 늘어나는 것은 함수 호출(cron·알림·상태 조회)과 DB 행(인박스·발송 기록 — 보존 기간을 정해 지운다)이다. 추가 청구가 없다고 보장하지 않는다.
