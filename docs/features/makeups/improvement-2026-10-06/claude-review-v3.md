## 3. 남은 필수 수정

### R1. 출결 트리거에 잠금을 넣지 말고, 겹침은 승인 시점에 닫는다

**v3의 설계**(116~117행): 접수는 `occ:` 키를 최신 결석 검증 전에 잡는다. 출결 AFTER 관측 트리거도 관련성 조기 종료 **전에** 같은 키를 잡는다. 이동이면 old/new 키를 정렬한다. 접수는 출결 행을 잠그지 않는다.

맞는 부분: 접수가 출결 행을 잠그지 않으므로 접수 쪽에서 "행 잠금 → 키" 역순은 생기지 않는다. 키를 검증보다 먼저 잡아야 한다는 것도 맞다. 겹침 창을 정확히 짚었다 — 지금은 정정이 커밋되기 전에 접수가 끝나면 트리거는 건을 못 보고 접수는 정정을 못 본다.

틀어지는 부분(출결 트리거 쪽):

1. **평소 출결 저장끼리 서로 막게 된다.** `lock_keys`는 배타 잠금이다(`0345a:19-27`). 지금 트리거는 원장과 무관한 저장에서 아무 잠금도 잡지 않는다(`0349b:80-83`). 출결 정정은 새 행을 넣는 방식이라 같은 칸을 동시에 저장해도 서로 기다리지 않는다. 조기 종료 전에 키를 잡으면 모든 출결 행 저장이 칸마다 배타 키를 쥔다. 여러 줄 저장은 실제로 있다(`attendance/server/actions.ts:130, 165, 201, 2259`, `seat/server/actions.ts:37, 433`). 같은 칸들을 다른 순서로 쓰는 두 저장은 새로 교착한다. old/new 정렬은 한 행 안의 두 키만 정렬할 뿐이다.
2. **잠금 순서가 뒤집힌다.** 문서화된 순서는 "키 → 케이스 행"이다(`0345a` 머리말). 여러 줄 출결 문장에서 트리거는 행마다 차례로 돈다. 첫 행의 관측이 케이스 행을 잠그고(`0349b:26-31`) 다음 행이 키를 잡는다 — "케이스 행 → 키"다. 접수는 "키 → 케이스 행"이다. 한 학생의 보강일 칸과 원수업일 칸을 한 번에 저장하는 출결과, 그 원수업 칸의 접수가 겹치면 교착한다. 지금 코드에서는 생기지 않는 교착이다. 계획이 스스로 금지한 "행 잠금 → 사건 잠금 역순"이 이 경로로 들어온다.
3. **실패 격리 밖에 놓일 수 있다.** 지금 조기 종료는 `begin … exception` 블록 **앞**에 있다(`0349b:80-84`). "조기 종료 전에 획득"을 글자대로 하면 잠금이 격리 밖에 놓이고, 교착 오류가 출결 저장 자체를 실패시킨다. v3는 격리를 보존한다고만 적고 잠금이 그 안에 있어야 한다고는 적지 않았다.
4. **잠금 수에 상한이 없다.** 과목·모드와 무관하게(영어, 꺼진 지점, 메모만 고치는 UPDATE 포함 — 트리거에 열 조건이 없다, `0349b:114-117`) 행마다 트랜잭션 끝까지 쥐는 키가 생긴다. PostgreSQL의 권고 잠금은 공유 잠금 풀을 쓰고 풀이 차면 서버 전체가 잠금을 못 준다. 대량 저장·백필에서 실제로 위험한 크기인지는 운영 설정과 묶음 크기에 달렸고 **확인하지 못했다**. 다만 "무관한 저장은 인덱스 조회 두 번으로 끝난다"는 지금 설계의 성질은 확실히 사라진다.

1~3은 소스만으로 확정되는 결함이고, 구현 뒤 병행 시험 관문에서 발견되면 계획을 다시 고쳐야 한다. 그래서 지금 고친다.

**좁은 대안(권장): 출결 경로는 그대로 두고, 권리가 생기는 첫 지점에서 닫는다.** 접수는 권리를 만들지 않는다(승인 대기). 권리가 생기는 것은 승인이다. 승인은 사람이 나중에 하므로 겹친 두 트랜잭션은 그때 이미 커밋돼 있다.

116~117행을 아래로 바꾼다:

> - 출결 저장 경로는 바꾸지 않는다. 0349b의 관측 트리거와 관측 함수에 새 잠금을 넣지 않고 정의를 그대로 둔다.
> - intake는 기존 `occ:` 키를 최신 결석 검증보다 **앞선 별도 문장**에서 잡는다(검증 조회가 잠금 대기 뒤의 스냅샷을 읽게). intake는 출결 행을 잠그거나 고치지 않는다. intake가 관측을 부르기 전에 닿는 케이스 행은 자기 케이스를 포함해 id순으로 한 번에 잠근다.
> - 정정이 먼저 커밋되면 stale 접수는 거절된다. 접수가 먼저 커밋되면 이후 정정의 기존 관측이 source_conflict를 연다.
> - 정정이 아직 커밋되지 않은 사이에 접수가 끝난 경우는 **승인 명령이 닫는다**. cmd_approve는 케이스를 잠근 뒤 원수업 칸을 기존 `observe_attendance_cell`로 한 번 관측하고, 그 뒤 이 건에 열린 source_conflict가 있으면 승인을 거절한다(확인 항목을 처리한 뒤 다시 승인). 사람이 같은 근거로 이미 처리한 항목은 다시 열리지 않는다. 승인 분량·정책·자기 검토 규칙은 그대로다.
> - 남는 한계: 접수 커밋과 승인을 모두 걸쳐 열려 있는 출결 트랜잭션(긴 일괄 작업)은 다음 출결 저장의 관측이나 대사 실행이 잡는다. 검증 기록에 적는다.

근거: 관측 함수는 같은 근거로 사람이 닫은 항목을 다시 열지 않는다(`open_recon`은 내용이 달라졌을 때만 다시 연다, `0345a:116-121`). 그래서 "처리 → 승인"이 되풀이 거절에 걸리지 않는다. 지금 승인은 원수업 칸을 보지 않는다(`0346b:30-80`).

함께 고칠 곳:
- 구현 순서 표 P2: "intake SQL/원결석 관측 잠금" → "intake SQL · 승인 시 원수업 칸 관측".
- 수용 기준 12: "정정 먼저 커밋 → 접수 거절 / 접수 먼저 커밋 → source_conflict / 겹침 → 건은 생기고 승인 때 source_conflict가 열려 승인 거절, 처리 뒤 승인 성공. 여러 줄 출결 저장(같은 학생의 원수업일·보강일을 한 문장에)과 접수·참여 기록을 함께 돌려도 출결 저장은 항상 성공. 0349b의 함수·트리거 정의가 적용 전후 같음을 대조. old/new 칸 이동, 기존 occurrence 중복 접수."
- 적용과 되돌리기: 백업 대상에 0346b(승인)를 넣고, 0349b는 바꾸지 않는다고 적는다.
- 유지 조건의 "분량 승인 … 바꾸지 않는다"에 "승인에 원수업 칸 관측과 열린 확인 항목 거절을 더한다"를 예외로 적는다.

승인을 거절하지 않고 **경고만** 하는 쪽을 택해도 받아들인다. 그때는 "승인은 진행하고 결과에 경고를 싣고 화면에 보이며 source_conflict가 종결을 막는다"를 명시하고 수용 기준에 그 경우를 넣는다. 둘 중 하나를 계획에 적어야 한다. 권장은 거절이다 — 권리를 주기 전에 사람이 본다.

**출결 쪽 잠금을 꼭 유지하겠다면** 아래를 전부 계획에 적어야 한다. 권장하지 않는다: (가) 트리거는 공유 잠금, 접수·연결은 배타 잠금. (나) 잠금 획득을 실패 격리 블록 안에 둔다(조기 종료의 위치를 바꿔야 한다). (다) 위 2번의 역순 교착이 남는다는 것과 그때 출결은 성공하고 실패 작업이 남는다는 것. (라) 트랜잭션당 키 수 상한과 상한을 넘었을 때의 동작. (마) 꺼진 지점·시범 밖 과목에서의 동작. (바) 수백~수천 줄 저장으로 실제 잠금 수를 재는 관문.

### R2. 대시보드의 새 참여는 "반 집합 ∪ 내가 맡은 회차"로 거른다

**요청한 결정**: 담당 반이 없는 배정 강사도 대시보드에서 자기가 맡은 새 보강을 본다. 반 명단 접근은 넓히지 않는다.

**v3의 문장**(77행): "대시보드의 native는 DB의 participant 범위를 따르고 legacy 반 집합으로 다시 잘라 버리지 않는다."

이 문장은 결정보다 넓다.

1. 대시보드의 강사 스코프는 로그인 계정이 아니라 `effectiveTeacherId()`다. 실 강사뿐 아니라 겸직 강사뷰와 '다른 강사 뷰'도 강사 스코프다(`src/lib/auth/view-mode.ts:33-52`, `dashboard/overview/server.ts:551, 632`). 이때 RPC를 부르는 계정은 지점 전체 읽기 권한자이므로 DB는 **지점 전체** 참여를 돌려준다. 반 집합 거름을 없애면 강사뷰 카드에 지점 전체 보강이 실린다.
2. 실 강사의 DB 범위에는 "지금 담당하는 같은 과목 반의 재원 학생"이 들어 있다(`0344c:61-63`). 내 반 학생이 다른 반에서 다른 강사에게 받는 보강까지 카드에 실린다.
3. 명단은 같은 문제를 이미 풀었다. 지점 전체 읽기 계정은 참여를 전부 받으므로 "내 담당 반 ∪ 내가 맡은 회차"로 거른다(`src/features/makeups/roster-merge.ts:31-51, 58-72`).

77행 첫 문장을 아래로 바꾼다:

> 대시보드의 native는 DB가 돌려준 참여 가운데서 고른다. 강사 스코프가 없는 화면(관리자 뷰)은 전부 보인다. 강사 스코프가 있는 화면(실 강사·겸직 강사뷰·다른 강사 뷰)은 **출결 반/합류 반이 그 강사의 이번 주 반 집합에 있는 참여 ∪ 실시 강사가 그 강사인 참여**만 보인다(명단의 `rosterNativePairs`와 같은 규칙). 담당 반 0개인 배정 강사는 둘째 조건으로 본인 참여를 본다. 같은 과목 재원 학생이라는 이유만으로 남이 맡은 다른 반의 참여를 싣지 않고, 지점 전체 읽기 계정의 강사뷰에 지점 전체를 싣지 않는다. 출결 반 없는 참여는 관리자 뷰에서는 전부, 강사 스코프에서는 그 강사가 맡은 것만 '출결 반 확인 필요'로 보인다.

수용 기준 10에 한 줄을 더한다: "겸직 강사뷰·다른 강사 뷰의 카드에 지점 전체 참여가 실리지 않는다. 내 반 학생이 다른 강사에게 다른 반에서 받는 보강은 실리지 않는다."

78행(기존 예약은 이번 주 반 집합, 새 참여·새 일정은 DB의 오늘 범위, 주 중 담당 변경 때 다를 수 있음, 전 과목·한 달과 수학·선택 기간의 총수를 같다고 주장하지 않음)은 그대로 좋다. 차이를 숨기지 않고 적은 것이 맞다.

## 4. 요청받은 확인

## 5. 권고 (승인 조건 아님)

- 67행 "검토 완료 + 확인 필요로 각각 표시"의 확인 필요가 무엇으로 정해지는지 한 줄로 적으면 좋다(예: 그 참여에 닿는 열린 대사 항목).
- 잠금 그래프 문서에 넣을 항목: 접수의 `cfg(공유) → cmd → occ → 케이스 행(id순) → 대사·작업 행`, 연결의 `예약 행 → occ·stu → 케이스 행`, 승인의 `케이스 행 → 관측`. 승인의 관측이 자기 건 밖의 케이스 행(그날 그 반이 출결 반인 참여의 건)을 잠글 수 있으므로 승인도 닿는 케이스를 id순으로 한 번에 잠근다.
- 검증 도우미가 `stable`이어도 되지만 잠금과 같은 SQL 문장 안에서 부르지 않는다는 것을 구현 메모로 남긴다.
- 104행의 `MakeupAddFlow`·`MakeupConfirmDialog`·`OpenWindowButton`은 실제로 있다(`src/features/attendance/components/makeup-add-flow.tsx`, `makeup-confirm-dialog.tsx`, `src/components/workspace/open-window-button.tsx`).

## 6. 확인하지 못한 것

- 운영 DB의 잠금 풀 크기와 실제 출결 일괄 저장의 최대 줄 수. R1의 4번은 이 값에 따라 크기가 달라진다. 1~3번은 이 값과 무관하다.
- 교착과 겹침 창은 SQL 판독으로 추론했다. 실제 병행 실행으로 재현하지 않았다.
- 승인에 거절 조건을 더했을 때 기존 pgTAP 시험과 충돌하는지. 시험 파일은 읽지 않았다.
- 강사 미니셸에서 `/makeups/new`가 열리는지(v3가 P2 시작 전 확인으로 넣었다).
- 새 조회·일정 RPC의 실제 성능(기준 24의 관문).

## 7. 재검토 조건

v4가 R1과 R2를 §3의 문구(또는 같은 뜻의 문구)로 반영하면 남는 필수 항목이 없다. 그 해시로 APPROVE 여부를 다시 판정한다. R1에서 경고만 하는 쪽이나 출결 쪽 잠금 유지를 택하면 §3에 적은 조건이 계획에 들어 있어야 한다.
