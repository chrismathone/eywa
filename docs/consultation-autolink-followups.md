# 등록상담 ↔ 학생 자동연결 — 후속 과제 (deferred)

> 배경: 2026-07-15 마이그 `0107a_robust_consultation_autolink.sql`로 **로버스트 자동연결**을 세팅했다
> (학교표기 정규화 + 이름/학교/학년 · 전화 다단 매칭, students·consultations 양방향 트리거, 동명이인 방어).
> "배정 완료" 컬럼은 저장 상태가 아니라 파생 배지(`assignedClassCount>=1` = 상담 `student_id` 연결 + 학생 활성수강≥1).
> 상세·매칭 로직은 CLAUDE.md 메모리 `project_enrollment-assign-badge-backfill` 및 0107a 파일 주석 참조.

> 아래는 이번에 **의도적으로 미룬** 항목들. 필요할 때 이 문서를 열어 착수한다.

## 1. 진급 케이스 주기 검토·연결 도구 (owner "데이터 정리" 버튼)
0107a 자동 트리거는 **안전한 tier1/2**(이름+학교정규화+학년 / 전화+이름)만 자동 연결한다.
**진급(초6→중1, 중3→고1)으로 학년·학교가 바뀐 같은 아이**는 "이름 + (학년차 = 상담 후 지난 학년도 3월 경계 수)"로만
매칭되는데, 이건 **동명이인 오연결 위험**이 있어 트리거에서 자동화하지 않았다(전화가 있으면 tier2로 자동 잡힘 — 전화 없는
진급만 사각).

- **제안**: owner `?tab=data`("데이터 정리")에 *"미연결 상담 검토·연결"* 버튼. 서버가 진급 모델로 후보를 계산해
  **표로 보여주고**(상담 ↔ 매칭 학생, 근거 tier, 학년차/경계), 관리자가 체크한 것만 연결. 자동이 아니라 **리뷰-후-연결**.
- **매칭 로직**(이미 검증됨, 2026-07-15 일회성 정리에 사용): 학년 사다리(초1..고3 = 1..12), 3월 경계수 =
  상담일~오늘 사이 3/1 통과 횟수, `gradeLevel(student) - gradeLevel(consult) == 경계수` + (레벨전환 초→중/중→고 **또는**
  같은 학교) + 유일 + 활성수강. 동레벨 학교변경(초3→초4에 초등학교가 바뀜)은 전학/동명이인 구분이 안 되니 별도 "검토권장"으로.
- 참고: 2026-07-15엔 이 로직으로 23건을 수동 연결(A+B 고신뢰)했고, 아래 4건(동레벨 학교변경)은 남겨뒀다.

## 2. 검토권장 4건 — 전학 여부 확인 후 연결
초3→초4인데 **초등학교가 바뀐** 케이스(전학이면 동일인, 아니면 동명이인). 원장 확인 필요:
- 이연아 [초3·달성초] → 학생 [초4·달산초]
- 최예준 [초3·서동초] → 학생 [초4·달성초]
- 안도현 [초3·신천초] → 학생 [초4·침산초]
- 김윤후 [초4·달성초] → 학생 [초5·칠성초]

확인되면 해당 상담 `student_id`만 채우면 배정완료로 이동(outcome은 이미 enrolled).

## 3. 학교명 표시/저장 정규화 (~초/~중/~고 통일)
현재 0107a의 `eywa_school_norm`은 **매칭용**(비교 시에만 정규화)이라 DB 저장값·화면 표시는 원본 그대로("신암초등학교"·"신암초"
혼재). 원장이 "항상 ~초/중/고로 통일" 표시/저장을 원하면 별도 작업:
- **표시만**: 목록/카드 렌더에서 `eywa_school_norm` 상당의 클라 헬퍼로 축약 표시(저장값 불변, 되돌리기 쉬움).
- **저장까지**: students·enrollment_consultations의 school/prospect_school를 일괄 정규화 마이그 + 입력 폼 정규화. ⚠️ 비가역이라
  신중히(원본 훼손·다른 학교 충돌 검토). 매칭은 이미 정규화로 해결되므로 표시-only가 저비용·저위험.

## 4. (선택) 진급 자동 tier 추가
동명이인 오연결을 감수하고 진급까지 트리거로 자동화하려면, `eywa_cs_match`에 "레벨전환 진급" tier를 추가하고 유일성 가드를
강화(활성수강 있는 유일 매칭 + 레벨전환만). 단 자동 오연결 = 개인정보 사고라 **기본은 1번(리뷰-후-연결)을 권장**.
