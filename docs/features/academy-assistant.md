## 1. 흐름

`POST /api/assistant/ask`(NDJSON 흐름 — `protocol.ts`):
1. 문(`gate.ts`) → 지점 AI 라이선스(`requireAiLicense`) → 15분(`ASSISTANT_RUNNING_MS`) 넘은 '도는 중' 줄을 실패로 닫기 → 하루 100번 · 자리 확인(`store.admission` — 같은 대화가 도는 중 · 동시 3개 참) → 대화·'도는 중' 줄 저장(빈 자리 `run_slot`부터). 🔴 **동시에 3개까지 · 대화마다 하나**(§7-3) — 두 탭에서 동시에 물어도 DB 고유 색인 둘(`assistant_messages_running_slot_idx` 사람·자리 · `assistant_messages_running_thread_idx` 대화, 멈춤 누른 질문은 제외 · s2_0034)이 막는다(앱 확인만으로는 경쟁 상태). 막히면 `429 { code: "busy" }` — 실패가 아니라 안내.
2. 비서 DB 연결(`executor.ts`) — 먼저 보기 갱신(바뀌었을 때만, service_role RPC).
3. AI 루프(`agent.ts`, 조회·차례 한도 없음 — §7-2 · 마무리 = 고정 기한 200초 전(차례 도중이면 다음 조회를 쓰던 응답을 끊고 기록에 넣지 않은 채 곧장 보고서를 부탁) 또는 직전 입력 15만 토큰 초과 또는 원장이 누른 '바로 결과 보기'(§7-3) · 그 뒤 조회·표 구조·전수 조회 요청은 실행하지 않음) — 도구 `describe_table` · `run_sql` · `survey_entity` · `render_report`. 표 구조 조회·SQL 검사기의 일시 오류는 그 도구만 실패로 돌려준다(질문 전체를 버리지 않는다).
   - `terra-client.ts`가 OpenAI Responses의 Terra low 한 곳만 호출한다(`store:false`, 도구 병렬 호출 없음). 도구 결과의 `call_id`와 암호화 reasoning을 다음 차례에 그대로 잇는다. 기존 실행기의 내부 메시지 계약은 어댑터 안에서 변환한다.
   - 캐시는 Responses의 자동 접두 캐시를 사용한다. 내부 호환 계약의 `ephemeral` 힌트는 OpenAI에 보내지 않는다. 적중량은 실제 `cached_tokens`로 기록하며 적중률·모델 간 공유를 보장하지 않는다.
   - 진행 단계 `step` 이벤트 — Responses 도구 입력 시작·증분을 기존 진행 이벤트로 바꿔 단계를 열고, 들어오는 `purpose`를 바로 붙인다.
4. 답 저장(보고서 · 조회 · 단계 · 사용량) · 감사 `assistant_ask` · 사용량 장부(`recordUsage`, provider `openai`, feature `academy_assistant`, 전용 키 우선 — 제공자가 끝까지 보고한 사용량만 기록한다. 중간에 끊겨 사용량이 없으면 임의로 추정하지 않는다. 캐시 입력·추론 출력을 이중 계상하지 않는다). 사람이 누른 멈춤은 실패로 적지 않고 고정 기한은 늘 실패로 적는다. 저장이 실패하면 표·차트 자료를 뺀 보고서로 한 번 더 저장하고, 그래도 안 되면 상태만 '실패'로 닫고(`markFailed`) 화면에도 실패로 보낸다(보인 답과 저장본이 어긋나지 않게 · 감사 outcome도 실제 저장 결과).
- 🔴 화면 연결이 끊겨도 끝까지 돌고 저장한다(`after`). 멈춤 = 사람이 누른 '멈춤'(`cancel_requested_at`, 2초마다 확인) 또는 **고정 기한 760초**(`ASSISTANT_HARD_DEADLINE_MS` — 라우트 기한 800초에 함수가 죽으면 저장·감사·사용량이 통째로 빠지므로 스스로 끊고 실패로 저장).
- 멈춤 순서 — 화면은 서버에 **알림이 끝난 뒤** 흐름을 끊는다(그 사이 '멈추는 중…' — 바로 다시 물어도 '앞 질문을 만드는 중'에 걸리지 않게). 번호(`started`)로 보내고, 실패하면(세션 만료·500·망) 화면이 보낼 때 만든 번호로 `POST /api/assistant/messages/<clientRef>/stop?by=ref` 한 번 더 · `keepalive`(동시에 여러 질문이 돌아 옛 '지금 도는 내 질문'(`current`)은 어느 것인지 몰라 없앴다). 번호를 받기 전에 누르면 기다렸다가 번호가 오자마자 알리고, 15초가 지나도 안 오면 `clientRef`로. 멈춘 질문은 마무리 중이어도 바로 다시 물을 수 있다.
- 다시 읽기 — 저장본이 '도는 중'이면 3초마다 `GET /api/assistant/threads/[id]?status=1`(도는지만)으로 묻고, 끝났으면 대화 전체를 한 번 읽는다(최대 15분 — 매번 표·차트 자료를 받지 않게).

## 7-2. 전수 조회 · 조회 한도 없앰(11-06 밤 · 원장 *"DB 전체 조회하고 답변하는거 맞아? … 하나도 빠짐없이 남김없이"* · *"한도 두지마"*)

- **왜** — '고등M 중2 PS3A 반 총괄 분석'이 조회 12번 한도에 막혀 표 11개만 보고 영상 숙제(검사·자동 판정·링크)·성적·원스크린 기록을 아예 안 봤다. 비서가 '볼 만한 표'를 스스로 고르는 구조라 빠짐이 생긴다.
- **전수 조회(`server/survey.ts` · 도구 `survey_entity`)** — 대상(원생·반·강사)이 정해지면 서버가 그 대상과 이어진 칸이 있는 보기를 **칸 이름 규칙으로 전부** 찾는다(원생 `student_id`·`…_student_id`·`student_a/b` · 반 `class_id`·`…_class_id` · 강사 `teacher_id`·`user_id`·`…_user_id`·`created_by`·`recorded_by` 등 + 수업보고서 `teacher_name` 글자 · 대상 자신의 표는 `id`). 표 목록을 손으로 적지 않아 새 표·칸이 생기면 저절로 들어간다. 12개씩 UNION ALL 한 문장으로 전체·기간·최근 날짜를 세고 — **비서 조회와 같은 길**(SQL 검사기 → 실행기 · 지점 증표 · 읽기 전용 · 8초 · 비용 상한) — 막힌 묶음은 반씩 쪼개 다시, 끝내 막힌 표만 '세지 못함'. 기간 날짜 식은 '일이 일어난 날'에 가까운 칸부터(수업보고서는 `coalesce(covers_date, report_date)` — covers_date만 보면 PS3A 402건이 기간 0건으로 나왔다).
  - 실측(11-06 · 읽기 전용): PS3A 반 → 보기 278개 중 이어진 57개 · 묶음당 0.02~0.8초 · 영상숙제 검사 26 · 자동 판정 26 · 숙제 영상 링크 16 · 원스크린 165 · 상담 17 · 수업보고서 239(기간) 등.
  - **리뷰 반영(11-09)**: ① 날짜 칸은 '일이 일어난 날' 먼저(성적 taken_on · 시험 test_date · 보강 makeup_date · 학부모 글 posted_at … 비면 입력 시각으로 메운다) → 시작·끝이 있는 줄(수강 start/end · 위임 from/to · 시간표 valid_from/to 등)은 **기간이 겹치는 줄** → 입력 시각(created_at). 결재·제출·완료 같은 처리 시각은 쓰지 않는다(대기 중인 줄이 기간에서 빠졌다) ② 강사는 `…_by` 칸 전부(대신 보강 taught_by · 후속조치 handled_by …, 고친·처리 흔적 updated_by·moved_by·cancelled_by 등은 뺌) + **이 기간에 맡은(맡았던) 반을 거친 표**(onto_class_teachers 중 맡은 기간이 조회 기간과 겹치는 반 · 폐지·보강용 반·기간 전에 끝난 반 제외 — `taughtClassesSql` · 반 id를 늘어놓지 않고 전수 조회 SQL의 `with` 절이 같은 조건으로 다시 고른다(검사기 8,000자 상한) · 영상 숙제 검사·반 출결처럼 강사 칸이 없는 반 자료 · '맡은 반을 거쳐'로 따로 센다 · 그 반의 기간 자료 전체라 다른 강사 몫도 섞인다고 AI에게 알린다) · 이름이 같은 사용자가 있으면 이름 글자(teacher_name)로는 세지 않는다 ③ 문서에 `internal`로 적힌 표(알림 구독·연동 코드 등)는 세지 않는다 ④ 대상 확인 — id가 그 종류의 표(students·classes·users)에 없으면 돌려보내고, 이름은 DB 이름으로 ⑤ 없는 날짜(평년 2월 29일)·시작 > 끝은 받지 않는다 ⑥ 반씩 쪼개기는 그 표 탓일 수 있는 조회 오류에만(실행기가 오류를 `query`/`connection`으로 가른다 — SQLSTATE가 없거나 08·57P·25P·53300이면 연결 쪽 · 바로 실패 — AI가 run_sql로 잇는다) · 실행 횟수 상한(묶음 수 × 9) · 전수 조회 한 번 2분 · 멈춤·마무리 시각이면 남은 묶음은 '세지 못함' ⑦ '자세히 봄' = 그 전수 조회 **뒤의** 조회가 읽은 표(대상 id를 찾던 앞 조회는 세지 않는다 · 대상이 여럿이면 SQL에 그 대상 id가 든 조회만, 아무 id도 없으면 가장 최근 대상) · 같은 표의 '직접'과 '맡은 반' 줄은 따로(`key`) · 여러 원본을 합친 보기(반 담당)는 원본을 봤다고 '자세히 봄'이 되지 않는다 ⑧ 전수 조회 단계는 제 종류(`survey`) — '조회 N번'에 세지 않고 표 구조 확인과 묶여 '다시 시도'로 읽히지 않는다.
  - AI는 이 지도를 받고 '기간 안 자료 있음' 표를 **하나도 빠짐없이** run_sql로 본다(안 볼 표는 까닭과 함께 '이번에 깊이 보지 않은 자료'). 보고서 끝에 서버가 **'확인한 자료 범위'**(센 표 수 · 자료 있는 표마다 기간 건수·최근 · ✓ 내용 조회(옛 이름 '자세히 봄' — §7-9) / 건수만 셈 · 세지 못함)를 붙인다 — 원장이 빠진 것을 직접 본다.
- **한도 없앰** — 조회 횟수(12) · 차례(14) 한도를 뺐다. 추론 강도는 모델·생각 깊이로만 나뉜다. 남은 물리적 한계 둘: ① 실행 시간 — 라우트 `maxDuration` 800초(Vercel Pro 최대) · 고정 기한 760초 · 그 200초 전부터 마무리(더 조회하지 않고 보고서 — 차례 도중이면 쓰던 응답을 끊는다: 차례가 끝나기를 기다리면 보고서 쓸 시간이 모자라 모은 결과가 통째로 사라졌다 · 적대 리뷰 11-09) ② AI가 한 번에 읽는 분량 — 직전 차례 입력이 15만 토큰을 넘으면 같은 마무리('적음' Haiku는 10만 토큰을 넘으면 단가가 5배라 7만 — 판정은 직전 차례 입력이라 한 차례 조회 결과가 더 붙을 여유 3만). 마무리 뒤 3차례 안에 보고서가 없으면 멈춘다. '도는 중'으로 보는 시간 15분.

## 7-3. 동시에 3개 · 바로 결과 보기 · 목록에서 지우기(11-06 밤 · SQL s2_0034)

- **동시에 3개까지**(원장 *"대화를 여러개 동시에 시작할 수 있는지 … 정상적인 동작으로 인식되게"* → '동시에 3개까지'를 고름 — 한도를 없애 답 하나가 최대 13분쯤 걸린다).
  - 대화마다 하나(같은 대화의 둘째 질문은 앞 답을 모르고 답하게 된다) · 사람당 셋. DB 색인 둘이 마지막에 가른다(§1) — 앱은 빈 자리(`run_slot`)로만 넣고, 23505가 자리 색인이면 다음 자리 · 대화 색인이면 `busy_thread`.
  - 화면(`assistant-state.ts`): `inflight`가 차례 배열 · 대화마다 제 손잡이(`use-assistant.ts` `Run` — 흐름 · 질문 번호 · `clientRef` · 번호 전 멈춤/마무리). 멈춤·마무리는 그 대화의 차례로.
  - **다른 탭·기기·새로 고침 뒤에도 정상으로 보이게** — 목록 응답에 `running`(멈춤 누른 것·15분 넘은 것 제외) · 저장본 '도는 중'도 센다(`runningThreadKeys`). 그 대화에서는 보내기를 막고 "이 대화는 아직 앞 질문의 답을 만드는 중…" · 셋이면 "답은 동시에 3개까지…". 그래도 서버가 `busy`로 받지 않으면 빨간 실패 카드 대신 보낸 차례를 거두고(`ask/rejected`) 입력칸 아래 안내 + **보낸 글을 입력칸에 되돌린다**(그사이 새로 쓴 글은 덮지 않는다) + 목록을 다시 읽는다. 다른 탭에서 도는 대화가 목록에 있으면 판이 열린 동안 15초마다 목록을 다시 읽어 끝난 것을 푼다.
- **'바로 결과 보기'**(원장 *"'여기서 조회 끝내고 바로 결과 출력' 버튼 만들자. 그럼 조회 멈추고, 지금까지 조회한 내용으로만 결과 출력"*) — 입력칸의 '멈추기' 옆. 조회를 하나 마친 뒤 누를 수 있다(근거 없는 보고서를 막는다).
  - `POST /api/assistant/messages/[id]/finish`(번호 전이면 `?by=ref`) → `wrap_requested_at` → 도는 쪽(`ask.ts`)이 2초마다 보고 `wrapSignal`을 끊는다.
  - `agent.ts` — 마무리 까닭 `user`: AI가 다음 조회를 쓰는 중이면 그 응답을 끊고 **기록에 넣지 않는다**(덧붙이기만 — 생각 블록이 어긋나지 않는다) → 마지막 사람 차례에 마무리 부탁을 붙여 곧장 보고서. 이미 보고서를 쓰기 시작한 응답은 끊지 않는다. 남은 도구 호출은 `cause: "user"`(화면은 옅은 멈춤 '여기서 조회를 끝냄' — 막힘이 아니다) · 전수 조회는 남은 묶음을 세지 않고 '세지 못함'으로 남긴다(빠진 것을 숨기지 않는다).
  - 보고서 위 한 줄(`cutShort` — 서버가 붙인다): '바로 결과 보기'로 여기서 조회를 끝내고 정리한 답 · 시간이 다 돼 · 읽은 자료가 많아. 감사 `assistant_ask` metadata에도 `cutShort`.
  - '멈추기'는 그대로 질문째 버린다('질문을 멈췄습니다').
- **목록에서 지우기**(원장 *"대화 지우기도 현재 대화 가장 위로 올라가야 지울 수 있는데, 대화 목록에서 x 버튼 마우스 오버시에 나오도록"*) — 목록 행에 마우스를 올리면(키보드 초점 · 터치 화면은 늘) 날짜 자리에 x → 그 행이 '지울까요?' 확인으로 바뀐다(초점 '취소' · Esc는 확인만 닫고 초점은 x로). 대화 머리의 '대화 지우기'는 뺐다. 도는 대화는 x 없음. x는 여는 버튼 옆 형제라 버튼 안 버튼이 아니다 — 앱 규약 '목록 행 안 아이콘 버튼 없음'의 원장 지시 예외.
- 로컬 시험(PGlite · 운영 표 구조) 22건(옛 앱이 자리 번호 없이 넣은 줄 · 되돌린 뒤 새 칸 없음 포함): 자리 1~3 · 넷째는 자리 색인 · 자리 4는 check · 빈 자리여도 같은 대화 둘째는 대화 색인(메시지에 색인 이름) · 멈춘·끝난 질문은 자리를 비움 · `client_ref`로 마무리 표시 · 두 번 적용 · 되돌리기(사람당 하나만 남김) → 다시 적용.
- **적대 리뷰 반영(11-09)**: ① 도는 대화는 지우지 않는다(서버 `deleteThread`도 409 — 지우면 목록에서 사라져 멈출 화면이 없는 질문이 자리를 최대 13분 차지했다 · 확인을 열어 둔 사이 돌기 시작하면 확인을 거둔다) ② 다른 대화로 옮긴 뒤 끝난 대화가 '도는 중'으로 남아 자리를 세던 것 — 판이 열린 동안 15초마다 목록 + 그 대화들의 '도는지'를 다시 읽는다(`staleRunningThreadIds`) ③ 멈추면 목록 '도는 중'을 바로 내리고, 멈춘(정리 중인) 질문은 저장본·`?status=1`에서도 도는 것으로 보지 않는다 ④ '바로 결과 보기'는 조회를 마쳤거나 전수 조회를 시작한 뒤(표 구조만 본 것은 자료가 아니다) ⑤ 이 화면이 받지 않는 도는 질문(다른 탭·새로 고친 뒤)에도 '바로 결과 보기' · '멈추기'(질문 번호로) ⑥ 번호 전 멈춤이 화면 번호로도 못 찾으면 끊지 않고 번호를 45초 더 기다린다(끊으면 서버만 돌며 자리를 쥔다) ⑦ 배포 전에 열린 옛 화면의 `messages/current/stop`은 가장 최근 질문 하나를 멈춘다 ⑧ 받지 않은 질문의 글은 보낸 대화를 보고 있을 때만 입력칸에 되돌리고, 안내는 자리가 나면 내린다 ⑨ 목록 조회와 '도는 대화' 조회는 함께(하나가 실패해도 목록은 낸다) ⑩ 늦게 온 목록이 방금 생긴 대화를 빼지 않는다 ⑪ 지운 뒤 초점은 '새 질문' · 지우는 중 Esc는 확인을 닫지 않는다 · 목록을 접으면 확인도 닫는다 · 입력칸 알림은 늘 있는 `aria-live` 칸 ⑫ 연결 상한 12. 재리뷰 반영: 원장이 끝낸 단계 표식(`cause: user`)을 화면이 버리지 않는다 · 자리 없음 안내는 목록을 다시 읽기 전까지만(그 뒤엔 목록이 말한다) · 다른 곳에서 지운 대화(404)는 도는 표시를 풀고 목록에서 뺀다 · 번호 전 멈춤은 번호가 언제 와도 그 번호로 · 늦게 온 목록이 방금 한 지우기·이름 바꾸기를 되돌리지 않는다 · 자료를 읽기 전에 누른 '바로 결과 보기'는 첫 자료를 읽은 뒤에 든다(다른 탭 버튼 포함).
- 적용 순서: **원장 승인 → s2_0034 운영 적용 → 앱 배포**(새 앱은 새 칸을 쓴다). SQL만 들어간 몇 분은 옛 앱이 `run_slot` 없이 넣어 사람당 하나 막기가 앱 확인뿐이다(대화마다 하나는 색인이 막는다).

- **답 품질:** 기존 v5의 역할·단위·중복·분모·기간·승인 주체·직접 조회·연락 첫마디 규칙과 보고서 검사·같은 모델의 재작성 절차를 유지한다. 잘못된 JSON을 임의 복구해 저장하거나 다른 모델로 넘기지 않는다. 도구 연결·암호화 reasoning·취소·진행 표시·사용량 계약은 전용 어댑터로 잇는다.
- **시각화:** 비교·추이·순위·구성에는 맞는 핵심 차트를 고르고, 차트에 맞는 모양으로 조회한다. 원그래프는 중복 없는 구성만, 서로 다른 단위·미완결 기간·빈 값을 섞지 않는다. 긴 이름·많은 항목의 막대는 가로 배치와 행별 높이로 표시한다. 실제 컴포넌트의 PC·390px 화면에서 막대·추이·원그래프, 범례·단위와 입력창을 확인했다.
- **이름 링크:** 표 이름 열의 `link: {entity: student|staff|class, idColumn: …}`는 같은 조회 행의 종류별 UUID 칸만 가리킨다. 주소는 앱이 `/students/…`, `/staff/…`, `/classes/…`로 만든다. 이름 검색·외부 URL·다른 종류 ID는 허용하지 않는다. 정렬해도 행의 ID를 유지하고 UUID 칸은 표시·CSV 열에서 뺀다. 예전 답도 명시된 종류별 ID가 있으면 연결하며, ID 없는 이름은 글자로 남긴다. 같은 탭 이동이면 판만 닫고 대화·초안을 보존한다. 목적지의 기존 접근 권한은 그대로 확인한다.
- **담당 필수:** 학생 이름·학교·학년·반 표에는 담당 열도 조회한다. 반별 담당을 짝지으며 현재·과거 시점을 섞지 않는다. 담당 누락은 서버가 재작성을 요청한다. 예전 답·시간 제한 답에서 담당을 확인하지 못한 경우에도 화면에는 담당 열을 `미확인`으로 표시한다. 실제 미배정·담당 없음과 구별하며 원본 조회 행은 바꾸지 않는다.
- **처리 인증:** '로그인이 필요합니다'는 처리 API의 인증 문이 낸 401이다. 쓰기 전 401일 때만 브라우저의 실제 세션을 갱신해 같은 잠금 시각·본문으로 한 번 다시 요청한다. 실패하면 메모와 폼을 남기고 재로그인 경로를 준다. 403·409·500·통신 끊김은 반복 저장하지 않는다. 세션 갱신 자체가 오래 걸려도 원래 요청의 취소 기한을 지킨다. 운영 브라우저의 정확한 만료·쿠키 원인을 재현했다는 뜻은 아니며 서버 인증·본인 소유·권한 검사는 유지한다.
- **환경:** 사용자가 Vercel `eywa`의 OpenAI API 키 등록을 확인했다. `OPENAI_API_KEY_ASSISTANT` 우선, 없으면 기존 `OPENAI_API_KEY`를 사용하며 Claude·DeepSeek 연결로 대체하지 않는다. 다른 AI 기능의 선택·폴백은 건드리지 않았다. 새 의존성·DB 마이그레이션·인증/과금 설정 변경은 없다.

저장소 밖 `terra-only-implementation`에 원문·해시·검증 기록을 남겼다. 구독 CLI의 첫 시각화 4사례는 원본 JSON·앱 검사 통과(추이 line·구성 pie·상담 문안에는 차트 없음). 첫 강사 비교는 그림을 생략했다. 주어진 차트용 조회에 미마감·기간 중 퇴사자가 섞여 있었지만 생략 원인 자체를 확인한 것은 아니며 시각화 성공으로 세지 않았다. 명시적인 로컬 필터 조회를 추가한 별도 비교는 원본 JSON 실패를 그대로 보존했고, 같은 Terra low에 검사 오류를 돌려준 별도 재작성에서 bar·정확한 두 시점·단위·대상 범위 검사를 통과했다. 이를 첫 시도의 성공으로 바꾸거나 운영 Responses 전송 검증으로 부르지 않는다. 단위 테스트는 실제 어댑터와 실행기를 연결해 조회→형식 오류→같은 모델 재작성, 대상 ID 유지·담당 검사도 확인한다.

최종 검증은 변경 44파일 범위의 린트·타입 오류 0건이다(`pnpm verify HEAD --skip-tests`). 변경 중 실행한 `pnpm verify HEAD`도 관련 테스트·가드를 기준선과 대조해 새 실패 0건으로 끝났다. 최초에 발견한 로그인 링크의 창 이동 가드 위반은 공용 `EmbedAnchor`로 수정했으며, 별도 처리·이동 검사 20건이 통과했다. 담당 표시·세션 취소·어댑터 재작성의 마지막 변경은 관련 3파일 27건으로 확인했다(앞선 7파일 83건과 중복되므로 합산하지 않는다). 남은 기존 실패 3건은 아이콘 SVG 허용 목록·Windows 출결 경로·AI 기능 목록의 기존 `love_note_draft` 누락이며 HEAD에서도 같은 실패임을 확인했다. 이들을 이번 작업에서 무관하게 고치거나 전체 검사를 추가 실행하지 않았다.
