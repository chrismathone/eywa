# 새 학원 지점장 발급 전 기능·동작 점검 (2026-09-24)

대상: 저장소 `d05b972f`의 AYWA 일반판 코드와 2026-09-24의 `www.aywa.co.kr` 배포 화면. 배포 커밋이 이 저장소 HEAD와 같은지는 확인하지 못했다. 새 학원에 `master` 계정을 발급했을 때 국내 학원관리 제품에서 기대하는 업무를 수행할 수 있는지 확인했다. 경쟁사 정보는 아래 **공식 사이트**의 공개 설명만 사용했다. 경쟁사 제품에 직접 로그인해 시험한 결과는 아니다.

**읽는 순서:** 아래 최초 검사 기록의 실패는 당시 상태다. 최신 판정은 문서 끝의 「배포 가정 최종 검사」에 있다.

## 최초 판정 (수정 전)

**현재 상태로는 “모든 동작이 예외 없이 작동한다”는 판정을 줄 수 없다.** `demo2` 지점장으로 핵심 일부를 실제 저장·조회했으나 로그인 폼에서 비밀번호 URL 노출을 재현했고, 저장소의 빌드·테스트 게이트가 실패한다. 외부 발송, 모든 역할·모듈·예외 입력의 종단 검사는 미완료다. 코드에 존재하는 기능과 새 테넌트에서 바로 켜진 기능도 다르다. 아래 `구현`은 동작 성공을 뜻하지 않는다.

## 기능별 대조표

표기: **기본** = 일반판에 코드 경로가 열림, **선택** = 구현돼 있으나 신규 학원에서 해당 모듈을 켜야 함, **조건부** = 별도 라이선스·채널·연동·설정이 필요, **일부** = 비교 제품의 끝까지 이어지는 흐름 중 일부만 있음, **없음** = 현재 코드에서 그 흐름을 확인하지 못함. 상태는 코드 존재 여부와 공개 기능 대조이며, 실측 범위는 아래에 따로 적었다.

## 확인한 출시 차단 요인과 잔여 위험

1. **P0 — 로그인 URL에 비밀번호 노출**: 배포판에서 하이드레이션 전 로그인 버튼을 누르자 폼의 기본 GET 제출로 이메일·암호가 URL에 포함됐다. 이 암호는 즉시 교체했다. 로컬 폼에 `method="post"`를 넣어 기본 제출을 POST로 바꾸고 단위 테스트를 추가했으나 **미배포**다. 배포 후 JS 비활성/느린 로드 상태에서도 URL과 네트워크를 재검사해야 한다.
2. **P1 — 빌드 게이트 실패**: TypeScript 오류 4건을 해결하고 `pnpm typecheck`·`pnpm build`를 통과시켜야 한다. 현재 `pnpm build`는 별도 실행하지 않았다.
3. **P1 — 테스트 게이트 실패**: 재현된 7개 실패 중 실제 결함과 낡은 기대를 확정해 코드 또는 테스트를 고쳐야 한다. E2E는 AYWA 전용 포트를 쓰고 기존 서버 재사용 시 앱 식별을 검증해야 한다.
4. **P1 — 신규 학원 실측 공백**: 직원/권한, 담임·시간표, 출결, 보강, 상담 전환, 성적·보고서, 분납·환불, 삭제·복구, 19개 선택 모듈, 모바일/데스크톱 모든 사용 동선과 예외 입력은 끝까지 저장·재조회하지 못했다. 운영 중인 `cs`에 쓰는 교차 지점 테스트는 하지 않았다.
5. **기능 노출 차이**: 새 테넌트는 19개 모듈이 모두 꺼져 출발한다. 온보딩 9단계 이후 무엇을 켜서 제공할지 계약/설정이 확정되어야 비교표의 “선택” 기능을 약속할 수 있다.
6. **실발송 설정**: `resolveKakaoChannel`은 라이선스·채널·템플릿이 없으면 `null`이고 키오스크는 `simulated`로 기록한다. 실제 학원 발급 후 “알림이 갔다”고 판단하기 전에 발송 로그와 학부모 수신을 확인해야 한다.
7. **시장 기능 격차**: 결제 승인과 자동 수납 반영, 학부모용 양방향 화면, 자동 청구, OMR/문제은행, 근태, 증명서는 비교 제품의 공개 기능과 다른 범위다. 이는 런타임 버그와 구별해 판매 설명에 반영해야 한다.

## 나머지 신규 지점장 종단 검사 순서

격리된 테스트 테넌트 A/B와 학부모 발송 수신 번호, 결제 테스트 환경에서 진행한다. 각 단계는 **생성→새로고침→수정→삭제/취소→재로그인**을 포함하고, B의 ID를 A 세션에서 직접 요청해 읽기·쓰기 모두 거부되는지 확인한다.

1. 슈퍼관리자로 A/B 발급 → 두 master 로그인 → 비밀번호 변경 → 학원 브랜딩·과목·교시·계좌·약관 저장.
2. A에서 직원 2명과 역할·권한 설정 → B 직원/원생이 모든 검색·직접 URL·API 응답에서 보이지 않는지 확인.
3. 강의실·반·시간표 생성 → 충돌·요일/교시 변경 → 학생 단건/엑셀 등록 → 중복·동명이인·잘못된 엑셀 행 처리.
4. 수강 배정·반이동·휴원·복귀·퇴원 → 일별/월별 출결·보강 예약·키오스크 체크인/퇴실, 알림 수신·실패 로그.
5. 상담/QR 접수→등록, 성적·수업보고서→공유/인쇄, 청구→분납/취소/환불/미납·엑셀 금액 대조.
6. 선택 모듈을 하나씩 켜고 새로고침/URL 직접 접근/서버 액션을 확인한 뒤 다시 꺼서 차단되는지 확인.
7. 데이터가 0/1/1,001건인 상태, 두 탭 동시 수정, 네트워크 실패, 모바일 폭, 인쇄, 시간대 경계(23:59/월말)를 확인.
8. 새 테넌트의 DB 행·Storage 객체·감사로그·알림/푸시/외부 연동이 A에만 귀속되는지 대조.

이 종단 검사를 통과하기 전에는 “타 학원에 바로 제공해도 예외 없이 동작”이라고 표시하지 않는다. 슈퍼관리자용 전 지점 관리 화면은 별도 워크트리 `superadmin-all-branches`에서 구현했고, 감사 수정 브랜치 위로 리베이스해 타입 검사·빌드를 통과했다. 미배포이므로 이 보고서의 배포판 판정에는 포함하지 않는다.

### 남은 한계와 발급 판정

**무조건 발급·무예외 보증은 불가.** 경쟁사 공식 자료 19개 제품과 대조한 45개 업무 중 학부모 앱/양방향 채팅, 실제 카드·링크 결제와 자동 수납 반영, OMR·문항 분석, 출퇴근 근태, 자동 증명서 등은 현재 제품 범위에 없다. 구현된 기능이라도 전체 역할·모듈 조합, 예외 입력, 대량 데이터, 모든 모바일 화면을 완주한 증거는 아니다.

특히 환불은 요청서와 청구/결제 상태가 분리돼 있다. 실제 환불 완료를 표시해도 송금·PG 취소 또는 청구액 갱신이 자동이라는 보증을 해서는 안 된다. 신규 학원의 19개 선택 기능은 기본적으로 모두 꺼져 있으므로 비교 제품에 있는 기능으로 계약하려면 학원별 활성화와 해당 기능별 운영 검사가 필요하다. 메인 환경에는 빌드 로그상 `NEXT_PUBLIC_APP_URL`과 `CRON_SECRET`이 없어서 음성 전사 콜백·관련 복구 cron은 이 환경에서 동작한다고 판정할 수 없다. Vercel 운영 환경 변수는 확인하지 못했다. 카카오 실발송·외부 makeedu/ClassNote/구글 동기화·실결제는 테스트 채널과 별도 자격이 없어 종단 실측하지 않았다.

슈퍼관리자 전 지점 관리 화면은 코드·서버 권한 검사와 빌드는 통과했으나 실제 슈퍼관리자 브라우저 계정으로 발급·수정·지점 전환을 완주하지 못했다. 다중 지점 본사 운영의 판매 약속은 이 화면의 실제 권한·감사 로그·테넌트 전환 실측 전까지 보류한다.

**배포를 가정한 결론:** `demo2`의 학생·직원·반·출결·상담·수동 수납과 기능 차단은 위 범위에서 작동했다. 학원 프로그램 전체를 ACA2000·메이크에듀 등과 동등하고 예외 없는 서비스로 보증할 근거는 없다. 신설 지점에 제공한다면 지원 기능과 외부 연동/결제/환불의 범위를 명시한 제한된 시범 운영으로만 판정한다.
