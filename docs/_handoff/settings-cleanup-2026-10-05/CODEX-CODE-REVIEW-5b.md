## 추가 반증 결과

- **input·checked의 출처**: 초기 검증의 input은 요청자가 보낸 parsedJson이다. 병합 검증의 checked는 **그 요청만이 아니라 DB fresh 값과 다른 창이 저장한 값도 포함한** merged다. helper의 ‘사용자가 보낸 값’ 주석은 병합 호출까지 설명하지는 못한다. 하지만 이 호출은 운영 쓰기 권한을 먼저 검사한 같은 학원 actor의 경로이고, 화면에는 checked 전체를 보내지 않고 허용된 오류 위치의 이름만 보낸다. 다른 사람의 과목 이름이 표시될 수 있지만 같은 설정의 읽기 가능한 이름이므로 새로운 권한 우회 근거는 없다. 주석은 구현 시 유의로 고치면 된다. `src/features/owner/server/actions.ts:110`, `:231`, `:236`, `src/features/owner/server/operations-save.ts:110`, `:115`, `:127`, `src/features/owner/settings-error.ts:103`.
- **PIN·민감 값**: quoteName은 숫자 인덱스로 들어간 객체의 label/name/title만 읽고, 현재 seatPins 스키마는 lab/jj 문자열 객체여서 실제 PIN 오류 path에 숫자 인덱스가 없다. 실제 billing 계좌에서는 별칭 label을 읽으며 number/holder를 이름 후보로 읽지 않는다. 직원 UUID·담당자 명단처럼 문자열 배열은 이름 대신 차례를 표시한다. 과목·영역·양식·그룹 이름은 원래 화면 표시값이다. malformed 요청에 직접 넣은 label/name/title을 되돌릴 수는 있어도 그것이 다른 사람의 비밀번호를 가져오는 경로는 찾지 못했다. `src/features/owner/settings-error.ts:111`, `:113`, `src/features/owner/settings-types.ts:279`, `:384`, `src/features/owner/settings-error.test.ts:167`. checked와 issue를 통째로 OwnerSaveState에 싣는 변화도 없다(`server/actions.ts:236`).
- **locate 경계**: input과 path가 어긋나면 node는 undefined로 내려가며 이름 대신 차례/허용 칸 이름을 사용한다. Symbol은 문구 이름으로 변환하지 않는다. 반복문이라 경로를 재귀적으로 순회하지 않으며 실제 스키마 오류 깊이는 선언된 구조에 제한된다. B1의 상속 속성은 예외다. 음수/NaN 같은 숫자 token은 정상 Zod 배열 오류에서 생기지 않으므로 정상 입력 경로의 발견 사항으로 올리지 않았다. `src/features/owner/settings-error.ts:108`, `:110`, `:115`, `:118`.
