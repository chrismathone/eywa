# 대규모 디자인 수정 세션 인수인계 — 메뉴 컴팩트화·버튼형 진입·창모드

작성일: 2026-09-07 KST.

이 문서는 사용자의 요청 **“대규모 디자인 수정 세션에 우리가 대화한 모든것을 아주 자세하게 넘겨줄 수 있겠나?”**에 따라 메인 세션의 논의와 산출물을 전달한다. 이 패키지와 전달 메시지가 인수인계의 본문이다. 수신 세션의 기존 시간표·색상·정렬·드래그 작업을 취소하거나 덮어쓰는 지시가 아니다.

## 먼저 읽을 내용

1. 사용자는 **왼쪽의 축약된 메뉴 구성을 좋아했다.**
2. 사용자가 직접 **“왼쪽 업무군을 누르면 본문에 버튼들이 나타나고, 그 버튼을 눌러 메뉴에 진입”**하는 방식을 제안했고, 최종적으로 **“버튼형으로 갈꺼니까 그렇게 넘겨”**라고 확정했다.
3. 그 방향으로 만든 HTML에 **“버튼 시안 아주 좋고”**라고 명시적으로 긍정했다. **버튼형은 후보안이 아니라 구현 방향이다.** 다시 플라이아웃/버튼 중 선택하라고 묻지 말 것.
4. **파스텔은 요구 사항이 아니다.** 사용자는 “꼭 버튼은 파스텔일 필요는 없음. 디자인은 맡길게”라고 말했다. 최신 시안은 흰색·얇은 테두리·네이비 SVG 아이콘이다.
5. 사용자는 버튼형 진입으로 바꿀 때 **iframe과 창모드를 유지할 가치가 있는지 질문했다.** 답변은 “이번에는 iframe을 유지하되, 기본은 큰 작업 화면 하나, 필요할 때 나란히 보기”였다. **이 아키텍처 답변에 대한 사용자의 명시적 수락·실행 지시는 아직 없었다.** 디자인 승인과 구분할 것.
6. 실제 앱 코드는 이 논의에서 수정하지 않았다. 산출물은 분석 문서, HTML 시안, 검증 이미지와 이 전달 자료다. HTML은 운영 앱이 아니라 화면 배치를 검토하는 모형이다.

## 3. 메뉴 전수 조사에서 확인한 사실

첨부 기존 사이드바의 독립 메뉴는 23개다. `NAV_GROUPS`에는 총 27개 정의가 있고 숨김 3개를 제외하면 권한 적용 전 후보는 24개다. 이미지에 없는 추가 후보는 관리자 기본 권한이 없는 선생님 원스크린이다. 실제 사용자별 메뉴 수는 권한에 따라 달라진다.

- 홈: 운영실, 캘린더.
- 수업: 시간표, 강사 시트, 출석부, 수업목록, 수업보고서. 조건부 선생님 원스크린.
- 학생: 학생목록, 성적관리, 학생상담, 등록상담, 이탈 방어, 퇴원관리.
- 운영: 직원관리, 수납관리, 셔틀, 재고관리, 회의록, 수업 평가, 전자결재, 데이터베이스.
- 지원: 도움말, 학원 설정.
- 숨김 정의: 교재 요청, 지출결의서, 관리자 도구.

현재 사이드바는 행 높이 36px, 행 사이 약 4px, 그룹 제목 22px다. 단순히 글씨를 줄이는 방식보다 항목 수·중복 탐색을 줄이는 쪽으로 판단했다. 접힘 52px 레일·드래그 폭 조절은 이미 있으므로 새 기능인 것처럼 재제안하지 않는다.

## 4. 최종 버튼형 시안의 왼쪽 구성과 목적지

### 상단 즐겨찾기 예시 4개

시간표 / 강사 시트 / 출석부 / 학생목록.

이는 예시이며 실제 사용 빈도를 측정하지 않았다. 운영실·캘린더와 즐겨찾기는 한 번 클릭으로 작업 화면에 바로 들어간다. 사용자가 즐겨찾기를 변경·고정하는 실제 기능은 시안에 구현돼 있지 않다.

### 전체 업무 8개

| 왼쪽 항목 | 진입 방식 | 본문 버튼 또는 목적지 |
|---|---|---|
| 운영실 | 직접 | 기존 대시보드 작업면 |
| 캘린더 | 직접 | 캘린더 |
| 수업 | 버튼형 메뉴 | 시간표, 영어 강사 시트, 수학 강사 시트, 출석부, 수업목록, 수업보고서, 수업 평가, 조건부 선생님 원스크린 |
| 학생 | 버튼형 메뉴 | 학생목록, 성적관리 |
| 상담·재원 | 버튼형 메뉴 | 학생상담, 등록상담, 이탈 방어, 퇴원관리 |

| 문서·결재 | 버튼형 메뉴 | 회의록, 전자결재, 데이터베이스 |

하단: 설정 / 도움말 + 계정 자리. 설정을 누르면 학원 정보 / 수업·운영 / 청구·안내 / 계정·권한 / 시스템 5개 버튼이 나타난다. 도움말은 직접 열린다.

‘14개’는 8개 전체 업무 + 4개 즐겨찾기 + 지원 2개를 모두 센 **상시 노출 위치 수**다. 즐겨찾기의 중복 입구도 포함했다. 기능 수를 23→14개로 삭제했다는 뜻이 아니다. 본문에는 기존 목적지가 모두 남는다. PC 사이드바 탐색 본문 버튼은 12개이고 지원이 하단 2개다.

### 디자인 방향

- 메뉴 선택 화면은 기존 학원색을 사용하는 흰색 버튼과 얇은 테두리.
- 개별 메뉴 아이콘은 기존 `EyIcon` SVG. 임의의 새 아이콘 체계를 만들지 않았다.
- 버튼: 약 108px 높이, 12px 모서리, 48px 아이콘 받침, 17px 메뉴명, 11px 설명.
- 넓은 PC: 3열. 1120px 이하: 2열. 모바일: 2열, 아이콘 위·메뉴명 아래 형태, 146px 정도 높이.
- 큰 배너·장식·애니메이션 없이 업무군 제목과 짧은 안내, 메뉴명·기능 설명을 보여준다.
- 버튼 클릭 뒤에는 실제 작업 화면의 작은 내부 탭을 유지하는 방향. 모든 하위 선택을 다시 큰 버튼으로 만들지 않는다.
- 작업 화면에서 ‘← 수업 메뉴로 돌아가기’와 같이 **어디로 돌아가는지 명시**한다.
- 버튼형 메뉴를 보여줄 때 왼쪽 항목의 세로 위치는 움직이지 않는다.
- 보통 2회 클릭(업무군→메뉴)이므로 자주 쓰는 메뉴는 즐겨찾기에서 1회 클릭으로 접근한다.
- 메뉴의 색은 새 상태 의미를 만들지 않는다. 대상 세션이 구현 중인 학생 상태·담임 색상 규칙과 이 메뉴 디자인을 섞지 말 것.

## 5. 내부 탭 재편 제안 — 개별 확정은 아님

동봉 분석 §4를 우선 참조. 기능 삭제가 아니라 선택 계층 재정리다.

### 학원 설정 11→5개 범주

- 학원 정보: 프로필·브랜드.
- 수업·운영: 운영 체계, 과목 운영. 과목의 세션 기간은 과목 운영 안에 유지.
- 청구·안내: 수납·청구, 알림·약관, 상담 양식, 팝업 공지.
- 계정·권한: 역할·권한.
- 시스템: 데이터 정리, 감사로그, 연동.

범주 아래 4개 탭을 또 누적하기보다 설정 목차/선택기를 쓴다. 11개 기존 URL을 유지하고 선택한 설정만 조회한다.

### 수납 최대 8개 + 계산기 5개 → 기본 5개 + 도구·설정

- 기본: 수납, 교재, 지출, 환불 요청서, 강사 정산(master만, 다른 역할은 4개).
- 계산·정산 도구: 수강료 계산기, 회차 확정, 시수 검증, 저장된 청구서.
- 단가·휴일: 수강료 단가, 교재 단가표, 공휴일.
- 교재 단가표를 교재와 계산기에서 별개 화면처럼 중복 유지하지 않는다. 기존 두 URL의 호환 진입은 남길 수 있다.
- 회차 확정·시수 검증을 매일 쓰는 사람은 그 도구 자체를 즐겨찾기할 수 있어야 한다.
- 계산식·청구 처리 순서는 이 디자인 변경에서 바꾸지 않는다.

### 수업보고서 최대 8→기본 4개

- 기본: 작성률, 목록, 반 공지, 반 구성.
- 직접 발송은 명확한 실행 버튼으로 기존 작성 화면 진입.
- 회수는 관리 메뉴에서 기존 회수 화면으로 연결. 일괄 회수 기능을 행 버튼 하나로 축소하지 않는다.
- 보고서 설정·AI 멘트는 설정 메뉴.

### 학생 상세 9→5개

- 개요 → 개요.
- 수업·출결 → 기존 수업, 출결.
- 학습 → 기존 성적, 진도.
- 상담·기록 → 기존 상담, 메모, 타임라인.
- 수납 → 기존 수납, 별도 권한 유지.

옛 `?tab=grades`, `?tab=timeline`을 열면 새 큰 영역 안의 해당 내용이 직접 선택되도록 한다. 탭 숫자를 줄이기 위해 9개 본문을 모두 마운트·조회하는 구현은 하지 않는다.

### 전자결재 7→4개 큐 + 상태 필터

전체 / 결재 대기 / 결재 예정 / 참조를 기본으로 남기고 진행 / 완료 / 반려·회수는 전체 큐의 필터로 옮기는 제안이다. 대기와 예정은 업무 의미가 다르므로 유지한다. 기존 각 조회의 범위를 검증해야 한다.

캘린더·이탈 방어·재고·셔틀의 4개, 직원 상세의 3~4개는 유지가 우선이다. 적은 개수의 서로 다른 업무까지 억지로 통합하지 않는다.

## 6. iframe·창모드 질문과 권고의 정확한 의미

사용자는 버튼형 디자인을 긍정한 뒤 다음을 물었다:

> 버튼 시안 아주 좋고, 구조적으로 버튼 시안으로 갔을때, ifram을 지금처럼 유지하는게 더 좋아 보여 ? 어떄? 창모드가 계속 진행하는게 장점이 있을까?

답변의 핵심은 세 가지를 분리하는 것이다.

| 층위 | 다루는 문제 | 이 세션의 판단 |
|---|---|---|
| 버튼형 메뉴 | 어디로 들어가는가 | **사용자가 최종 확정한 구현 방향** |
| 여러 작업 화면·창 | 화면들을 어떻게 함께 쓰는가 | 학원 관리 업무에서 유지 가치가 있음 |
| iframe | 작업 화면을 어떤 기술로 실행하는가 | 단기 유지 권고, 장기적으로 성능·복잡도를 보고 교체 여부 판단 |

### 창모드를 남길 실제 업무상의 이점

- 시간표를 보며 강사 시트를 확인하는 경우.
- 학생 기록을 참고하며 상담 내용을 작성하는 경우.
- 출석부와 수납관리의 출결·회차를 대조하는 경우.
- 같은 메뉴에서 서로 다른 학생·반을 나란히 비교하는 경우.
- 다른 업무를 잠깐 보고 돌아왔을 때 스크롤·기간·선택·작성 중인 내용을 이어가는 경우.

이 예시들은 업무 성격을 바탕으로 든 사용 시나리오다. 사용자 로그를 계측해서 빈도를 확인한 결과는 아니다.

### 권고한 사용자 경험

1. 왼쪽 업무군 선택 → 본문에 해당 메뉴 버튼.
2. 메뉴 버튼 선택 → 작업 영역을 넓게 채워 한 화면을 기본으로 표시.
3. 다른 메뉴로 이동 → 기존 작업을 유지하고, 열린 작업 목록에서 다시 선택.
4. 비교할 때만 ‘나란히 보기’로 두 화면 배치.
5. 자유로운 창 이동·리사이즈는 추가 기능으로 유지.

여기서 ‘큰 작업 화면’은 **브라우저 전체화면 API**가 아니라 앱의 주 작업 영역을 넓게 채우는 표시 방식이다. 작은 플로팅 창을 여러 개 띄우고 사용자가 매번 정렬해야 하는 것을 기본 사용 흐름으로 삼지 않겠다는 제안이다. 창 기능의 가치는 남기되, 일상적인 한 화면 작업은 단순하게 만든다.

메뉴로 돌아갈 때 기존 작업을 닫지 않는 것이 핵심이다. 기존 창이 있는 메뉴를 다시 선택하면 원래 창에 포커스하고, Shift+클릭 같은 명시적 요청으로만 복제 화면을 열 수 있다. 기본 클릭의 ‘루트 화면으로 리셋’ 등 현재 동작과의 차이는 수신 세션에서 구체화해야 한다. 이 세션에서 실제 창 동작을 수정하지 않았다.

### iframe을 당장 유지하자고 한 이유

- 이미 있는 Next 라우트·서버 조회·페이지별 권한을 독립 화면으로 재사용할 수 있다.
- 현재 창별 탐색, 뒤로가기, 타이틀 갱신, 인쇄·미저장 가드 등이 iframe 구조에 맞춰 연결돼 있다.
- 버튼형 메뉴는 입구 변경이므로 엔진 전체 교체를 동시에 해야만 하는 구조적 이유가 없다.
- 메뉴 개편·기본 표시 방식·엔진 교체를 한꺼번에 진행하면 회귀 범위가 커진다.

### iframe의 비용

- 프레임마다 별도 document/실행 환경이 생기므로 메모리·JS 실행·하이드레이션 비용이 추가된다. HTTP 파일 캐시가 공유돼도 모든 실행 상태가 한 인스턴스로 공유되는 것은 아니다.
- 프레임마다 QueryProvider·여러 컨텍스트가 구성된다. 최상위 React 라우터 상태와 동일한 상태 공간으로 취급할 수 없다.
- 저장 후 다른 화면 갱신, 포커스, 단축키, 녹음·미저장 잠금 등을 프레임 간에 연결해야 한다.
- 화면을 숨기는 것과 모든 백그라운드 작업을 중단하는 것은 같은 동작이 아니다. 실제 폴링·연결·재조회 정책을 계측해서 관리해야 한다.
- 같은 origin iframe을 보안 격리나 권한 그 자체로 설명하지 말 것. 권한은 기존 서버 액션·페이지 게이트·RLS가 담당한다.

웹 확인 근거: [MDN iframe 설명](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe). 문서마다 실행 환경·자원 비용이 추가된다는 점을 확인했다. 사용자에게 “이번에는 버튼 메뉴와 작업 전환부터 개선하고, 이후 실제 속도·동시 작업 수를 측정해서 iframe 교체 범위를 정하자”고 답했다. 여러 작업 화면을 유지하는 기능은 iframe 없이도 구현할 수 있으므로 **창모드 유지=iframe 영구 유지**는 아니다.

## 7. 구현에서 놓치면 안 되는 연결

### 권한과 탐색

- 그룹의 표시 조건은 자식 중 접근 가능한 목적지가 하나라도 있는가로 정한다. 그룹에 기존 한 메뉴의 권한만 재사용하지 않는다.
- 특히 영어 ECS와 수학 MCS는 독립 권한이다. ECS 없음 + MCS 있음인 계정도 수학 시트 버튼에 접근할 수 있어야 한다.
- 학생상담과 등록상담도 독립 권한·창이다. 같은 업무군에 놓는다고 하나의 권한으로 합치지 않는다.
- 수납 강사 정산 master 전용, 보고서 직접 발송·회수 쓰기 권한, 보고서 설정 owner 쓰기, 학생 수납 권한, 직원 활동 로그 조건, EiE 전용 MP를 유지한다.
- 관리자/강사/학생 셸은 이미 다르다. 강사 홈과 ‘내 메뉴’를 관리자 버튼 허브로 대체하지 않는다.

### 메뉴 정의와 검색

- `NAV_GROUPS`, `SUBTABS_BY_MENU`, 각 페이지 FaceTabs를 따로 하드코딩하면 서로 어긋난다. 목적지 정의와 노출 표면을 분리하고 공유한다.
- 현재 command-palette와 관리자 모바일 메뉴는 부모 `NAV_GROUPS`만 사용한다. 내부 탭을 숨기기 전에 내부 목적지 검색·모바일 진입을 보완해야 한다.
- MCS는 `NAV_GROUPS`에 독립 부모가 없고 ECS 하부탭으로 정의돼 있으므로 관리자 모바일·검색에 직접 항목이 없다. 강사 ‘내 메뉴’에는 이미 MCS가 있다.
- ECS 페이지의 MCS 링크는 빈 상태 안내용이라 항상 보이는 공통 과목 전환기를 대신하지 못한다.
- 화면 이름을 바꾸면 페이지 metadata/창 제목도 함께 맞춘다. 새 그룹명 추가는 기존 화면명을 모두 바꿔야 한다는 뜻이 아니다.

### 탭 제거와 기능 유실 방지

- `features/shuttle/faces.ts`는 지금 `SUBTABS_BY_MENU.shuttle`에서 파생한다. 사이드바 하부탭이 불필요하다고 정의 배열을 삭제하면 셔틀 화면 안 탭도 사라진다. 데이터 정의와 사이드바 노출을 먼저 분리할 것.
- 재고 내부 탭은 이미 왼쪽에서 숨기는 정책이다. 새 그룹 정의 과정에서 다시 중복 노출하지 않는다.
- 출석부 기본 진입은 월별이고, 셔틀 기본 진입은 노선 편성이다. 빈도가 높아 보인다는 추정으로 기본 착지를 임의 변경하지 않는다.
- LAB/JJ 자리 출석부는 강사 선택의 갈래이며 독립 좌측 메뉴로 승격시키지 않는다.
- 셔틀 실시간 위치는 조사 시 준비 화면이었다. 지도·GPS 완성 기능처럼 시연하거나 홍보하지 않는다.
- 개발 시간표·등록상담 옛 대시보드·구 직원 급여·구 휴가 메뉴를 되살리지 않는다.

### 작업 상태와 성능

- 기존 `menuKey`, `windowId`, 창 크기 정책은 업무군 ID와 분리한다. 수업 그룹으로 묶었다고 시간표와 강사 시트를 한 창 식별자로 합치지 않는다.
- 현재 URL의 `embed=1`, 탭, 하위 탭, 날짜·주·월, 과목·반, 셔틀 시즌을 보존한다.
- 작성 중인 상담·보고서·시트 상태, 미저장 닫기 가드, 녹음 잠금을 유지한다.
- 큰 영역 5개로 묶었다고 그 안의 기존 11개/9개 페이지를 전부 미리 렌더하지 않는다. 선택한 화면만 필요한 조회를 수행한다.
- 메뉴 허브 자체는 가벼운 목적지 목록이어야 한다. 8개 버튼에 각 업무 데이터·대형 컴포넌트를 미리 가져오지 않는다.
- 창을 감추고 메뉴를 보여주는 실제 연결은 구현이 필요하다. HTML에서 `display:none`을 토글하는 것만 보고 앱의 전체 창 상태 보존이 구현됐다고 간주하지 않는다.

## 8. HTML이 구현한 것과 생략한 것

구현한 시안 동작:

- 기본은 수업 업무군의 8개 메뉴 버튼.
- 현재 구조 / 버튼형 시안 비교 전환.
- 왼쪽 축약 업무군 및 즐겨찾기 예시.
- 각 업무군 버튼, 수납 도구 버튼, 설정 범주 버튼으로 화면 모형 진입.
- 작업 화면에서 해당 메뉴로 돌아가기.
- 내부 탭·선택기·도구 선택.
- 전체 메뉴·내부 이름 검색.
- 모바일 메뉴 열기·선택·닫기, 키보드 포커스 이동, Escape 닫기.
- PC/모바일 반응형, reduced-motion 대응, 기존 SVG 내장.

생략·주의:

- **실제 iframe, window-store, 여러 작업 동시 실행은 없음.** 창 타이틀바는 화면 모형이다.
- API·DB·로그인·권한·진짜 업무 본문 없음. 운영 데이터가 들어 있지 않다.
- 최대로 볼 수 있는 메뉴들을 비교한다. 원스크린·급여 등 운영의 역할 조건을 시안이 집행하지 않는다.
- 학생목록 버튼에서 바로 학생 상세 탭 예시가 보인다. 실제 앱에서는 목록→학생 선택→상세여야 한다.
- 즐겨찾기는 고정 예시 4개이고 편집·계정 저장은 없음.
- 검색은 화면 이름을 찾아 모형의 선택을 바꾸는 수준이며 실제 href·권한 레지스트리는 아님.
- 과거 플라이아웃 시안의 일부 숨겨진 CSS/함수가 파일에 남아 있다. 현재 추천 동선은 그 함수를 사용하지 않는다. HTML 코드를 그대로 운영 컴포넌트로 복사하지 말고 시각·동선 명세로 사용할 것.
- HTML의 데스크톱 메뉴 피치 34px와 기존 40px는 제안/코드 값이다. 모바일에서 동일하게 32px 클릭 영역을 강제하지 않는다.

## 10. 수신 세션의 후속 진행 제안

1. 진행 중인 기존 사용자 요청과 본 인수인계를 함께 작업 목록에 통합한다. 본문 전달 때문에 기존 색상·정렬·통합뷰 작업을 원복하지 않는다.
2. 이 문서 → 대화 기록 → HTML → 분석 문서 순으로 읽고, 확정도 표를 유지한다. **버튼형으로 진행한다는 사용자의 최종 결정을 실행 방향으로 반영한다.**
3. 수신 브랜치의 현재 메뉴·권한·창 코드와 조사 HEAD의 차이를 확인한다.
4. 버튼형 메뉴의 운영 컴포넌트 구조와 공유 목적지 정의를 설계한다. 내부 탭 통합을 한 번에 강제하지 않는다.
5. 검색·모바일·MCS 독립 권한 진입을 보완한 후 왼쪽 인라인 하부탭을 제거한다.
6. 창 기본 표시 방식은 최종 아키텍처 권고를 토대로 구체화한다. iframe 전면 교체는 이 전달만으로 확정하지 않는다.
7. 실제 구현 시 단일 화면·복귀·두 화면 비교·Shift 복제·미저장 상태·역할별 권한·모바일에서 검증한다.
8. 성능은 새 창 최초 열기, 재진입, 두 화면 동시 사용, 숨긴 화면의 활동을 나눠 측정한다. 과거 문서의 숫자로 완료 판정하지 않는다.

이 인수인계 자체는 사용자에게 이미 요청받은 전달 작업이다. 자료를 읽고 현재 세션의 작업에 이어 반영해 달라는 맥락이며, 새 배포·권한 변경·데이터 삭제까지 일괄 승인한 메시지가 아니다. 이후 우선순위는 수신 세션의 최신 사용자 지시를 함께 반영한다.
